Google Cloud 免费 e2-micro 建站与隐身流量监控实战

很多人开 Google Cloud 的免费 e2-micro，一不留神就被默认的均衡盘（pd-balanced）和高级网络（PREMIUM）悄悄扣费；或者为了看流量，在公网裸奔一个 80 端口监控页。这篇指南记录一套可直接复现的零成本方案：锁定官方免费层级与每月 200 GB 标准出站流量，部署 Xray VLESS-REALITY，并把 Nginx 流量看板彻底藏进加密隧道内部——公网扫描器只看到一个关闭 80 端口的正常 443 服务。

Anaxagore · 更新于 2026-11-15

TL;DR（核心架构与避坑结论）
  • 锁死免费层级四要素：美西机房 us-west1 + e2-micro + 启动盘显式指定 --boot-disk-type=pd-standard --boot-disk-size=30GB + 静态 IP 与网卡显式指定 --network-tier=STANDARD（每月免费 200 GB 出站，入站永久免费）。
  • 避开新版本握手坑：在部分 verge-mihomo 客户端上，Xray v26.10.31 与客户端 X25519MLKEM768 协商存在兼容报错，服务端锁定 v25.8.3 + iosapps.itunes.apple.com SNI 实测稳定连通。
  • 零暴露隐身监控：关掉 GCP 公网 80 防火墙，Nginx 仅监听 127.0.0.1:80；利用 Xray 内部 routing 将隧道内发往 VPS IP 80 端口的请求回环转发至本地看板，外网端口全关，只有自己连着隧道的设备能秒开。

1. 计费避坑：为什么默认命令还是会扣钱？

Google Cloud 的 Always Free（永久免费）对 e2-micro 有非常严格的边界条件，用默认参数开出来的机器往往踩中两个隐形计费项：

资源项 gcloud 默认值（会扣费） 免费层级正确参数
可用区 任意区 仅限 us-west1、us-central1、us-east1
系统盘类型 pd-balanced（均衡永久性磁盘） --boot-disk-type=pd-standard --boot-disk-size=30GB
网络层级 PREMIUM（高级层级，出站约 $0.12/GB） --network-tier=STANDARD（每月免费 200 GB 出站）
静态公网 IP 未绑定运行中实例会按小时计费 绑定在 RUNNING 实例上免费；换 IP 后记得删旧 IP

如果你同时订阅了 Google One AI Ultra（5x），Google Developer Program 还会每月赠送 $40 Google Cloud Credits。注意它不会自动出现在项目里，必须按顺序完成两步：

  1. 先在 Google Cloud 结算控制台 绑定付款方式创建一个结算账户载体（新号同时会获得 $300 欢迎赠金，且试用期默认锁死不扣信用卡）；
  2. 打开 Google Developer Program 权益页，在 Google Cloud Credits ($40) 的下拉框里选中刚才建好的结算账户，额度才会正式入账。
注意：赠金只能抵扣云资源与 Gemini API 费用，不能用于 Cloud Domains 买域名；在免费试用保护模式下买域名会要求升级付费账户并直接刷卡。

2. 一键开出标准层级免费机（Bash 脚本）

下面这段脚本会自动检查当前 gcloud 项目与结算账户绑定状态，并在 us-west1-b 分配一个 STANDARD 静态 IP 创建 e2-micro 实例：

#!/usr/bin/env bash
set -euo pipefail

PROJECT_ID=$(gcloud config get-value project)
REGION="us-west1"
ZONE="us-west1-b"
IP_NAME="e2-micro-standard-ip"
VM_NAME="e2-micro-instance"

# 1. 开启 Compute Engine API（未关联结算账户会报 UREQ_PROJECT_BILLING_NOT_FOUND）
gcloud services enable compute.googleapis.com

# 2. 申请 STANDARD 标准层级静态 IP（200GB/月免费出站）
if ! gcloud compute addresses describe "$IP_NAME" --region="$REGION" &>/dev/null; then
  gcloud compute addresses create "$IP_NAME" --region="$REGION" --network-tier=STANDARD
fi
STATIC_IP=$(gcloud compute addresses describe "$IP_NAME" --region="$REGION" --format="value(address)")

# 3. 创建 30GB pd-standard 磁盘的 e2-micro 实例
if ! gcloud compute instances describe "$VM_NAME" --zone="$ZONE" &>/dev/null; then
  gcloud compute instances create "$VM_NAME" \
    --zone="$ZONE" \
    --machine-type=e2-micro \
    --network-tier=STANDARD \
    --image-family=debian-12 \
    --image-project=debian-cloud \
    --boot-disk-type=pd-standard \
    --boot-disk-size=30GB \
    --address="$STATIC_IP" \
    --tags=http-server,https-server
fi

# 4. 仅放行 443 端口（不开放公网 80）
gcloud compute firewall-rules create allow-proxy-443 \
  --allow=tcp:443,udp:443 \
  --target-tags=https-server || true

如果机器最初不小心用 PREMIUM 建好了，也不必删机重来：先申请一个 STANDARD 静态 IP，执行 delete-access-config 摘掉旧网卡配置，再用 add-access-config --network-tier=STANDARD --address="<NEW_IP>" 挂上新 IP，最后删掉旧静态 IP 即可原地无损切换。

3. 部署 Xray（VLESS + XTLS-Vision + REALITY）与 BBR 加速

选 REALITY 的最大好处是不需要买域名和自签证书，直接借用目标站点（如 iosapps.itunes.apple.com）的官方 TLS 证书做握手伪装。

实测踩坑：为什么服务端锁定 Xray v25.8.3？

实际联调时发现：用最新版 Xray v26.10.31 部署后，本机回环自测 HTTP 204 正常，但 macOS 上的 Clash Verge（verge-mihomo 内核）连接始终报 REALITY Authentication: false（日志显示 is using X25519MLKEM768 for TLS' communication: false），服务端直接将其当成非法探针转发给了目标 SNI。将服务端显式安装为 v25.8.3 后，mihomo 客户端立刻握手成功，延迟稳定在 180~230 ms。

# 1. 开启 TCP BBR 拥塞控制
echo -e "net.core.default_qdisc=fq\nnet.ipv4.tcp_congestion_control=bbr" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p

# 2. 安装指定稳定版 Xray v25.8.3
sudo bash -c "$(curl -fsSL https://github.com/XTLS/Xray-install/raw/main/install-release.sh)" @ install --version v25.8.3

# 3. 生成凭据（记住输出的 PrivateKey / PublicKey）
UUID=$(/usr/local/bin/xray uuid)
/usr/local/bin/xray x25519
SHORT_ID=$(openssl rand -hex 8)

注意新版 xray x25519 输出的公钥字段名可能是 Password (PublicKey):，如果用脚本解析记得兼容匹配，不要只 awk 旧字段 PublicKey: 而漏空值。

4. 隐身流量看板：公网全关 80 端口，只走加密隧道访问

很多人会在 VPS 上装一个 Web 面板看每月流量，但只要把 80 端口暴露在公网上，Shodan/Censys 爬虫每天都会来扫，页面标题一不小心就暴露了代理节点特征。更稳妥的做法是物理关闭公网 80 端口，把监控页藏进自己的 Xray 隧道里。

采集端：/proc/net/dev + vnstat

cron 每分钟跑一次轻量脚本，把网卡 ens4 的累计收发字节数、vnstat --json 按日明细、内存、磁盘、BBR 状态写入纯静态 stats.json，零常驻 Web 框架开销（1GB 内存占用不到 400MB）。

访问端：127.0.0.1:80 + Xray 内部路由

删掉 GCP 的 allow-http-80 防火墙规则，让 Nginx 仅监听 127.0.0.1:80；在 Xray 的 outbounds 加一个 redirect: "127.0.0.1:80"，当客户端连上 443 隧道后访问 http://<VPS_IP>/<SECRET_PATH>/，直接内部直达看板。

服务端 Xray 核心路由配置（/usr/local/etc/xray/config.json）

{
  "log": { "loglevel": "warning" },
  "inbounds": [
    {
      "listen": "0.0.0.0",
      "port": 443,
      "protocol": "vless",
      "settings": {
        "clients": [{ "id": "<YOUR_UUID>", "flow": "xtls-rprx-vision" }],
        "decryption": "none"
      },
      "streamSettings": {
        "network": "tcp",
        "security": "reality",
        "realitySettings": {
          "show": false,
          "dest": "iosapps.itunes.apple.com:443",
          "xver": 0,
          "serverNames": ["iosapps.itunes.apple.com"],
          "privateKey": "<YOUR_PRIVATE_KEY>",
          "shortIds": ["<YOUR_SHORT_ID>"]
        }
      },
      "sniffing": { "enabled": true, "destOverride": ["http", "tls", "quic"] }
    }
  ],
  "outbounds": [
    { "protocol": "freedom", "tag": "direct" },
    {
      "protocol": "freedom",
      "settings": { "redirect": "127.0.0.1:80" },
      "tag": "local-dashboard"
    },
    { "protocol": "blackhole", "tag": "block" }
  ],
  "routing": {
    "rules": [
      {
        "type": "field",
        "ip": ["<YOUR_VPS_IP>", "10.138.0.2", "127.0.0.1"],
        "port": "80",
        "outboundTag": "local-dashboard"
      }
    ]
  }
}

统计脚本与流量数字校准

看板上线时容易遇到两个疑惑，提前写进展示逻辑里最省心：

  • 为什么 TX 和 RX 几乎 1:1？ 代理服务器相当于“中转站”：你下载 1 GB 文件，VPS 先从远端拉取（入站 RX 1 GB，GCP 入站永久免费），再转发给你（出站 TX 1 GB）。真正计入 200 GB 免费额度的只有 TX（出站），不是两者相加。
  • 为什么 /proc/net/dev 比 vnstat 大？ 如果先跑了一段时间再装 vnstat，它只记录安装后的增量，而网卡底层计数器从开机起就在累计。前端计算 max(0, boot_tx - vnstat_total_tx) 补齐首日差额，两边数字就能严丝合缝。

5. 客户端接入与持久化（Clash Verge / FlClash）

  • Clash Verge（桌面端防覆盖）：如果直接改订阅 YAML，下次机场订阅自动更新就会把自建节点冲掉。正确做法是把节点和路由规则写进该订阅关联的 Profile Enhancement Script（Script.js）：把自建节点 unshift 到 proxies 与各 proxy-groups 顶部，同时注入 IP-CIDR,<YOUR_VPS_IP>/32,<NODE_NAME>,no-resolve，保证无论当前切到哪个节点，访问看板都自动走加密隧道。
  • FlClash（手机端扫码踩坑）：FlClash 扫码只认 http://... 订阅配置文件链接，不认单条 vless:// 节点二维码。可以临时起一个随机文件名的 YAML 放在本机或 Nginx 供手机扫一次，手机导入成功后立即删除订阅文件并关闭公网 80 端口，不要长期挂在公网上。

6. 真实复盘：新号第 4 天被 Suspend 了怎么办？

机器部署完第 4 天，突然发现整台服务器 ping 不通，gcloud compute instances list 报错：

Permission denied: Consumer 'projects/<PROJECT_NUMBER>' has been suspended.

有趣的是邮箱里并没有收到封号邮件，检查后发现结算账户依然是 OPEN: True，但打开 Google Cloud 控制台首页顶部出现了一条红字警告，提示“检测到项目可能违反了服务条款”，并附带了一个「提出申诉（Appeal）」表单。

为什么会触发？

新绑卡账号在开通后 3~7 天内会进入 Trust & Safety 的离线复核期；如果刚绑卡就快速建机且连续跑出对称大流量，很容易被自动风控模型判定为可疑代理或高风险测试账户，先下发保护性暂停等待号主确认。

怎么申诉才能快速恢复？

  1. 不要提及任何代理或绕过网络限制的表述，如实说明这是个人学习云原生部署与轻量监控工具的测试环境，并承诺检查防火墙与安全策略；
  2. 提交工单后，实测约 10 分钟就收到了 reinstated 恢复通知邮件，执行 gcloud compute instances start e2-micro-instance --zone=us-west1-b 后原有静态 IP 和磁盘数据原封不动恢复，且账号相当于完成了一次人工白名单校验。
  3. 日常防复封红线：绝对不跑 BT/P2P 版权下载与恶意扫描爬虫；高流量的日常影音尽量走商业订阅分流，把这台纯净的美西节点留给开发测试、AI 工具登录与核心服务，既省 200 GB 额度也最稳。

English summary

This note walks through provisioning a zero-cost Google Cloud e2-micro instance in us-west1 without tripping hidden billing traps: explicitly setting --boot-disk-type=pd-standard --boot-disk-size=30GB and --network-tier=STANDARD (which includes 200 GB/month of free egress traffic).

On top of the VM, we deploy Xray (pinned to v25.8.3 for clean verge-mihomo compatibility) with VLESS + XTLS-Vision + REALITY and TCP BBR. Instead of exposing a traffic dashboard on public port 80, we delete the public HTTP firewall rule, bind Nginx strictly to 127.0.0.1:80, and route port 80 requests inside the encrypted 443 tunnel directly to the local dashboard—keeping the server invisible to public port scanners while giving real-time egress quota tracking across desktop and mobile clients.
