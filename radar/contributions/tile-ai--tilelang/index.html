一、项目定位

Tile Language (tilelang) 是一个构建在 Apache TVM 编译器基础设施之上的 Pythonic 领域特定语言 (DSL)，专为开发高性能 GPU/CPU/加速器内核（如 GEMM、FlashAttention）而设计。它的核心定位是“在保持 Python 生产力的同时，不牺牲底层硬件极致优化的能力”。与 Triton 类似，它允许开发者用 Python 语法写 Kernel；但不同的是，它底层依托 TVM 的 TIRX 中间表示，并深度集成了 Z3 符号求解器，且对多硬件后端的支持极其激进。从证据来看，该项目目前处于高速迭代的 Beta 阶段（最新版本 v0.1.14，2026年9月），不仅第一时间跟进了 NVIDIA Blackwell (SM100/SM120) 的 TMA/TMEM 和 Block-scaled MMA，还原生支持 AMD (CDNA4/RDNA4) 以及 Apple Metal 和 CPU (LLVM)。 对于你（只有 MacBook Air 的资深性能工程师）来说，这是一个绝佳的切入标的。虽然你没有本地 NVIDIA GPU，但该项目拥有**一等公民级别的 Apple Metal 后端**（支持 M 系列 simdgroup 甚至 M5 cooperative-tensor）和 **CPU 后端**。你可以完全在 Mac 上进行核心编译器 Pass (`src/transform`)、JIT 引擎 (`tilelang/jit`)、Metal 算子生成以及 Z3 布局推导的开发与本地 C++/Python 测试。最终的 CUDA 逻辑验证，由于项目支持“无宿主工具链构建 (Host-toolchain-free builds)”和跨主机 CUDA 二进制缓存，你完全可以在 Mac 上生成 PTX/CUBIN，最后利用 Colab 的 T4 跑几十分钟的端到端正确性回归测试。

解决什么问题、给谁用

解决的具体问题：1. 编写极致优化的硬件 Kernel（如适配 DeepSeek MLA 或 DiT 模型的 Block-causal attention）通常需要手写极其复杂的 C++ (CUDA/CuTe/CUTLASS)，开发门槛高、周期长。2. 现有的 Python DSL（如 Triton）在跨平台（特别是 Apple Metal 和纯 CPU）以及极早期新硬件特性（如 Blackwell NVF4、AMD MXFP4）的支持上存在滞后。目标用户：AI 编译器研究员、算子开发工程师、大模型/扩散模型部署工程师。典型场景：为新模型架构快速编写定制化融合算子；在端侧设备（Mac/Windows/CPU）上实现与云端对齐的高性能推理；利用自动调优 (Auto-tuning) 压榨特定硬件的极限算力。

核心目标用户为：1. 资深 GPU/AI 芯片 Kernel 工程师（需要直接操控 TMA、Cluster、Warp specialization 等底层特性）。2. 深度学习系统架构师（需要为 DeepSeek V4、BitNet 等新模型开发非标准算子）。3. 端侧部署工程师（需要在 Apple Silicon 或纯 CPU 上榨取极限性能）。

同类项目与差别

  • OpenAI Triton：两者都提供 Pythonic 的 Kernel 编写体验。区别在于 TileLang 依托 TVM TIRX，原生且深度地支持 Apple Metal 和 CPU 后端（Triton 的 Metal/CPU 支持相对边缘），并且 TileLang 在引入最新硬件特性（如 SM120 Block-scaled GEMM、Metal M5 cooperative-tensor）上表现得更为激进。
  • NVIDIA CUTLASS / CuTe：CuTe 是纯 C++ 模板库，学习曲线陡峭。TileLang 提供了更高层的 Python 抽象，但保留了底层控制力，且 TileLang 实际上包含了一个 CuTe DSL 后端（可将 Python 代码 Lowering 到 CuTe C++ 代码，见 README 2025-12-18 记录）。
  • Apache TVM (TensorIR)：TileLang 是构建在 TVM 之上的。TVM 偏向于端到端的整图编译，而 TileLang 专注于单个 Kernel 的极致开发体验，相当于为 TVM 提供了一个专用的、更现代化的 Kernel Authoring 前端。

二、架构与代码地图

TileLang 的架构设计深受 Apache TVM 影响，采用典型的「Python 前端 + C++ 中间层 + 多后端代码生成」的三层架构。对于只有 MacBook Air 的你来说，这种架构极其友好，因为 90% 的编译与优化逻辑都可以在 Apple Silicon 上本地运行和调试。 1. **前端与 DSL 层 (Frontend & DSL)**：位于 `tilelang/language`。这是用户编写 Kernel 的入口，采用高度 Pythonic 的语法（如 `@T.prim_func`, `T.Kernel`, `T.Parallel`）。它通过 TVM FFI 将 Python AST 转换为底层的 TIRX（Tile IR eXtended）中间表示。 2. **核心编译与变换层 (IR & Transform)**：位于 `src/transform` (C++) 和 `src/layout`。这是 TileLang 的核心大脑。包含大量的编译器 Pass（如循环展开、内存提升、指令映射）。特别值得注意的是，这里深度集成了 Z3 求解器（`maint/layout_inference`），用于自动推导 Shared Memory 的 Layout 和 Swizzle 策略，以消除 Bank Conflict。这部分完全是 CPU 密集型任务，你的 Mac 编译和运行毫无压力。 3. **后端与代码生成层 (Backend & Codegen)**：位于 `src/backend` 及其子目录（`src/metal`, `src/cuda`, `src/cpu`, `src/rocm`）。经过优化的 TIRX 会通过 Backend Registry 路由到特定硬件的代码生成器。项目对 Apple Metal 的支持是一等公民（支持 M 系列 simdgroup 甚至 M5 cooperative-tensor），这意味着你可以直接在 Mac 上生成 MSL (Metal Shading Language) 并验证算子逻辑。 4. **JIT 与运行时层 (JIT & Runtime)**：位于 `tilelang/jit` 和 `src/runtime`。负责将生成的源码（MSL/PTX/LLVM）即时编译为可执行二进制，并绑定 PyTorch Tensor 的数据指针进行 Launch。由于支持「无宿主工具链构建」，你甚至可以在 Mac 上生成 CUDA PTX/CUBIN，利用跨主机缓存机制，最后丢到 Colab T4 上瞬间完成验证。 5. **工具与生态层 (Tools)**：包含性能分析器（`tilelang/profiler`，最近集成了 IKET 和 Wall-clock benchmark）、自动调优器（`tilelang/autotuner`）以及丰富的调试工具（如 Pass Visualizer 和 IR Lower Trace）。

一次调用怎么流过这些模块

一次 Kernel 的编译与执行（以在 Mac 上运行 Metal GEMM 为例）经历了从 Python AST 到硬件二进制的完整数据流： 1. **定义阶段 (Definition)**：用户在 Python 中使用 `@T.prim_func` 装饰器定义函数，通过 `T.Kernel` 划分 Grid/Block，使用 `T.alloc_shared` 分配共享内存，并调用 `T.gemm` 等内置指令。此时，代码并未执行，而是被 TileLang 前端捕获为 Python AST。 2. **触发编译 (Compilation Trigger)**：用户调用 `tilelang.compile(program, target="metal")`。这会将 Python AST 通过 TVM FFI 传递给底层的 C++ 编译器。 3. **中间表示与变换 (IR Lowering & Transform)**：AST 被转换为 TIRX (Tile IR eXtended)。数据流进入 `src/transform`，经历一系列 Pass（如循环展开、死代码消除）。关键的一步是，如果涉及复杂的 Shared Memory 访问，系统会调用 Z3 求解器（`src/layout`）进行符号推导，自动计算出最优的 Swizzle 布局以避免 Bank Conflict。 4. **代码生成 (Codegen)**：优化后的 TIRX 被送入 Backend Registry。由于 target 是 metal，`src/metal` 会接管数据流，将 TIRX 节点遍历并翻译为 Apple Metal Shading Language (MSL) 字符串。 5. **即时编译 (JIT)**：`tilelang/jit` 接收到 MSL 源码，在 Mac 本地调用 Apple 的 Metal 编译器将其编译为可执行的 Metal Library。同时，JIT 会生成一个 Python 包装器（Host Launcher），用于处理参数传递。 6. **执行阶段 (Execution)**：用户将 PyTorch Tensor (`torch.Tensor`) 传入编译好的函数。Host Launcher 会提取 Tensor 的数据指针（Data Pointer）、形状（Shape）和步长（Strides），将其绑定到 Metal Kernel 的参数上，最后在 Apple Silicon GPU 上 Launch Kernel，计算结果直接写回 PyTorch Tensor 的显存中。

扩展点

  • src/backend 及其子目录：接入新后端（如新的 NPU）：在 C++ 层实现新的 Codegen 类继承自基础 Codegen，并通过 Backend Registry 注册。由于项目已解耦了 target，只需关注 TIRX 到目标指令的字符串翻译。
  • src/transform：接入新调度策略/优化 Pass：在 C++ 中编写新的 TVM TIR Pass，通过 `TVM_REGISTER_GLOBAL` 暴露给 Python，并在 `tilelang.compile` 的 Pass 管道中插入。
  • src/op 和 tilelang/tileop：接入新硬件指令（如新的 MMA/WMMA）：在 C++ `src/op` 中定义指令的 TIRX 节点语义，在 Python `tilelang/tileop` 中暴露给用户，并在对应的 Backend 中添加 Codegen 规则。
  • examples/ 目录：接入新模型 Kernel（如 DiT 的 Block-causal attention）：直接使用纯 Python 在 `examples/` 下新建目录，利用现有的 `T.prim_func` 编写逻辑，并添加对应的 `benchmark_*.py` 和 `test_*.py`。

三、本地跑起来（没有 GPU 的 Mac）

安装

  1. git clone --recurse-submodules git@github.com:tile-ai/tilelang.git && cd tilelang
  2. uv venv --seed .venv && source .venv/bin/activate
  3. uv pip install --requirements requirements-dev.txt
  4. uv pip install --requirements requirements-test-metal.txt

哪些路径能真跑

作为只有 MacBook Air 的开发者，你的本地开发边界非常清晰且宽广：\n1. **完全本地执行 (Apple Silicon)**：核心编译器 Pass (`src/transform`)、Z3 布局推导 (`maint/layout_inference`)、JIT 引擎 (`tilelang/jit`)、CPU 后端 (`src/cpu`) 以及一等公民的 Metal 后端 (`src/metal`)。你可以直接在 Mac 上编写、编译并运行 Metal GEMM 算子（如 `examples/matmul_metal`）。\n2. **本地编译 + 异构验证 (Mac -> Colab)**：得益于 PR #1833 引入的「无宿主工具链构建」，你可以在 Mac 上直接将 CUDA Kernel 编译为 PTX/CUBIN（利用跨主机缓存），然后将生成的 Artifacts 丢到 Colab T4 上，仅需几分钟即可完成最终的端到端正确性与性能回归测试（如 `examples/deepseek_mla` 或 `examples/flash_attention`）。

测试

测试框架使用 `pytest`，测试用例集中在 `testing/` 目录下（分为 `python` 和 `cpp`）。在 Mac 上，为了跳过无法执行的 CUDA/ROCm 测试，建议使用命令 `pytest testing/python -k "not cuda and not rocm"`。由于主要执行的是编译器 IR 生成、Z3 求解和 Metal 算子验证，纯 CPU/Metal 子集的测试耗时通常在几分钟内，非常适合本地高频 TDD 开发。

调试

  • 环境变量：使用 `TILELANG_DISABLE_CACHE=1` 强制禁用 JIT 缓存，确保每次修改编译器 C++ 代码后都能重新触发编译。
  • IR 追踪：利用最近合并的 IR Lower Trace (PR #2725) 和 Pass Diff (PR #2375) 工具，在 Python 侧配置 PassConfig 即可 dump 出每一步 TIRX 的变换，这对于调试循环展开或内存提升极其有效。
  • 性能分析：项目已集成 IKET profiler (PR #2515) 并支持 Wall-clock benchmarking (Commit db5584f)，可通过 `tilelang.profiler` 模块注入 timeline 探针。
  • C++ 调试：由于 90% 的编译逻辑在本地，你可以直接使用 `lldb` 附加到 Python 进程，在 `src/transform` 或 `src/layout` 下设置断点，调试 Z3 求解器或 AST 转换逻辑。

CI

CI 依赖 GitHub Actions (`.github/workflows`)。PR 的核心卡点是代码格式化与静态检查。提交前必须在本地通过 `pre-commit run --all-files`（包含 Ruff 检查 Python）以及 `bash format.sh`（调用 clang-format 检查 C/C++）。此外，C++ API 的修改建议先跑一遍 `python3 maint/scripts/audit_cpp_api_style.py` 确保符合规范。

坑

  • Mac 上的 Torch 依赖：根据 `pyproject.toml`，在 Darwin 系统上必须确保安装 `torch>=2.4` 和 `setuptools`，否则 JIT 编译 Torch Extension 时会报错。
  • TVM FFI 冷启动耗时：如果环境中缺少 `torch-c-dlpack-ext`，TVM FFI 在首次 import 时可能会触发缓慢的 JIT 编译，不要误以为是死锁。
  • Metal 后端边界情况：Metal 后端迭代极快（如 Commit 030556d 刚修复了 GEMM buffer region offsets 问题，PR #2252 刚加入 M5 cooperative-tensor）。在 Mac 上测试非常规 Shape 时，如果 simdgroup_matrix 不支持，可能会遇到 Fallback 失败或精度问题，需查阅 `src/metal` 的最新实现。
  • CUDA 交叉编译陷阱：在 Mac 上生成 CUDA 代码时，务必确保不要触发 Launch 逻辑（如分配 CUDA Tensor），否则会直接抛出 Device Not Found 异常。建议将编译与执行逻辑解耦。
