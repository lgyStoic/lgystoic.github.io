一、项目定位

TileLang 是一个基于 Python 语法的领域特定语言（DSL），旨在简化高性能 GPU/CPU/加速器内核（如 GEMM、FlashAttention、LinearAttention 等）的开发。它构建在 Apache TVM 的 TIRX 基础设施之上，通过 Pythonic 的语法让开发者能够专注于算子逻辑与生产力，同时保留对底层硬件（如 TMA、MMA、Tensor Core）的细粒度控制。 对于目前仅有一台 MacBook Air 的候选人而言，TileLang 是一个极其理想的切入点。与重度绑定 NVIDIA 生态的同类工具（如 Triton）不同，TileLang 原生提供了完善的 Apple Silicon (Metal) 和 CPU (LLVM) 后端支持。这意味着你完全可以在本地 Mac 上进行算子逻辑的原型开发、布局推导（Layout Inference）和正确性验证，甚至利用 Metal 的 simdgroup_matrix 和 M5 cooperative-tensor 特性进行端侧性能调优。验证无误后，同一套代码可以通过切换后端，直接在 Colab 的免费 T4 GPU 上编译为 CUDA 内核进行最终确认。这种跨平台能力完美契合了你当前的硬件约束。 项目目前处于 Beta 阶段（v0.1.14），但迭代极其迅速。它不仅支持了前沿的硬件特性（如 Blackwell SM100/SM120、AMD CDNA4），还在积极跟进大模型领域的最新需求，例如 DeepSeek V3/V4 相关的稀疏算子（Sparse MLA）。对于擅长算子融合、分布式训练性能和端侧部署的资深工程师来说，TileLang 提供了一个极具潜力的基础设施，既能发挥你在 CUDA/CuTe 上的深厚积累，又能让你在无 GPU 环境下保持高效产出。

解决什么问题、给谁用

手写 CUDA/CUTLASS 门槛极高且难以跨架构移植；复杂 AI 算子（如 Block-scaled GEMM、Sparse MLA）在不同硬件上的开发和调优成本巨大；缺乏在无 GPU 环境下（如 Mac/CPU）进行高性能算子逻辑验证的有效手段。

目标用户为 GPU Kernel 工程师、AI 编译器工程师、大模型推理/训练性能优化专家。典型使用场景包括：开发前沿大模型（如 DeepSeek V3/V4、BitNet）的定制化高性能算子；在 Mac (Apple Silicon) 上进行算子逻辑的原型开发与验证，随后无缝编译部署到云端 NVIDIA/AMD GPU 上；利用自动调优（Autotuner）探索最佳 Tile 调度策略。

同类项目与差别

  • OpenAI Triton：Triton 是目前最流行的 Pythonic GPU DSL，但重度绑定 GPU 生态，对 Apple Silicon (Metal) 和 CPU 支持极弱。TileLang 提供了完善的 Metal 和 CPU 后端，允许在 Mac 上闭环开发。
  • NVIDIA CUTLASS / CuTe：C++ 模板库，性能极致但学习曲线陡峭，且仅限 NVIDIA 硬件。TileLang 提供了 CuTe DSL 后端，用 Python 语法封装了 CuTe 的核心概念，并支持跨平台。
  • Apache TVM (TensorIR)：TVM TIR 偏向底层编译器 IR，手写难度大。TileLang 建立在 TVM TIRX 之上，提供了更高层的 Tile 级编程抽象和自动调优。

二、架构与代码地图

TileLang 的架构设计深受 Apache TVM 影响，但专门针对高性能 Kernel 开发进行了领域特定（DSL）的抽象与精简。整体架构自上而下可分为四个核心层，完美契合你「本地 Mac 原型开发 -> 云端 GPU 验证」的工作流。\n\n1. 前端 DSL 层 (Python Frontend)：位于 tilelang/language 和 tilelang/tileop。这是你直接交互的层级，提供 @T.prim_func、T.Kernel 等 Pythonic 装饰器和上下文管理器。它允许你用类似 Triton 的语法编写算子逻辑，但保留了对底层硬件（如 T.mma_gemm_blockscaled、T.tma_copy）的细粒度控制。\n\n2. IR 与变换层 (IR & Transform)：位于 src/transform、src/layout 和 tilelang/transform。这是 TileLang 的核心大脑，基于 TVM 的 TIRX 基础设施。当你调用 tilelang.compile 时，Python AST 会被 lowering 为 TIRX。随后，一系列 C++ 编写的 Compiler Passes 会在此执行，包括极其关键的「布局推导 (Layout Inference)」。该层集成了 Z3 Solver (z3-solver) 进行符号化形状推导，确保在无 GPU 环境下也能完成复杂的内存排布计算和正确性校验。\n\n3. 后端代码生成层 (Backend Codegen)：位于 src/backend、src/metal、src/cuda 和 src/cpu。这是实现跨平台开发的关键。IR 经过变换后，会根据目标硬件分发到不同的 Backend。在你的 MacBook Air 上，src/metal 会将 IR 翻译为 Metal Shading Language (MSL)，并利用 simdgroup_matrix 或 M5 cooperative-tensor 实现加速；而在 Colab T4 上，src/cuda 会将其翻译为 CUDA C++ 或 PTX。\n\n4. 运行时与工具层 (Runtime & Tools)：位于 tilelang/jit、tilelang/profiler 和 src/runtime。负责宿主机与设备端的数据交互、Kernel 启动（Host Launcher）以及性能分析。最近集成的 IKET profiler 和 Wall-clock benchmarking 工具，能帮助你在 T4 上进行最终的微秒级性能调优。

一次调用怎么流过这些模块

在你的硬件约束下（MacBook Air 开发，Colab T4 验证），一次典型的算子开发与执行数据流如下：\n\n1. 算子定义 (Mac 本地)：你使用 Python 在 examples/ 目录下创建一个新文件。通过 @T.prim_func 装饰器定义入口，使用 T.Kernel 划定 Grid/Block 结构。在 Kernel 内部，你使用 T.alloc_shared 声明共享内存，并调用 T.gemm 或 T.copy_cluster 编写核心计算逻辑。此时，代码完全是硬件无关的 DSL。\n\n2. 即时编译与 lowering (Mac 本地)：当你调用 tilelang.compile(program, target="metal") 时，数据流进入 tilelang/jit。Python AST 被解析并转换为底层的 TVM TIRX 表达式。\n\n3. 核心变换与布局推导 (Mac 本地)：TIRX 数据流进入 src/transform 和 src/layout。这是最关键的一步。编译器会调用 Z3 Solver 解析你定义的符号化形状（Dynamic Shapes），并自动推导 Shared Memory 的 Swizzle 布局以避免 Bank Conflict。近期提交显示，这里还会进行「原子操作向量化宽度规划 (Plan atomic vector widths)」。这一步完全在 CPU 上完成，如果你的逻辑有误，编译器会在此抛出 Source-aware diagnostics 错误。\n\n4. 代码生成 (Mac 本地)：通过验证的 TIRX 进入 src/metal。TileLang 会将其翻译为 Metal Shading Language (MSL)，并将 T.gemm 映射为 Apple Silicon 的 simdgroup_matrix 指令。随后调用 Mac 本地的 Metal 编译器生成动态链接库。\n\n5. 本地执行与验证 (Mac 本地)：你使用 PyTorch (CPU/MPS) 创建测试 Tensor，传入编译好的 Kernel。src/backend/common/codegen/codegen_c_host.cc 生成的 Host Launcher 会负责参数绑定和 Kernel 启动。你可以在 Mac 上验证算子的数值正确性（Correctness）。\n\n6. 云端编译与性能确认 (Colab T4)：将代码推送到 Colab，仅需将 target 改为 "cuda"。数据流在第 4 步会进入 src/cuda，生成 CUDA C++ 代码。由于 T4 是 Turing 架构 (SM75)，TileLang 会自动匹配 Native SM75 MMA GEMM 路径（支持 FP16/INT8/INT4 Tensor Core）。通过 NVRTC 编译后，结合 tilelang/profiler 的 Wall-clock benchmarking 和 NVTX 注入，你可以获取精确的 GPU 耗时，完成最终的性能确认。

扩展点

  • 新模型算子实现：在 examples/ 目录下新建文件夹（如 examples/deepseek_v4），使用 T.prim_func 编写逻辑，并添加 test_*.py 和 regression_*.py 接入 CI 测试。
  • 新后端 (Backend) 接入：在 src/backend/ 下新建目录（如 src/webgpu），实现继承自 TVM Codegen 的 C++ 访客类；在 tilelang/backend/ 注册该后端的 Python 分发逻辑。
  • 新 Kernel 原语 / 硬件指令：在 tilelang/tileop/ 中定义 Python 侧的语法糖（如 T.new_hw_op），然后在 src/op/ 中实现对应的 C++ Lowering 逻辑，将其映射为 TIRX 内置函数或 LLVM/PTX 内联汇编。
  • 新调度策略 / 编译器 Pass：在 src/transform/ 中编写新的 C++ Pass（如 PlanNewOptimization.cc），并在 tilelang/transform/ 中暴露给 Python 层，通过 PassConfigKey 控制其开关。

三、本地跑起来（没有 GPU 的 Mac）

安装

  1. git clone --recurse-submodules git@github.com:tile-ai/tilelang.git
  2. uv venv --seed .venv && source .venv/bin/activate
  3. uv pip install --requirements requirements-dev.txt
  4. python3 -m pip install --no-build-isolation --verbose --editable .
  5. 注意：由于在 Mac 上开发，请跳过 pyproject.toml 中 [project.optional-dependencies] 的 nvcc 组（如 nvidia-cuda-nvcc, nvidia-cuda-cccl 等），这些仅在云端 T4 验证时需要。

哪些路径能真跑

在你的 MacBook Air 上，你可以完整执行并验证以下路径：1. 前端与 IR 转换：tilelang/language, tilelang/transform, src/transform，你可以编写算子并观察 AST 到 TIRX 的 lowering 过程。2. 布局推导：maint/layout_inference 目录下的逻辑（依赖 z3-solver），这是纯 CPU 符号推导。3. Metal 后端：src/metal, tilelang/metal，以及 examples/matmul_metal 下的 Metal 专属算子，甚至可以利用 simdgroup_matrix 特性。4. CPU 后端：src/cpu, tilelang/cpu，通过 LLVM 执行。你只能读代码或用 Colab T4 验证的路径包括：src/cuda, src/rocm，以及 examples/deepseek_v32, examples/blockscaled_gemm_sm100 等强绑定 NVIDIA TMA/MMA/Tensor Core 硬件特性的前沿大模型算子。

  1. python examples/matmul_metal/benchmark_matmul_metal.py
  2. python examples/elementwise/example_elementwise_add.py

测试框架为 pytest。核心测试目录位于 testing/python（该目录是全库最热的 commit hotspot，高达 28 次提交）。在 Mac 上，你可以通过安装 requirements-test-metal.txt 的依赖，并运行 pytest testing/python 来执行测试。框架底层会基于 torch.cuda.is_available() 自动跳过 CUDA 强绑定的测试用例。纯 CPU/Metal 子集的测试大概在几分钟内即可完成。

调试

  • IR 调试：利用 2026年7月引入的 Pass Visualizer 和 IR Lower Trace 工具，可以可视化检查 AST 到 TIRX 的每一步 compiler pass 转换，这在无 GPU 环境下推导算子逻辑极其有用。
  • 环境变量：在运行测试或 benchmark 时，可设置 TILELANG_DISABLE_CACHE=1（见 cutedsl_launcher_overhead.py）来强制重新编译，避免缓存干扰。
  • 性能分析：使用 tilelang/profiler 和 IKET profiler（参考 examples/iket/minimal.py），结合最近提交的 wall-clock benchmarking 工具（commit db5584f2），在 Colab T4 上进行微秒级调优。

CI

CI 基于 GitHub Actions 运行 (.github/workflows)。你的 PR 主要会被代码格式化和 Lint 卡住：必须通过 pre-commit run --all-files，包括 Python 的 Ruff 检查和 C/C++ 的 clang-format（可通过 bash format.sh 自动修复）。此外，修改 C++ 源码时，maint/scripts/audit_cpp_api_style.py 会进行 API 命名和头文件边界审计（如 TLCPP001-004 规则），虽然是 advisory，但涉及 FFI 暴露的修改会被 Reviewer 严格把关。

坑

  • Mac 编译依赖坑：pyproject.toml 明确指出在 Darwin 系统上 JIT 编译 torch extension 强依赖 setuptools，确保你的虚拟环境中已安装，否则运行时会报错。
  • TVM FFI 初始化坑：项目依赖 torch-c-dlpack-ext 提供预编译的 torch 扩展，如果缺失，TVM FFI 会在首次 import 时触发意外的 JIT 编译，导致启动极慢或失败。
  • Metal 硬件特性回退：README 指出 Metal 4 cooperative-tensor 仅支持 Apple M5，在你的 MacBook Air 上运行时，底层会自动 fallback 到 simdgroup_matrix，在做端侧性能 profiling 时需注意这一硬件差异。
  • API 兼容性：v0.1.13 版本移除了大量 legacy APIs，在阅读早期 examples（如部分 deepseek_v32 代码）时，如果发现 API 找不到，请参考最新的 multi-backend language dialect 语法。
