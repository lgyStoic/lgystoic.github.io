一、项目定位

Tile Language（tile-lang）是由 Tile-AI 维护的 Pythonic DSL，目标是让高性能 GPU/CPU/NPU kernel 的开发更接近写 PyTorch，同时仍能做 tile 级别的底层优化。它构建在 Apache TVM 之上，自 TVM 的 TIR 之上发展出 TIRX IR 与一套独立的 pass 管道，并在 IR lowering 之后对接多种后端：CUDA（含 CuTe DSL、NVRTC、SM75/90/100/120 各代 tensor core / block-scaled MMA / TMA / cluster copy / warp specialization）、ROCm/HIP（CDNA4、RDNA3/RDNA4、WMMA）、Metal（simdgroup、cooperative tensor GEMM）、Ascend 950 NPU（PTODSL、SIMT/SIMD 向量编程）、LLVM CPU、以及实验性的 WebGPU。项目当前处于活跃演进期，从 2025 年的 CuTe DSL 后端、Metal 起步，到 2026 年已覆盖 Blackwell（SM100/SM120）FP8/MXFP8/INT4、Windows 包、并行 autotune、LSP、源码级诊断、pass 可视化、Ascend 官方后端等。README 与 pyproject 自称 Beta（Development Status :: 4 - Beta），但多个新后端（WebGPU、部分 Ascend 能力、eager-mode autotune）仍在快速迭代。仓库规模可观：tilelang/ 下约 414 个 Python 文件、src/ 下约 398 个 C++ 文件、testing/ 约 499 个测试文件、examples/ 约 387 个示例、benchmark/ 与 maint/ 若干工具脚本。近 30 天内 release 节奏约每月一版（v0.1.13→v0.1.14→v0.1.15），提交热点集中在 testing/python、jit、contrib、autotuner、CUDA/Ascend/ROCm 后端与 transform pass，说明项目正处在多后端扩展与稳定性并重的阶段。

解决什么问题、给谁用

解决的核心矛盾是：手写高性能 kernel（GEMM、dequant GEMM、FlashAttention、MoE、稀疏 MLA 等）需要精细控制 tile、shared memory、tensor core / MMA 指令、TMA、pipeline，而传统 CUDA/Triton/CuTe 的开发与调试成本仍然很高。TileLang 让开发者在 Python 中用 T.copy、T.gemm、T.mma_*、T.copy_cluster、T.tma_copy 等 tile 级原语描述计算，由编译器自动完成 layout 推断、software pipeline、warp specialization、host 代码生成，并在多后端间复用同一套 kernel 描述。目标用户是：需要为特定硬件（H100/B200/Mi300/Apple Silicon/Ascend）自研高性能算子的性能工程师、训练框架底层开发者、编译器/DSL 研究者，以及希望快速验证新硬件特性的工程师。典型场景包括：为 DeepSeek V3/V4 / MLA / NSA 写自定义 attention kernel；为 MoE 写 fused MoE + quant/dequant 路径；为 Blackwell 写 block-scaled GEMM / TMA / two-SM 核；在 Apple Silicon 上用 Metal 验证算法；在 CPU/LLVM 上做 kernel 正确性回归；用 autotuner 自动搜优 tile/ pipeline 参数。

1. GPU 性能工程师：用 TileLang 替代手写 CUDA 或 Triton，开发 GEMM、attention、MoE、sparse attention 等算子，尤其适合需要跨代硬件（SM75→SM120）统一代码库的团队。2. 训练框架底层开发者：为自研 LLM 训练框架集成高性能 attention / fused MoE / block-scaled GEMM，利用 TileLang 的 autotune 和 pass 调试工具快速迭代。3. 编译器/DSL 研究者：研究 tile-level DSL、IR lowering、layout inference、software pipeline，TileLang 提供相对完整的端到端基础设施（Python 前端 → TIRX → 多后端 CodeGen）。4. 端侧 / 多硬件开发者：在 Apple Silicon 上通过 Metal 后端验证 kernel，或在 Ascend NPU 上利用 PTODSL 后端做算子开发，避免为每个硬件维护一套独立代码。5. 库维护者与贡献者：通过 maint/ 下的 audit 脚本、docs/ 的 CONTRIBUTING.md、format.sh、pre-commit 等工具参与。

同类项目与差别

  • Triton（OpenAI）：Triton 是更成熟的 Python DSL，生态更广（PyTorch 集成、FlagGems 等），但主要面向 NVIDIA GPU，对 AMD / Ascend / Metal / CPU 支持有限；TileLang 的优势在于多后端（CUDA/ROCm/Metal/Ascend/CPU/WebGPU）统一描述、更贴近 TVM 的编译器基础设施（pass 可视化、layout 可视化、源码级诊断）、以及更激进的 Blackwell / TMA / block-scaled MMA 支持。
  • CUTLASS / CuTe DSL（NVIDIA）：CUTLASS/CuTe DSL 是 NVIDIA 官方 C++/Python DSL，性能上限与硬件贴合度最高，但仅限 NVIDIA GPU，且 C++ 开发成本高；TileLang 把 CuTe DSL 作为一个后端（3rdparty/cutlass），在之上提供更高层 Pythonic 接口，同时把同一 kernel 描述 lowering 到非 NVIDIA 后端。
  • TVM（Apache）：TVM 是通用深度学习编译器栈，调度语言较底层（TE / Meta Schedule / Relax）；TileLang 直接构建在 TVM 之上，复用其 TIRX、CodeGen、runtime，但提供了更面向 kernel 作者的 tile-level DSL 与更友好的调试工具（IR Lower Trace、Pass Visualizer、layout 可视化）。
  • Triton-distributed / oneMKL-SYCL 等：这些项目侧重分布式或特定厂商的 kernel 库；TileLang 定位是单 kernel / 单设备 DSL，分布式能力较弱（主要依赖 autotune 多 GPU benchmarking），但单 kernel 表达力与硬件覆盖更广。

二、架构与代码地图

TileLang 采用经典的编译器分层架构，自上而下分为五层。最上层是 接入层，以 tilelang.__init__.py 暴露的 tilelang.compile()、tilelang.jit 装饰器以及 tilelang.dsl / tilelang.language 中的 T.Kernel、T.Tensor、T.Pipelined、T.copy、T.gemm 等 Pythonic DSL 构成，用户在这一层写出看起来像 PyTorch 的 kernel 描述。DSL 原语会被捕获成 TIRX IR（TVM Script 风格的中间表示），缓存在 tilelang/cache 中，并由 tilelang/jit 负责即时编译与缓存命中。 往下一层是 调度层 / 编译器层，核心在 tilelang/transform、tilelang/analysis、tilelang/carver、tilelang/engine 以及 C++ 侧的 src/transform、src/ir.cc/.h。这里承担 pass 管道：layout inference、layout propagation、tensorization、TMA / MMA / warp-specialization 注入、Lower TIRX → TIR/LLVM IR、autotune 搜索、pass 计时与 IR dump。tilelang/autotuner 与 tilelang/contrib（含 contrib/triton、contrib/dsl）则提供高层调度策略与第三方 DSL 桥接。 再往下是 执行层 / 后端层，由 tilelang/backend 与 src/backend 暴露统一的 Backend 注册表，把编译产物分发给各硬件后端：CUDA（tilelang/cuda、src/cuda，含 NVRTC、CuTe DSL、SM75/90/100/120 tensor core、TMA、warp specialization）、ROCm/HIP（tilelang/rocm、src/rocm）、Metal（tilelang/metal、src/metal）、Ascend NPU（tilelang/ascend、src/ascend）、LLVM CPU（src/cpu）、WebGPU（src/webgpu）以及 src/tl_templates 里的模板 kernel。 最底层是 硬件抽象与运行时层，由 src/runtime、3rdparty/tvm、3rdparty/cutlass、3rdparty/hip-headers 提供 TVM runtime FFI、CuTe CUTLASS 模板、HIP 头文件与 CUDA stub。工具层（tilelang/profiler、tilelang/instrumentation、tilelang/tools、benchmark/、maint/）贯穿各层，负责 profiling、layout 可视化、autodd、IR trace / pass diff、正确性评估等开发者体验。

一次调用怎么流过这些模块

一次 TileLang kernel 请求从用户代码开始。用户在 Python 中用 T.Kernel、T.Tensor、T.Pipelined、T.copy、T.gemm 等 DSL 原语（tilelang/language）描述 kernel；这些原语被 TVM Script 解析器捕获成 TIRX IR（tilelang/ir.py + src/ir.cc/.h），缓存在 tilelang/cache。 当用户调用 tilelang.compile(fn) 或用 @tilelang.jit 装饰时，tilelang/jit 的 JITFunction 接管：先查缓存，未命中则进入 tilelang/engine 的 Engine 调度。Engine 把 TIRX 喂进 tilelang/transform 与 src/transform 的 pass 管道——依次做 layout inference、layout propagation、tensorization、TMA/MMA/warp-specialization 注入、Lower TIRX → TIR/LLVM IR。tilelang/autotuner 可在这一层搜索 pass configs 与 tile 尺寸（#2159 并行 autotune、#1906 eager-mode）。 Lower 后的 IR 进入 tilelang/backend + src/backend 的 BackendRegistry，按目标硬件分发给具体后端：CUDA（tilelang/cuda、src/cuda）走 NVRTC 或 CuTe DSL（3rdparty/cutlass），ROCm（tilelang/rocm、src/rocm）走 HIP，Metal（tilelang/metal、src/metal）走 Metal Shading Language，Ascend（tilelang/ascend、src/ascend）走 PTODSL，CPU（src/cpu）走 LLVM IR，WebGPU（src/webgpu）走 WGSL。后端 codegen 产出可执行二进制或源码。 tilelang/jit 把产物包装成 JITKernel 返回给用户；用户像调 PyTorch op 一样传入 tensor，由 src/runtime 的 runtime 在指定 stream 上 launch kernel。tilelang/profiler 的 Profiler 可包裹 JITKernel，提供计时与 assert_allclose 正确性验证（maint/gemm/correctness_evaluation.py 大量使用）。tilelang/instrumentation 的 IKET profiler 可插入 CUDA timeline 做细粒度分析。tilelang/tools 的 lower_trace、pass_diff、layout_visualization、autodd 则用于调试 IR 变化与定位性能瓶颈。 关键调度点：① tilelang/jit 的缓存与 Lower 触发；② tilelang/engine 的 pass 管道调度；③ tilelang/backend 的 BackendRegistry 分发；④ tilelang/autotuner 的 trial 调度；⑤ src/runtime 的 kernel launch。关键数据结构：TIRX IR（src/ir.cc/.h）、JITKernel（tilelang/jit）、Backend 注册表（tilelang/backend）、PassContext（tilelang/transform）、Profiler（tilelang/profiler）。

调试

  • 断点：Python 层可在 tilelang/jit/、tilelang/engine/、tilelang/transform/ 关键函数入 pdb.set_trace()；C++ 层需重新编译并用 lldb attach（scikit-build-core 产物在 build/ 目录）。
  • 日志开关：环境变量 TILELANG_LOG_LEVEL=DEBUG 或 TVM 相关日志（TVM_LOG_DEBUG）控制 IR lowering 输出；pass 计时通过 PassConfigKey 启用（README 2026-07-16 条目）。
  • IR dump：tilelang.PassConfigKey.TL_DUMP_IR 或类似配置（README 2026-03-05 条目 "IR dump configuration"）可在每次 pass 后打印/保存 IR。
  • Pass Diff 工具：docs/tools/pass_diff.md 提供编译器 pass 间 IR 对比，适合定位 lowering 回归。
  • Profiling 入口：tilelang.profiler 模块 + kernel.get_profiler(tensor_supply_type=...) 可获取编译后 profiler，支持 assert_allclose 与自动测时（需 GPU 才能真实测时）。
  • 源码位置：启用 source-aware diagnostics（README 2026-07-28）后，编译器报错会指向 Python 源码行号。

CI

GitHub Actions（.github/workflows/），多后端矩阵：CUDA（cu118/cu120/.../cu128）、ROCm、Metal、Ascend、CPU/LLVM；PR 会跑 lint（pre-commit: ruff + clang-format + pymarkdown）、单元测试、示例回归测试。无 GPU 贡献者提交会被 GPU 测试 skip，但 lint 与 CPU 测试必须通过；CodeRabbit 自动评审（最近提交 fd2ddda 启用）。具体 job 名与阈值需查看 .github/workflows/*.yml 确认。

坑

  • 1. 不要安装 [project.optional-dependencies] nvcc 组：pyproject.toml 中 nvidia-cuda-nvcc 等仅在 Windows 或需要 CUDA JIT 时适用，macOS 无 NVIDIA GPU 会触发 CMake FindCUDAToolkit 失败。
  • 2. 必须 git clone --recurse-submodules：3rdparty/tvm 是核心依赖，缺失会导致 C++ 编译失败。
  • 3. 首次 import tilelang 可能触发 JIT 编译 torch extension（torch-c-dlpack-ext），需 setuptools 且耗时数分钟（pyproject 注释说明）。
  • 4. CPU 后端覆盖有限：并非所有 tilelang.language 原语都支持 LLVM CPU lowering，复杂 kernel（FlashAttention、TMA、warp specialization）在 CPU 上会报错或 silent 回退。
  • 5. Metal 后端需 macOS 13+ 与 Metal API，且仅部分算子（GEMM、elementwise）有实现；cooperative-tensor GEMM 需 M5 或更新，M1/M2 MacBook Air 可能回退到 simdgroup 或失败。
  • 6. examples/ 中大量脚本默认 target='cuda'，直接运行会报 CUDA 错误，需手动改 target 或仅阅读代码。
  • 7. testing/ 中测试可能硬编码 GPU 设备检查（torch.cuda.is_available()），无 GPU 时自动 skip，但部分测试可能未正确标记导致 collect 失败，需用 -k 过滤。
  • 8. 可编辑安装（pip install -editable .）后修改 C++ 代码需重新运行 python3 -m pip install --no-build-isolation --verbose --editable . 重新编译，增量构建依赖 scikit-build-core + ccache（若配置）。
