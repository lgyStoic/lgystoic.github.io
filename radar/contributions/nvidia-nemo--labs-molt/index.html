NVIDIA-NeMo/labs-molt

该仓库是基于 PyTorch、Ray 和 vLLM 的 RL 框架，虽然核心训练依赖 GPU，但其纯逻辑层（如分布式调度、启动脚本）和 PyTorch 机制（如 Checkpointing）完全可以在 CPU/Mac 上进行开发和验证，非常适合拥有深厚分布式训练和 PyTorch 底层经验的候选人发挥专长。

当前方向：目前仓库正致力于支持更大规模的模型（如 DeepSeek-V4）的 RL 训练，解决极端规模下的显存优化（Activation Checkpointing）和多节点集群部署问题。

修复 SFT 训练中 Activation Checkpointing 的 Metadata Shape Mismatch

Issue #90 · [bug] Quickstart Qwen3.6 SFT crash with metadata shape mismatch ↗

无人认领3 条评论bug更新 2026-09-10

用到的专长：深入理解 PyTorch autograd 与 activation checkpointing 机制。

目标：定位并修复 SFT 训练开启 gradient checkpointing 时，forward 和 recompute 阶段 tensor shape 不一致（如 1296 变 1297）的 bug。

为什么值得长期做：解决大模型训练中常见的 activation checkpointing 状态不一致问题，展现对 PyTorch 底层机制的深刻理解，是建立核心贡献者信任的绝佳切入点。

怎么介入：Issue 处于 open 状态，虽有 linked PR #91 但已 closed，无 assignee，适合介入。
第一个 PR 的边界：包含一个复现该 bug 的 CPU 单测，以及修复 recompute 状态不一致的代码修改。
第一步：构造一个极简的 CPU 单元测试，使用 dummy 模型和变长输入，开启 checkpointing 并触发 backward，复现 shape mismatch 报错。
认领留言（英文，可直接贴到 Issue）
Hi, I'd like to look into this checkpointing metadata mismatch. I plan to first write a minimal CPU-based unit test with a dummy model to reliably reproduce the `1296 vs 1297` shape divergence during recomputation, then fix the underlying state/padding inconsistency. Could you share why PR #91 was closed so I can avoid the same pitfalls? I can have a PR ready in a few days.
大致实施方案
  • 编写单测：在 `tests/` 下新建测试，模拟 `sft_trainer.py` 的 `_run_microbatch`，传入带 padding 的 dummy 数据。
  • 调查根本原因：排查模型 forward 中是否有依赖全局状态、随机数或未固定 padding 长度的操作，导致 recompute 时 sequence length 发生 +1 的偏移。
  • 修复逻辑：在 `molt/trainer/sft_trainer.py` 或相关模型代码中，确保 recompute 时的输入和上下文与 forward 完全一致（例如显式传递 attention mask 或 sequence lengths）。
  • 验证：确保 CPU 单测通过，且不影响正常的不带 checkpointing 的训练逻辑。
可能涉及的目录或文件
  • molt/trainer/sft_trainer.py
  • molt/trainer/fsdp/strategy.py
验收方式
  • 在 Mac 上运行编写的 CPU 单测，确保 `loss.backward()` 成功执行且不抛出 `CheckpointError`。

  • 是否可以提供一个更小规模的复现配置（比如 1B 模型）以便在 Colab T4 上做最终的端到端验证？

风险

提供 DeepSeek-V4 RL 的多节点 SLURM 与 Ray 启动脚本

Issue #10 · [feature] Roadmap for DeepSeek-V4 RL training support (DSA/MLA kernels, mixed precision, GPU footprint, and the agentic environment path) ↗

无人认领2 条评论更新 2026-07-31

用到的专长：丰富的分布式训练集群（SLURM/Ray）工程部署经验。

目标：为 DeepSeek-V4 RL 训练提供标准的 SLURM sbatch 脚本和裸机多节点 Ray 启动脚本，解决网络接口检测、端口冲突和环境变量传播等常见问题。

为什么值得长期做：完善分布式训练的基建和文档，帮助社区用户跨越集群部署的门槛，是展现分布式工程经验的高价值贡献。

怎么介入：Issue 为 Roadmap，无 assignee，正文中明确列出了该子任务，适合认领。
第一个 PR 的边界：新增多节点启动脚本及配套的使用文档，不涉及核心训练代码的修改。
第一步：在 `examples/scripts/` 目录下创建 `slurm_ray_cluster.sh` 和 `baremetal_ray_cluster.sh` 草稿。
认领留言（英文，可直接贴到 Issue）
Hi, I'd like to tackle the 'Multi-node launch scripts' item from this roadmap. I can contribute a robust SLURM sbatch script and a bare-metal Ray bring-up script that handle network interface detection, staggered startup, and env propagation. I'll test the logic locally using mock nodes. Does the team have a preference on how network interfaces (e.g., InfiniBand vs Ethernet) should be specified in these scripts? I can submit a PR this weekend.
大致实施方案
  • 编写 SLURM 脚本：解析 `$SLURM_NODELIST`，启动 Ray head 节点，并使用 `srun` 启动 worker 节点，处理好 `RAY_ADDRESS` 和端口分配。
  • 编写裸机脚本：提供基于 SSH 的多节点 Ray 启动逻辑，包含注册等待门控（registration gate）。
  • 环境变量处理：确保 `PYTHONPATH`、`CUDA_HOME` 等关键环境变量正确传播到所有非 head 节点。
  • 文档更新：在 README 或 `docs/` 中添加多节点启动的使用说明。
可能涉及的目录或文件
  • examples/scripts/
  • README.md
验收方式
  • 在 Mac 上使用本地多个终端或 Docker 容器模拟多节点环境，验证 Ray 集群能否成功组建且环境变量正确传递。
