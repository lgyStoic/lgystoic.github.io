RightNow-AI/autokernel

AutoKernel 是一个基于 AI 代理的 GPU kernel 自动优化框架，核心涉及 Triton、CUDA C++ 编写以及 PyTorch 算子融合。这与候选人在底层 kernel 优化、算子融合、扩散模型加速及量化部署方面的资深经验完美契合。项目处于快速发展期，非常需要具备深厚 GPU 架构和数值计算背景的工程师来扩展其算子库和硬件兼容性。

当前方向：目前仓库的重点在于完善核心算子库（如支持扩散模型所需的复杂融合算子）、提升新一代硬件（如 Hopper 架构）的兼容性，并探索对量化模型的支持，以拓宽其在推理加速领域的应用。

怎么介入这个项目

  • 沟通渠道：项目有活跃的 Discord 社区，建议加入并在其中进行日常交流。
  • PR 规范：对于引入新算子或量化等较大特性，务必先在 Issue 中与维护者对齐设计方案（如内置 vs 插件化）。
  • 测试要求：所有 kernel 的修改或新增，必须在本地通过 `uv run bench.py` 的 5 阶段正确性测试（Smoke, Shape Sweep, Numerical Stability 等）。
  • 依赖管理：项目使用 `uv` 管理依赖，开发前需运行 `uv sync` 确保环境一致性。

目标：修复 `bench.py` 在 H200 上运行 fp32 matmul 时精度测试失败的问题。

为什么值得长期做：解决新一代硬件（Hopper）上的精度兼容性问题，展示你对 GPU 架构底层细节（如 TF32）的深刻理解。

怎么介入：Issue 开放且无 assignee，无 linked PR，适合介入。
第一个 PR 的边界：在 `bench.py` 中处理 TF32 设置或调整容差。
第一步：租用一台 H100/H200 或 4090，运行 `bench.py` 复现问题，检查是否是 TF32 默认开启导致的精度损失。
认领留言（英文，可直接贴到 Issue）
Hi! This looks like it might be caused by TF32 being enabled by default on Hopper/Ada architectures, which reduces fp32 precision. I can investigate this on an H100/4090. Would you prefer to explicitly disable TF32 during the benchmark for strict fp32 comparison, or should we relax the tolerances for these architectures? I can open a PR once we decide on the approach.
大致实施方案
  • 在 Hopper/Ada 架构 GPU 上运行 `uv run bench.py` 复现 fp32 失败。
  • 在 `bench.py` 的初始化部分尝试设置 `torch.backends.cuda.matmul.allow_tf32 = False`。
  • 如果禁用 TF32 后测试通过，说明是 TF32 导致。
  • 修改 `bench.py`，根据硬件架构动态调整 fp32 的容差，或者在 benchmark 期间显式禁用 TF32 以保证严格的 fp32 测试。
