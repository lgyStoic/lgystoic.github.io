一、项目定位

autokernel 是一个受 Karpathy autoresearch 启发的 GPU kernel 自动化优化框架。它的核心理念是将 AI Agent 引入到底层算子优化中，通过“修改代码-运行基准测试-保留或回退”的无限循环，系统性地探索 Triton 和 CUDA C++ kernel 的优化空间。与目前业界常见的依赖 LLM 一次性生成（one-shot generation）算子代码的工具不同，autokernel 强调通过 50-300+ 次的迭代实验来逼近硬件性能极限，并内置了严格的 5 阶段正确性校验（涵盖形状扫描、数值稳定性、边缘情况等），确保生成的 kernel 既快又对。 项目目前处于活跃开发阶段，已经具备了从 PyTorch 模型输入到最终优化算子导出的完整端到端 Pipeline（包含 profile.py、extract.py、bench.py 和 verify.py）。它原生支持 9 种深度学习核心算子（如 Flash Attention、Fused MLP、RMSNorm 等），并提供 Triton 和 CUDA C++ 双后端。近期开发重点集中在 CUDA 后端的完善以及与 HuggingFace Kernels 的生态打通。 对于只有 MacBook Air 的候选人：该项目的核心价值在于其 Agent 编排逻辑（orchestrate.py、program.md）和评估反馈机制（bench.py）。由于强依赖 NVIDIA GPU 进行真实的 Profiling 和性能测试，若要在 Apple Silicon 上切入，建议优先关注如何解耦 Agent 决策层与硬件执行层。你可以通过 Mock bench.py 的返回结果（如伪造 results.tsv 的吞吐量和延迟数据），在纯 CPU 环境下调试和优化 Agent 的探索策略（如基于 Amdahl 定律的调度逻辑），或者为项目补充针对 CPU/MPS 后端的实验性支持，最后再利用 Colab T4 进行真实环境的端到端验证。

解决什么问题、给谁用

深度学习模型中长尾算子或核心算子的性能瓶颈难以快速突破。人工手写和调优 Triton/CUDA kernel 耗时极长且需要极高的硬件架构知识门槛；而现有的 LLM 代码生成往往无法一次性写出最优且完全正确的底层算子，缺乏系统性的验证与迭代机制。

AI 基础设施工程师、模型性能优化工程师、需要极致推理/训练性能的 AI 研究员。典型场景：用户提供一个 PyTorch 模型（如 LLaMA 7B），运行 profile.py 找出耗时瓶颈，随后启动 Agent 通宵运行。Agent 会根据 program.md 的指令迭代优化，第二天用户即可获得验证过正确性且性能提升的 Triton/CUDA kernel，并可通过 export_hf.py 导出分享。

同类项目与差别

  • karpathy/autoresearch：本项目的直接灵感来源。autoresearch 专注于 LLM 训练研究的自动化探索，而本项目将相同的“迭代-评估”哲学应用到了更底层的 GPU kernel 优化领域。
  • ScalingIntelligence/KernelBench：GPU kernel 生成的评估基准。本项目深度集成了它（kernelbench/ 目录），但区别在于 KernelBench 论文主要评估 LLM 的一次性生成能力，而本项目利用其数据集进行 50-300+ 次的迭代优化实验。
  • OpenAI Triton：本项目依赖的底层编译器和目标语言之一。Triton 提供了编写高效 kernel 的基础设施，而本项目解决了“如何利用 AI 自动写出最优 Triton 代码”的问题。

二、架构与代码地图

AutoKernel 的架构设计围绕“AI Agent 驱动的底层算子优化”展开，整体可划分为五个核心层。入口与模型层（models/、profile.py）负责接收用户提供的 PyTorch 模型，通过 torch.profiler 运行真实的前向/后向传播，捕获 GPU 耗时并定位长尾或核心算子瓶颈。调度与 Agent 层（orchestrate.py、program.md）是整个系统的大脑，orchestrate.py 基于 Amdahl 定律计算全局加速收益，决定当前应该优化哪个 kernel；而 program.md 则是详尽的 Prompt，指导 LLM Agent 执行“修改代码-运行基准测试-保留或回退”的无限循环。评估与验证层（bench.py、verify.py）是确保生成的 kernel“既快又对”的守门员。bench.py 包含严格的 5 阶段正确性校验（Smoke、Shape Sweep、数值稳定性、确定性、边缘情况）和基于 CUDA Event 的性能测速；verify.py 则负责将优化后的 kernel 重新注入模型进行端到端验证。Kernel 执行层（kernels/、kernels/cuda/）提供了 Triton 和 CUDA C++ 的初始模板，其中 CUDA 后端通过 kernels/cuda/_compile.py 封装 torch.utils.cpp_extension.load_inline 实现源码级的动态编译与 Hash 缓存。工具与生态层（export_hf.py、kernelbench/）负责将最终产物导出至 HuggingFace Kernels 生态，并与 KernelBench 评测集打通。 对于只有 MacBook Air 的候选人：由于执行层和评估层强依赖 NVIDIA GPU（如 cuda_runtime.h、torch.cuda.Event），在 Apple Silicon 上直接运行会报错。你的最佳切入点是解耦调度层与评估层。你可以修改 bench.py，在检测不到 CUDA 时，拦截真实的编译与测速逻辑，转而读取预先录制的假数据（Mock results.tsv），从而在纯 CPU 环境下跑通 Agent 的调度数据流，专注于优化 orchestrate.py 中的调度算法或 program.md 中的探索策略。此外，你也可以尝试在 kernels/ 下引入实验性的 MPS 后端支持。

一次调用怎么流过这些模块

AutoKernel 的核心数据流是一个高度自动化的“分析-提取-迭代-验证” Pipeline。首先，用户通过命令行触发 profile.py（例如 uv run profile.py --model models/llama_7b.py）。该脚本加载 PyTorch 模型，使用 torch.profiler 运行预热和真实推理，收集底层算子的 GPU 耗时。通过匹配 _KERNEL_CLASSIFICATION 中的规则，将这些算子归类（如 matmul、flash_attention），并输出包含耗时占比和硬件规格（GPUSpec）的 profile_report.json。 接着，extract.py 读取该报告，将 Top-N 耗时的算子对应的模板文件从 kernels/ 或 kernels/cuda/ 复制到 workspace/kernel.py。此时，Agent 介入，读取 program.md 中的指令，开始对 kernel.py 进行修改。 每次 Agent 修改代码后，都会触发 bench.py。对于 CUDA 后端，bench.py 会调用 kernels/cuda/_compile.py 中的 compile_cuda，该函数计算源码的 Hash 值（_hash_source），若无缓存则调用 load_inline 动态编译并生成 C++ 扩展。随后，bench.py 执行严格的 5 阶段校验（与 reference.py 中的 PyTorch 原生实现对比）。若校验通过，则使用 CUDA Event 测量吞吐量和延迟，并将结果追加到 results.tsv 中。Agent 读取 TSV 结果，决定保留优化或回退代码。 在宏观层面，orchestrate.py 监控 results.tsv，利用 Amdahl 定律评估当前 kernel 的全局收益，决定何时停止当前循环并切换到下一个 kernel。所有 kernel 优化完成后，verify.py 将它们重新注入原模型进行端到端验证，最终可通过 export_hf.py 导出。 Mac 用户的调试路径：在 Apple Silicon 上，bench.py 的动态编译和 CUDA Event 测速会直接崩溃。你可以修改 bench.py 的入口，使其在检测到非 CUDA 环境时，直接解析 Agent 修改的源码特征（或简单返回一个随机波动的 TFLOPS 值）并写入 results.tsv，从而在纯 CPU 下跑通整个 Agent 调度和决策数据流。

扩展点

  • 新模型接入：在 models/ 目录下新增 Python 文件（参考 models/custom.py），实现标准的 PyTorch nn.Module。然后通过 uv run profile.py --model models/new_model.py --class-name YourModelClass 即可接入 Profiling 流程。
  • 新 Kernel 类型支持：1. 在 kernels/ 和 kernels/cuda/ 下新增对应的模板文件（如 conv2d.py）。2. 在 profile.py 的 _KERNEL_CLASSIFICATION 列表中添加对应的正则匹配规则。3. 在 reference.py 中添加对应的 PyTorch 原生实现，供 bench.py 进行正确性校验。
  • 新后端支持（如 Apple MPS，适合 Mac 候选人）：1. 在 kernels/ 下创建 mps/ 目录并提供基于 MPS Graph 或纯 PyTorch 的模板。2. 修改 export_hf.py 中的 detect_backend 以识别 mps。3. 修改 bench.py，在硬件检测和计时逻辑中增加对 torch.backends.mps.is_available() 的支持，使用 mps.Event 替代 cuda.Event。
  • 新 Agent 调度策略：修改 orchestrate.py。目前的调度基于 Amdahl 定律的贪心策略，你可以引入强化学习模型，或者基于历史 results.tsv 数据的贝叶斯优化算法，来决定下一个优化的 kernel 或指导 Agent 的探索方向。

三、本地跑起来（没有 GPU 的 Mac）

安装

  1. git clone https://github.com/RightNow-AI/autokernel.git
  2. cd autokernel
  3. # 必须修改 pyproject.toml 移除 CUDA 和 Triton 强依赖，否则在 Mac 上 uv sync 会报错
  4. sed -i '' '/triton>=3.3.0/d' pyproject.toml
  5. sed -i '' '/\[tool.uv.sources\]/,+7d' pyproject.toml
  6. uv sync --extra models

哪些路径能真跑

在 Apple Silicon 上真正能执行的路径包括：profile.py（内置了 _fallback_detect_gpu 处理无 GPU 情况，可运行模型前向/后向耗时分析）、extract.py（基于 profile 结果提取 kernel 模板）、export_hf.py（基于正则和 AST 的纯文本处理，提取 CUDA_SRC）、orchestrate.py（Agent 调度逻辑，需 Mock 评估层）以及 analysis.py。只能读代码或用 Colab T4 验证的路径包括：bench.py（强依赖 CUDA Event 和 5 阶段校验）、verify.py（端到端验证）、kernels/cuda/_compile.py（依赖 nvcc 和 torch.utils.cpp_extension）以及 kernelbench/bench_kb.py。

最小可运行

  1. uv run prepare.py
  2. # 注意：将 README 示例中的 float16 改为 float32，以避免 Mac CPU 上的半精度运算报错
  3. uv run profile.py --model models/llama_7b.py --class-name LlamaModel --input-shape 1,512 --dtype float32
  4. uv run extract.py --top 5
  5. uv run export_hf.py --name my_matmul

测试

项目没有使用传统的 pytest 或 unittest，也没有 tests/ 目录。核心的测试逻辑内置在 bench.py（包含 Smoke、Shape Sweep、数值稳定性、确定性、边缘情况 5 阶段正确性校验）和 kernelbench/bench_kb.py 中。README 指出每次完整的 bench.py 实验耗时约 90 秒。由于强依赖 CUDA，无法直接在 Mac 上运行测试子集；若要调试，必须在 bench.py 中拦截 torch.cuda.is_available()，并 Mock 返回预造的 results.tsv 数据，从而跑通 Agent 的调度数据流。

调试

  • Profiling 入口：profile.py 内部封装了 torch.profiler，是整个系统定位长尾算子的入口，可在此处打断点分析模型解析逻辑。
  • 日志开关：profile.py 引入了 logging 模块，可通过修改日志级别查看模型解析与算子分类（_KERNEL_CLASSIFICATION）的细节。
  • 编译缓存清理：CUDA 编译缓存位于 ~/.cache/autokernel/cuda_build（见 kernels/cuda/_compile.py），在 Colab 调试编译错误时，需手动清理此目录强制重编。
