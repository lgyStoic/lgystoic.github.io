一、项目定位

AutoKernel 是一个基于大模型 Agent 的 GPU 算子自动化搜索与优化框架。其核心理念直接受 @karpathy/autoresearch 启发，将“修改代码-运行基准测试-保留或回滚”的无限循环应用于底层算子优化。给定一个 PyTorch 模型，框架会自动 Profile 找出耗时瓶颈，将其提取为独立的 Triton 或 CUDA C++ 算子，然后交由 LLM Agent（如 Claude/Codex）根据 program.md 中的指令进行彻夜的迭代优化，最终验证端到端加速比。项目目前处于功能完备且快速横向扩展的阶段（版本 1.0.0，Changelog 提及 1.3.0），近期提交热点高度集中在 kernels/cuda（13次提交）和 export_hf.py，说明其在完善 Triton 链路后，正大力推进原生 CUDA C++ 后端以及与 HuggingFace 生态的融合。 对你的关键提示：作为一个资深 Kernel 工程师，这个库的架构对你来说会非常清晰。但硬约束警告：该项目强依赖 NVIDIA GPU 环境（triton>=3.3.0，pytorch-cu128，以及 bench.py 中的硬件测速）。在你的 MacBook Air 上，你无法运行核心的 Profiling 和 Benchmarking 闭环。你的切入路径只能是：1) 在 Mac 上纯静态阅读源码，梳理 Agent 编排逻辑（orchestrate.py）和评测指标（bench.py）；2) 优化 Agent 的 Prompt 知识库（program.md 和 kernelbench/program_kb.md），注入你深厚的 CUDA/Triton 优化经验（如 memory coalescing, swizzling, wmma 技巧）；3) 将修改推送到分支，利用 Colab T4 进行几十分钟的端到端验证。

解决什么问题、给谁用

解决深度学习模型中长尾算子或特定瓶颈算子手工优化成本极高的问题。通过 AI Agent 自动化完成“瓶颈定位 -> 算子提取 -> 代码编写 -> 正确性与 Roofline 性能验证 -> 端到端集成”的完整闭环，替代人工手写和调优 Triton/CUDA 算子的繁琐过程。

AI 基础设施工程师、算子优化工程师、模型部署专家，以及希望一键加速自定义 PyTorch 模型的 AI 研究员。

同类项目与差别

  • karpathy/autoresearch：AutoKernel 的直接灵感来源。区别在于 autoresearch 针对 LLM 训练研究（算法层），而 AutoKernel 专注于 GPU Kernel 优化（系统底层），并针对算子特性设计了严格的 5 阶段正确性校验和 Roofline 性能测试。
  • ScalingIntelligence/KernelBench：AutoKernel 在 kernelbench/ 目录下深度集成了该项目。区别在于 KernelBench 论文主要评估 LLM 的 One-shot（单次）算子生成能力，而 AutoKernel 引入了迭代式优化引擎，对每个问题进行 50-300+ 次的实验探索。
  • PyTorch Inductor / OpenAI Triton Auto-tuner：传统的编译器自动调优通常基于预设模板进行参数搜索（如 block size）。AutoKernel 则是让 LLM Agent 直接修改人类可读的源码（Triton/CUDA C++），探索空间更广，甚至能进行算法层面的算子融合重写。

二、架构与代码地图

AutoKernel 的架构设计高度模块化，其核心思想是将“人类性能工程师的日常工作”抽象为一条自动化的流水线。整体架构可划分为五个层次： 1. 模型接入与剖析层 (Model Ingestion & Profiling)：由 profile.py、extract.py 和 models/ 目录组成。这一层负责加载任意 PyTorch 模型，利用 torch.profiler 运行前向与反向传播，收集 GPU 耗时数据，定位长尾或瓶颈算子，并将其提取为独立的可编译文件。这是整个自动化流程的起点。 2. Agent 编排与调度层 (Agent Orchestration)：由 orchestrate.py、program.md 和 kernelbench/program_kb.md 构成。这是 AutoKernel 的“大脑”。orchestrate.py 实现了基于 Amdahl 定律的全局调度器，动态决定下一个应该优化的算子以最大化端到端收益。program.md 则是注入给 LLM Agent 的“知识库”与“操作手册”，包含了 6 级优化策略和严格的决策框架。对于没有本地 GPU 的你来说，这里是发挥你深厚 CUDA 经验的最佳切入点。 3. 评测与验证层 (Benchmarking & Verification)：由 bench.py、verify.py 和 reference.py 组成。bench.py 是 Agent 彻夜工作的“沙盒”，提供严苛的 5 阶段正确性检查（smoke, shape sweep, numerical stability, determinism, edge cases）和 Roofline 性能评估。verify.py 则负责将优化后的算子插回原模型，验证端到端加速比。 4. 算子实现与编译层 (Kernel Implementation & Compilation)：集中在 kernels/ 目录下。包含 Triton 和原生 CUDA C++（kernels/cuda/）的初始实现。特别地，kernels/cuda/_compile.py 实现了一个基于 Hash 缓存的轻量级 JIT 编译器，利用 torch.utils.cpp_extension.load_inline 在几秒内完成 CUDA 源码的编译与绑定。 5. 生态集成层 (Ecosystem Integration)：由 export_hf.py 和 kernelbench/ 组成。负责将优化产物打包导出至 HuggingFace Kernels 格式，以及与 KernelBench 评测基准对接，实现标准化评估。

一次调用怎么流过这些模块

AutoKernel 的核心数据流是一个由 AI Agent 驱动的“剖析-提取-优化-验证”无限闭环。整个流程如下： 1. 瓶颈定位 (Profiling)：用户通过命令行启动 profile.py，指定目标模型（如 models/llama_7b.py）。脚本会执行模型的前向与反向传播，利用 torch.profiler 收集底层的 GPU Kernel 耗时。随后，脚本根据 _KERNEL_CLASSIFICATION 规则（如匹配 gemm, flash 等关键字）对算子进行分类，并生成包含耗时排名和内存带宽分析的 workspace/profile_report.json。 2. 算子提取 (Extraction)：extract.py 读取上述报告，找出 Top-N 的瓶颈算子。它会从 kernels/（Triton）或 kernels/cuda/（CUDA C++）目录中拷贝对应的基线实现，在 workspace/ 下生成独立的 kernel.py 文件，准备交由 Agent 处理。 3. Agent 迭代优化 (The Core Loop)： - Agent（如 Claude/Codex）读取 program.md 中的指令，分析当前的 kernel.py。 - Agent 运用其知识（或你注入的 CUDA 经验）修改 kernel.py，例如调整 Block Size、引入 wmma 张量核加速、优化 Shared Memory 布局以消除 Bank Conflict。 - 修改完成后，触发 bench.py。如果后端是 CUDA，bench.py 会调用 kernels/cuda/_compile.py，利用 _hash_source 计算源码哈希，若无缓存则调用 torch.utils.cpp_extension.load_inline 进行 JIT 编译。 - 编译通过后，bench.py 将编译出的算子与 reference.py 中的 PyTorch 原生实现进行 5 阶段正确性比对。只有正确性完全通过，才会测量 TFLOPS 或 GB/s，并将结果写入 results.tsv。 - Agent 读取 results.tsv，如果性能提升则保留（Keep），否则回滚（Revert），继续下一次迭代。 4. 全局调度与端到端验证：在多算子场景下，orchestrate.py 会监控所有算子的收益，利用 Amdahl 定律动态切换 Agent 的优化目标。优化结束后，verify.py 将所有优化后的算子重新组装回原模型，验证端到端精度和总加速比。最终，用户可通过 export_hf.py 将产物导出至 HuggingFace Hub。

扩展点

  • 新模型接入：在 models/ 目录下新建 Python 文件定义 PyTorch 模型（参考 models/custom.py），或直接使用 profile.py --module transformers --class-name ... 接入 HuggingFace 模型。
  • 新算子 (Kernel) 支持：1. 在 kernels/ 和 kernels/cuda/ 下分别添加 Triton 和 CUDA 的基线实现（需包含 kernel_fn）。2. 在 reference.py 中添加对应的 PyTorch 参考实现。3. 在 profile.py 的 _KERNEL_CLASSIFICATION 中注册名称匹配规则。
  • 新后端支持 (如 ROCm/HIP)：在 kernels/ 下新建后端目录（如 kernels/hip/），实现类似 _compile.py 的 JIT 编译逻辑。同时在 export_hf.py 的 detect_backend 中添加新后端的识别规则。
  • 新优化策略与 Agent 知识：直接修改 program.md（标准模式）或 kernelbench/program_kb.md（KernelBench 模式）。由于你没有本地 GPU，这是你发挥专长的最佳位置：将你关于 memory coalescing, warp shuffle, wmma 的经验写成 Prompt 规则注入其中。

三、本地跑起来（没有 GPU 的 Mac）

安装

  1. git clone https://github.com/RightNow-AI/autokernel.git
  2. cd autokernel
  3. sed -i '' '/triton>=3.3.0/d' pyproject.toml
  4. sed -i '' '/pytorch-cu128/d' pyproject.toml
  5. uv sync --extra models --extra kernelbench

哪些路径能真跑

在 Mac (Apple Silicon) 上，你只能运行纯文本处理与调度逻辑，包括：export_hf.py（正则解析与打包 HuggingFace 格式）、kernelbench/bridge.py（从 HuggingFace 下载题目）、orchestrate.py（纯 Python 的 Amdahl 定律调度逻辑）。 绝对无法运行：bench.py（强依赖 Triton/CUDA JIT）、kernels/cuda/_compile.py（依赖 nvcc）、profile.py（源码 _fallback_detect_gpu 强依赖 torch.cuda，在 Mac 上会 fallback 且无法收集真实 GPU 耗时）。核心验证必须将修改推送到分支，在 Colab T4 上进行。

最小可运行

  1. uv run prepare.py
  2. uv run kernelbench/bridge.py fetch --source hf --level 1
  3. uv run export_hf.py --name my_matmul --kernel kernels/cuda/matmul.py

测试

项目没有传统的 pytest 测试套件，也没有 tests/ 目录。测试即基准评测，全部由 bench.py 和 kernelbench/bench_kb.py 承担（包含 smoke, shape sweep, numerical stability, determinism, edge cases 5 个阶段）。 CPU 子集：无。所有测试强依赖 GPU。在 Colab T4 上，单次 bench.py 实验耗时约 90 秒。

调试

  • CUDA 编译缓存清理：JIT 编译产物缓存在 ~/.cache/autokernel/cuda_build（见 kernels/cuda/_compile.py），修改编译 flag 时需手动 rm -rf 该目录以强制重编。
  • Agent 提示词调试：核心 Prompt 位于 program.md 和 kernelbench/program_kb.md，修改后可通过观察 Agent 生成的 kernel.py 差异来验证 Prompt 效果。
  • 日志开关：profile.py 使用了标准 logging 模块，可通过修改源码中的 logging level 开启 debug 输出。

CI

当前仓库目录树中未发现 .github/workflows/，说明暂无开源的自动化 CI 流程。PR 的合并主要依赖于本地运行 bench.py 后的 results.tsv 报告，以及 correctness must ALWAYS pass 的硬性要求。

坑

  • 依赖冲突坑：pyproject.toml 中硬编码了 pytorch-cu128 和 triton>=3.3.0，在 Mac 上直接 uv sync 会报错，必须手动剔除这两个依赖。

缺口依据为什么是你
Agent 提示词知识库（program.md）缺乏高阶 CUDA 优化策略（如 CuTe/CUTLASS 模式、Shared Memory Swizzling、TMA 等）。README 提到 program.md 包含 6 级优化策略，但当前仓库的 kernels/cuda/ 初始实现（如 matmul.py）仍在使用基础的 wmma 和双缓冲，未见更现代的 Hopper/Ada 架构级优化指导。作为资深 Kernel 工程师，你脑中有大量现成的 Roofline 突破技巧，可以直接将其转化为自然语言或伪代码注入 program.md，大幅提升 Agent 生成代码的上限。这完全不需要本地 GPU 即可完成。
缺乏针对扩散模型（DiT/视频生成）和端侧量化（W4A16）的算子模板。README 和 profile.py 的 _KERNEL_CLASSIFICATION 显示，目前仅支持 9 种基础算子（matmul, softmax, flash_attention, fused_mlp 等），缺乏 AdaLN、Shifted Window Attention 或 Quantized GEMM。你擅长扩散模型推理加速和量化部署，可以轻松编写这些算子的基础 Triton/CUDA 模板（放入 kernels/），填补项目在 AIGC 前沿模型上的支持空白。
macOS/CPU 环境下无法进行核心逻辑的 Dry-run 测试。profile.py 中的 _fallback_detect_gpu 强依赖 torch.cuda.is_available()，且 bench.py 强依赖真实 GPU 测速，导致无 GPU 开发者连调度逻辑都无法本地调试。你可以为 profile.py 和 orchestrate.py 引入 --mock-gpu 或 Dry-run 模式，通过伪造 Profiling 数据（如返回预设的耗时字典），让 Mac 开发者也能参与调度器和 Agent 编排逻辑的开发。
HuggingFace 导出脚本（export_hf.py）的正则解析在面对复杂 C++ 宏或嵌套结构时可能较为脆弱。export_hf.py 中的 extract_cuda_source 依赖简单的正则匹配（如 CUDA_SRC = r"""..."""）来提取 CUDA 源码，一旦 Agent 生成了非标准格式的字符串拼接，导出就会失败。这是纯 Python 的字符串/AST 处理工作，在 Mac 上即可完美开发和测试。你可以利用 Python ast 模块重写提取逻辑，使其更加健壮。
CUDA JIT 编译缓存（kernels/cuda/_compile.py）缺乏跨平台/离线语法检查能力。_compile.py 中的 _get_arch_flags 直接调用 torch.cuda.get_device_capability()，在 Mac 上会直接失效或报错，无法仅做 nvcc 语法校验。你可以修改编译逻辑，允许在无 GPU 但有 nvcc 的环境（或通过特定 flag）只生成 PTX 进行语法检查，这能极大加速你在 Colab 上的调试效率。
调度器（orchestrate.py）的 Amdahl 定律实现可能未充分考虑 Memory-bound 与 Compute-bound 的差异。README 提到 profile.py 会对算子进行 compute/memory-bound 分类，但调度逻辑仅基于“全局收益最大化”。作为性能优化专家，你深知对于 Memory-bound 算子，优化的天花板是显存带宽。你可以优化调度算法，使其结合 Roofline 模型预判优化潜力，避免 Agent 在已达带宽极限的算子上浪费时间。

认领留言（英文，可直接贴到 Issue）
Hi, I specialize in performance modeling and roofline analysis. Instead of adding heavy dependencies like HTA right away, I could add a lightweight trace parser in profile.py to extract temporal breakdown (compute vs memory bound, GPU idle time) from the existing PyTorch profiler dump. This would enrich the context given to the Agent. Let me know if you'd welcome a PR for this!
大致实施方案
  • 在 profile.py 中，当 profiler 导出 trace JSON 后，添加一个可选的分析步骤。
  • 解析 trace 文件，计算 GPU 闲置时间、内存带宽受限时间 vs 计算受限时间。
  • 将这些高级指标追加到 profile_report.json 中，供 Agent 在 program.md 中使用。
  • 在 Mac 上使用预先生成的 trace JSON 文件进行纯 Python 逻辑开发和测试。
可能涉及的目录或文件
  • profile.py
验收方式
  • 在 Mac 上提供一个 dummy 的 PyTorch trace JSON，运行分析逻辑，检查输出的报告是否包含正确的 breakdown 指标。
开工前问题与风险

向维护者确认

  • 是否希望引入 hta 作为可选依赖，还是倾向于用纯 Python 解析 trace JSON 以保持轻量？

风险

  • trace JSON 文件可能非常大，解析时需要注意内存占用。
