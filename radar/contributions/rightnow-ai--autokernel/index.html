一、项目定位

AutoKernel 是一个受 Karpathy autoresearch 启发的 GPU 算子自动化研究与优化框架。它的核心思想是将大模型（如 Claude/Codex）作为 Agent，通过「修改代码 -> 运行基准测试 -> 保留或回滚」的无限循环，全自动地为 PyTorch 模型优化 Triton 或 CUDA C++ 算子。对于你这位资深 Kernel 工程师来说，这个项目本质上是一个「算子优化流水线编排工具」加「Agent Prompt 最佳实践库」。它不仅支持 Triton，还原生支持 CUDA C++（通过 Ninja 编译，支持 wmma 和 PTX 内联汇编），并内置了 5 阶段的严格正确性校验（Smoke、Shape 扫描、数值稳定性、确定性、边界条件），防止 Agent 产生「快但错误」的垃圾代码。项目目前处于活跃迭代期（近期合并了生产级 Bugfix 和 AMD ROCm 支持）。 针对你的硬件约束（仅 Mac M1 + 免费 Colab T4）的切入建议： 由于你本地没有 NVIDIA GPU，你无法在本地完整运行 bench.py 或 profile.py。但该项目的架构是高度解耦的。你的高价值切入路径是： 1. 纯 CPU/Mac 侧：研究并改进 orchestrate.py（基于阿姆达尔定律的多算子调度逻辑）和 program.md（Agent 的 6 级优化剧本）。你可以 Mock bench.py 的返回结果（results.tsv），在 Mac 上无缝调试 Agent 的决策树和代码生成逻辑。 2. Colab T4 侧：利用每天有限的 T4 算力，运行 uv run bench.py 验证你改进的 CUDA/Triton 模板（位于 kernels/ 和 kernels/cuda/），或测试 export_hf.py 的 HuggingFace 导出链路。

解决什么问题、给谁用

解决的具体问题：1. 手写和调优 GPU Kernel（尤其是 CUDA C++ 和 Triton）耗时且门槛高，难以快速覆盖模型的所有瓶颈算子；2. 现有的 LLM 一次性生成（One-shot generation）算子代码往往无法通过严格的正确性测试，且性能难以达到极致；3. 缺乏一个将「模型 Profile -> 算子提取 -> 迭代优化 -> 端到端验证」串联起来的自动化闭环。 目标用户：1. AI 基础设施工程师和算子优化专家（如你），用于自动化生成 Baseline 代码或探索极端优化空间；2. 模型研究员，希望在不深入底层硬件细节的情况下加速自定义 PyTorch 模型；3. AI Agent 研究者，用于测试大模型在复杂代码工程中的长上下文推理和试错能力。

典型使用场景： 1. 夜间自动化调优：下班前输入一个自定义的扩散模型或 LLM，运行 orchestrate.py，第二天早上收获一组经过数百次迭代优化的 Triton/CUDA 算子。 2. 算子标准化评测：集成 KernelBench，对 250+ 个标准 GPU 算子问题进行批量评分（kernelbench/scorer.py），评估不同 LLM 的算子编写能力。 3. 开源算子分发：将优化好的算子通过 export_hf.py 一键导出并发布到 HuggingFace Kernels Hub，供社区复用。

同类项目与差别

  • karpathy/autoresearch：AutoKernel 的灵感来源。autoresearch 侧重于 LLM 训练研究的自动化，而 AutoKernel 将相同的「编辑-评估-保留/回滚」循环专门应用于 GPU 算子（Triton/CUDA）的性能优化。
  • ScalingIntelligence/KernelBench：AutoKernel 深度集成了 KernelBench（斯坦福的算子评测集），但核心区别在于：KernelBench 论文主要评估 LLM 的「一次性生成」能力，而 AutoKernel 引入了 50-300+ 次的「迭代优化（Iterative refinement）」机制来系统性探索优化空间。
  • OpenAI/Triton：Triton 是底层的算子编程语言和编译器。AutoKernel 是上层的自动化生成与调优框架，它不仅生成 Triton 代码，还支持生成 Native CUDA C++ 代码，并负责端到端的正确性验证。

二、架构与代码地图

AutoKernel 的架构设计高度解耦，将「模型分析」、「多算子调度」、「Agent 迭代」与「底层编译评测」完全分离。这种设计对你（仅有 Mac M1 + Colab T4）非常友好：你可以在 Mac 上完成前三层的开发与调试，仅将最底层的编译评测放到 Colab 上验证。 1. 入口与分析层 (Profiling Layer)：由 profile.py 和 extract.py 组成。负责接收任意 PyTorch 模型，利用 torch.profiler 追踪执行图，识别出耗时占比最高的瓶颈算子，并将其映射到内置的算子模板库中。 2. 调度与编排层 (Orchestration Layer)：核心是 orchestrate.py。它扮演「AI 研发总监」的角色，基于阿姆达尔定律（Amdahl's Law）计算每个算子的理论最大全局收益，动态决定 Agent 当前应该优先优化哪个算子。（Mac 侧切入点：你可以在本地 Mock 评测结果，专注于改进这里的多算子调度算法） 3. Agent 交互层 (Agent Layer)：由 program.md（剧本）和 kernel.py（沙盒）组成。program.md 包含了极其详尽的 6 级优化策略（从基础 Tiling 到 PTX 内联汇编），指导 LLM Agent 如何一步步修改 kernel.py。 4. 编译与评测层 (Execution & Benchmarking Layer)：由 bench.py 和 kernels/cuda/_compile.py 构成。负责对 Agent 生成的代码进行 JIT 编译，并执行严苛的 5 阶段正确性校验（Smoke、Shape 扫描、数值稳定性、确定性、边界条件）和性能测试。（Colab 侧切入点：在这里验证你手写的 CUDA/Triton 模板） 5. 生态接入层 (Ecosystem Layer)：包括 export_hf.py 和 kernelbench/ 目录。负责将优化好的算子打包导出到 HuggingFace Kernels，或接入 KernelBench 进行标准化 LLM 算子生成能力评测。

一次调用怎么流过这些模块

AutoKernel 的核心数据流是一个「Profile -> Extract -> Orchestrate -> Agent Edit -> Bench -> Verify」的无限闭环。对于没有本地 GPU 的开发者，理解这个数据流有助于你在 Mac 上进行断点 Mock。 1. 模型分析 (Profiling)：流程始于 profile.py。用户输入一个 PyTorch 模型（如 models/llama_7b.py），脚本使用 torch.profiler 运行少量 Warmup 和 Profile 迭代。它会捕获底层算子调用，利用 _KERNEL_CLASSIFICATION 规则（如匹配 flash 或 fmha 归类为 flash_attention），计算各算子的 GPU 耗时占比，最终在 workspace/ 生成 profile_report.json。 2. 算子提取 (Extraction)：extract.py 读取该 JSON 报告，找出耗时 Top-N 的算子。它会从 kernels/ 或 kernels/cuda/ 目录中拷贝对应的 Baseline 模板（如 matmul.py），准备好独立的优化环境。 3. 调度与分发 (Orchestration)：orchestrate.py 启动。它读取 Profiling 数据，利用阿姆达尔定律计算每个算子如果加速 N 倍能带来的全局收益。它选择当前 ROI 最高的算子，将其代码复制到 kernel.py（Agent 的沙盒文件）。（在 Mac 上，你可以手动伪造 profile_report.json 来测试调度逻辑） 4. Agent 迭代 (Agent Loop)：LLM Agent（如 Claude）读取 program.md 中的优化剧本，分析 kernel.py 的当前瓶颈，修改代码（例如调整 Triton 的 BLOCK_SIZE 或 CUDA 的 wmma 布局）。 5. 编译与评测 (Benchmarking)：Agent 修改完成后触发 bench.py。如果代码包含 BACKEND = "cuda"，bench.py 会调用 kernels/cuda/_compile.py。该模块会提取 CUDA_SRC，计算源码 Hash，若无缓存则调用 torch.utils.cpp_extension.load_inline 进行 JIT 编译。编译成功后，bench.py 注入随机张量，执行 5 阶段正确性校验。若校验通过，则测量 TFLOPS/带宽，并将结果（包含 speedup_vs_pytorch 和 correctness）追加到 results.tsv。（在 Mac 上，你可以写一个假的 bench.py 直接向 results.tsv 写入 Mock 数据，欺骗 Agent 继续迭代） 6. 决策与回滚 (Decision)：Agent 读取 results.tsv，若性能提升则保留代码，否则回滚。循环继续。 7. 端到端验证 (Verification)：优化结束后，verify.py 将所有优化好的算子重新 Patch 回原模型，运行真实推理，验证最终输出的数值误差并报告端到端加速比。

扩展点

  • 新模型接入：在 models/ 目录下新建 Python 文件定义 PyTorch 模型，或直接使用 profile.py --module transformers --class-name ... 接入 HuggingFace 模型。
  • 新算子类型支持：1. 在 kernels/ 和 kernels/cuda/ 下添加对应的 .py 模板文件；2. 在 profile.py 的 _KERNEL_CLASSIFICATION 列表中添加该算子的名称匹配规则；3. 在 reference.py 中添加对应的 PyTorch 参考实现。
  • 新后端支持 (如 ROCm/HIP)：在 kernels/ 下新建 hip/ 目录存放模板，修改 export_hf.py 中的 detect_backend 逻辑以识别新后端，并在 bench.py 中添加对应的 JIT 编译支持。
  • 新调度策略：修改 orchestrate.py。当前的调度基于阿姆达尔定律，你可以引入强化学习或基于历史成功率的启发式调度算法。

三、本地跑起来（没有 GPU 的 Mac）

安装

  1. curl -LsSf https://astral.sh/uv/install.sh | sh
  2. git clone https://github.com/RightNow-AI/autokernel.git && cd autokernel
  3. sed -i '' '/triton>=/d' pyproject.toml
  4. sed -i '' '/pytorch-cu128/d' pyproject.toml
  5. uv sync --extra models

哪些路径能真跑

在 Mac (Apple Silicon) 上真正可执行的路径：profile.py（模型分析与算子提取，需将 dtype 改为 float32）、extract.py（生成 Baseline 代码）、orchestrate.py（多算子调度逻辑，可 Mock results.tsv 调试）、export_hf.py（HuggingFace 格式导出）、analysis.py（结果可视化）。 只能读代码或在 Colab T4 验证的路径：bench.py（5 阶段正确性校验与性能测试，强依赖 CUDA）、verify.py（端到端验证）、kernels/cuda/_compile.py（依赖 nvcc 和 ninja，包含特定架构的 gencode）、kernelbench/bench_kb.py（KernelBench 评测）。

最小可运行

  1. uv run prepare.py
  2. uv run profile.py --model models/llama_7b.py --class-name LlamaModel --input-shape 1,512 --dtype float32
  3. uv run extract.py --top 3
  4. uv run export_hf.py --name test_export --kernel kernels/matmul.py

测试

仓库目前没有标准的 tests/ 目录或 pytest 配置。核心的测试逻辑内置在 bench.py（5 阶段正确性校验：Smoke、Shape 扫描、数值稳定性、确定性、边界条件）和 verify.py 中。在 Mac 上，你无法运行这些测试。建议在本地开发调度逻辑（orchestrate.py）时，手动构造一个假的 workspace/results.tsv 来模拟测试通过/失败，从而验证 Agent 的行为。

CI

仓库根目录没有 .github/workflows/，目前似乎没有配置自动化的 CI 流水线（需验证）。PR 的合并主要依赖于人工 Review。对于 Kernel 相关的 PR，Reviewer 会重点关注 bench.py 的 5 阶段正确性校验是否通过，以及在目标硬件（如 H100/A100）上的实际 TFLOPS/带宽收益。

坑

  • Mac 依赖冲突：pyproject.toml 强依赖 triton 和 pytorch-cu128，在 Mac 上直接 uv sync 会报错，必须手动剔除相关依赖和 index。
  • FP16 限制：Mac CPU 对 float16 的支持有限，运行 profile.py 时务必使用 --dtype float32，否则可能在 torch.profiler 阶段崩溃。
  • CUDA 编译缓存：kernels/cuda/_compile.py 会在 ~/.cache/autokernel/cuda_build 下生成基于源码 Hash 的缓存。在 Colab 调试时，如果修改了编译参数但没改 CUDA 源码，可能命中缓存导致不生效，需手动清理该目录。
  • Agent 幻觉：program.md 中包含极其详尽的指令，但 Agent 偶尔可能会尝试修改 bench.py 绕过测试，需确保沙盒环境仅允许修改 kernel.py。

旧架构 (如 T4/Turing) 的兼容性盲区kernels/cuda/_compile.py 会自动检测架构，但现有的 CUDA 模板可能隐式依赖 Ampere+ 的特性（如硬件 BF16 或异步拷贝），在 T4 上可能编译失败或性能异常。你唯一的验证环境是 Colab T4 (sm_75)，这迫使你必须完善模板的向后兼容性（如使用 #if __CUDA_ARCH__ 宏），提升项目的鲁棒性。

基础模板对边界条件 (Edge Cases) 的泛化性不足bench.py 包含 Shape 扫描测试，但 kernels/cuda/flash_attention.py 等模板在处理非 2 的幂次序列长度或奇数维度时，可能存在越界风险。资深工程师对边界条件极其敏感。你可以重构这些基础模板，增加健壮的边界检查和 Padding 逻辑，降低 Agent 迭代时的 Crash 率。
