任务 1高 · 低 · 低算力（仅需能运行 Triton 编译的普通 GPU）

module 'triton.language.math' has no attribute 'tanh'

Issue #19 · module 'triton.language.math' has no attribute 'tanh' ↗

目标：修复 `kernels/fused_mlp.py` 中因 Triton API 变更导致的 `tl.math.tanh` 属性错误，使算子能够成功编译。

为什么值得长期做：修复基础算子的编译错误是保障系统可用性的底线。解决此问题能帮助候选人快速熟悉 Triton API 的版本差异以及 AutoKernel 的算子代码结构，是建立代码库直觉的绝佳切入点。

第一步：定位 `kernels/fused_mlp.py` 中的 `tanh` 调用，查阅当前版本 Triton 文档寻找替代 API（如 `tl.extra.cuda.libdevice.tanh` 或通过数学公式重写）。
大致实施方案
  • 在 `kernels/fused_mlp.py` 中找到使用 `tl.math.tanh` 的代码行。
  • 查阅 Triton 官方文档或源码，确认 `tanh` 在目标 Triton 版本中的正确调用路径。
  • 修改代码，将 `tl.math.tanh` 替换为正确的 API 调用。
  • 使用 Issue 中提供的最小复现脚本在本地进行编译测试，确保不再抛出 `AttributeError`。
可能涉及的目录或文件
  • kernels/fused_mlp.py
验收方式
  • 运行 Issue 描述中的 `repro_tanh.py` 脚本，确认 `triton.compile` 成功执行且无报错。
  • 运行 `uv run bench.py`（如果支持指定 kernel，则指定 `fused_mlp`），确保正确性测试通过。
开工前问题与风险

向维护者确认

  • 项目目前主要针对哪个版本的 Triton 进行测试和兼容？
  • 除了 `fused_mlp.py`，是否还有其他 kernel 文件可能使用了已被废弃的 `tl.math` API 需要一并排查？

风险

  • 不同版本的 Triton 对数学库的组织方式差异较大，可能需要条件导入或锁定 Triton 版本。
任务 2中 · 中 · 低算力（正确性验证无需高性能 GPU）

[Feature] Support modulated norm and gated-residual fusion for diffusion/video transformer models

Issue #14 · [Feature] Support modulated norm and gated-residual fusion for diffusion/video transformer models ↗

目标：为 DiT 模型中常见的 modulated LayerNorm/RMSNorm 和 gated-residual 模式添加内置 Kernel 支持及 PyTorch 参考实现。

为什么值得长期做：DiT 是当前生成式 AI 的核心架构。引入 modulated norm 和 gated-residual 融合算子，能大幅扩展 AutoKernel 的适用范围，使候选人成为多模态/视频生成模型优化方向的负责人。

第一步：在 Issue 中回复维护者，确认是优先添加内置 Kernel 类型（如 `modulated_norm`）还是开发通用的自定义 Kernel 插件接口。
大致实施方案
  • 根据沟通结果，在 `kernels/` 和 `kernels/cuda/` 目录下创建 `modulated_norm.py` 和 `gated_residual.py` 的初始模板。
  • 在 `reference.py` 中添加对应的 PyTorch 参考实现，确保支持 fp16/bf16 输入和 fp32 累加，以及不同的 broadcast 布局（如 `[B, 1, D]`）。
  • 更新 `bench.py` 中的测试用例生成逻辑，加入针对新算子的 shape sweep 和 edge cases。
  • 在本地低算力 GPU 上运行 Benchmark，验证 Triton 初始实现的正确性。
可能涉及的目录或文件
  • kernels/
  • kernels/cuda/
  • reference.py
  • bench.py
验收方式
  • 执行 `uv run bench.py`，观察新增的 `modulated_norm` 和 `gated_residual` 算子在 Stage 1 (Smoke Test) 和 Stage 2 (Shape Sweep) 中是否全部 PASS。
开工前问题与风险

向维护者确认

  • 对于 DiT 算子，您更倾向于将其作为内置的 Kernel 类型（类似现有的 `layernorm`），还是希望借此机会引入 Issue 中提到的通用自定义 Kernel 扩展接口？
  • 是否有推荐的开源 DiT 模型（如 DiT-XL）可以作为 `models/` 目录下的新增示例模型？

风险

  • DiT 算子的 broadcast 布局较为复杂，在编写 Triton kernel 时处理不同维度的 stride 容易出错，需要仔细设计测试用例。
任务 3中 · 高 · 低算力（前期 Profiling 和架构设计无需高性能 GPU）

quants support

Issue #4 · quants support ↗

目标：扩展 `profile.py` 和 `verify.py`，使其能够加载、Profile 并识别量化模型（如 bitsandbytes）的特定 Kernel。

为什么值得长期做：量化是端侧部署和推理加速的核心。主导量化支持的架构设计与实现，将使候选人深度掌握项目的 Profiling 与验证闭环，成为推理优化方向的核心维护者。

第一步：在 Issue 中提出分阶段的实施计划（先支持加载与 Profiling，再支持 Kernel 优化），并请求维护者对 `profile.py` 中 Kernel 分类逻辑的修改方向给予反馈。
大致实施方案
  • 在 `pyproject.toml` 中添加 `bitsandbytes` 作为可选依赖（如 `[project.optional-dependencies] quants = [...]`）。
  • 修改 `profile.py`，增加 CLI 参数（如 `--quantization`），并在加载 HuggingFace 模型时传入相应的 `BitsAndBytesConfig`。
  • 运行 Profiler 收集量化模型的 Trace，分析量化特有 Kernel（如 dequantize 融合算子）的命名特征。
  • 扩展 `profile.py` 中的 Kernel 分类器，使其能正确识别并归类量化 Kernel，避免回退到未分类状态。
可能涉及的目录或文件
  • pyproject.toml
  • profile.py
  • verify.py
验收方式
  • 使用 `uv run profile.py --module transformers --pretrained <model> --quantization bnb4` 对一个小模型进行 Profiling，检查输出的 Kernel 排名列表中是否正确识别了量化相关的算子。
开工前问题与风险

向维护者确认

  • 考虑到量化 Kernel（如 W4A16）与现有的密集型 fp16 Kernel 差异巨大，是否应该在 `kernels/` 下建立一个专门的 `quant/` 子目录来存放 Starter Kernels？
  • 对于第一阶段的 PR，仅实现量化模型的加载和 Profiling 分类是否可以接受？

风险

  • 量化模型的 PyTorch Profiler 输出可能包含大量底层特定的 CUDA Kernel 名称，编写健壮的分类正则表达式具有挑战性。
任务 4低 · 中 · 无 GPU（纯 CPU 分析 Trace 文件即可）

Feature Request: better profiler to identify bottleneck in performance

Issue #1 · Feature Request: better profiler to identify bottleneck in performance ↗

目标：调研并集成高级 Profiling 工具（如 HTA 或 tlparse），丰富 `profile.py` 输出的诊断信息，为 Agent 提供更深度的优化上下文。

为什么值得长期做：AI Infra 的核心在于可观测性。引入高级 Profiling 工具能极大提升 Agent 优化的上限，使候选人深入参与到项目的核心 Agent 决策逻辑（`program.md`）的设计中。

第一步：在 Issue 中回复，提供一个轻量级的集成方案（例如将 HTA 作为可选依赖，仅在检测到安装时生成增强报告），询问维护者是否接受。
大致实施方案
  • 调研 Holistic Trace Analysis (HTA) 的 API，编写一个独立的脚本，测试其解析 PyTorch Profiler dump 文件的能力。
  • 在 `profile.py` 中增加逻辑：在现有的 `torch.profiler` 运行结束后，将 Trace 保存到临时文件。
  • 如果启用了高级分析，调用 HTA API 分析 Trace，提取内存瓶颈或算子调度瓶颈信息。
  • 将提取的高级诊断信息格式化，追加到 `profile.py` 输出的 JSON 或文本报告中，供 Agent 读取。
可能涉及的目录或文件
  • profile.py
  • pyproject.toml
验收方式
  • 运行 `uv run profile.py` 并附加新增加的增强分析 Flag，检查终端输出或生成的报告文件中是否包含了 HTA 提供的额外瓶颈诊断信息。
开工前问题与风险

向维护者确认

  • 为了保持 AutoKernel 的轻量级，是否应该将 HTA 等工具放在 `[project.optional-dependencies]` 中？
  • Agent 目前主要通过读取哪些输出来感知瓶颈？增强的诊断信息应该以何种格式（如 Markdown 摘要）呈现给 Agent 最有效？

风险

  • 引入外部 Profiling 库可能带来复杂的依赖冲突，且解析大型 Trace 文件可能显著增加 Profiling 阶段的耗时。
