hao-ai-lab/FastVideo

该仓库是一个统一的视频生成推理与后训练框架，涉及大量前沿模型（Wan, MiniMax-H3, LTX）和底层优化（Sparse Attention, FP8/FP4 量化）。候选人作为资深 GPU kernel 与性能工程师，非常契合该项目的技术栈。虽然目前没有真机 GPU，但可以通过纯逻辑层的内存管理、构建系统适配、端侧（Mac MPS）修复以及性能建模（MFU）等方向切入，发挥在 PyTorch 底层机制和架构设计上的专长。

当前方向：目前项目正大力推进 FastH3（MiniMax-H3 的稀疏蒸馏版本）的推理加速、多模态条件生成（Dreamverse）、以及端侧（Apple Silicon MLX）和新硬件（DGX Spark GB10）的适配。同时，量化（NVFP4/MXFP8）和性能基建（Dashboard, MFU）也是近期的核心发力点。

目标：消除 `VideoGenerator` 在主进程加载模型后向 `MultiProcExecutor` 子进程 handoff 时的内存双重占用，使 1.3B 模型能在 16GB RAM 环境下成功运行。

为什么值得长期做：内存管理是推理框架的核心，优化多进程 handoff 的内存峰值能极大提升框架在平民硬件（如免费 Colab）上的可用性，是走向核心维护者的绝佳切入点。

怎么介入：Issue 无 assignee 且无 linked PR，可直接认领。
第一个 PR 的边界：仅修改 `VideoGenerator` 和 `MultiProcExecutor` 的初始化与模型加载顺序，不涉及模型结构修改。
第一步：定位 `fastvideo/worker/multiproc_executor.py` 中 worker 进程 spawn 时的内存继承与传递逻辑。

为什么值得长期做：量化与 LoRA 的结合是当前高效推理的前沿。掌握框架的量化生命周期管理能让你深入理解模型权重在内存中的流转，为后续的 Kernel 优化打下基础。

为什么值得长期做：性能建模与监控是训练框架的核心竞争力。引入标准的 MFU 计算能帮助所有开发者评估硬件利用率，是极具价值的架构级贡献。

怎么介入：作者在 Issue 中明确表示 'Happy to design/implement trainer-level MFU logging if maintainers agree on the approach.'，但目前无人认领该 Structural gap。可以作为 RFC 子任务提案。

第一步：查阅 `fastvideo/tests/training/Vanilla/mfu_calculation.py` 中现有的 MFU 计算逻辑。

大致实施方案
