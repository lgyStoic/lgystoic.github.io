[Bug] MPS generation fails when multiprocessing worker returns output tensors

Issue #1846 · [Bug] MPS generation fails when multiprocessing worker returns output tensors ↗

目标：在跨进程传递结果前，将 MPS 张量（包括嵌套在字典中的张量）显式转换为 CPU 张量，以避免 `_share_filename_` 报错，同时保持原有的 CUDA IPC 路径不受影响。

为什么值得长期做：多进程通信是 FastVideo 异步推理架构的核心。修复 MPS 张量序列化问题不仅能打通 Apple Silicon 上的端到端生成，还能让你深入理解框架的 Worker 调度与内存共享机制，为后续参与端侧部署优化打下基础。

第一步：在 `fastvideo/worker/multiproc_executor.py` 中定位 `worker_busy_loop` 的结果发送逻辑，并编写一个递归函数将字典中的 MPS 张量转移到 CPU。
大致实施方案
  • 调查 `fastvideo/worker/multiproc_executor.py` 中的 `worker_busy_loop` 方法，找到 `self.pipe.send` 调用的位置。
  • 编写一个辅助函数（如 `normalize_tensors_to_cpu`），递归遍历输出字典，检查张量设备，如果是 `mps` 则调用 `.cpu()`。
  • 在调用 `self.pipe.send` 前，对 `output_batch` 应用该辅助函数。
  • 确保该修改不会影响 CUDA 张量（保留原有的 CUDA IPC 共享策略）。
  • 运行 Issue 中提供的 Minimal transport reproduction 脚本，确认修改后不再抛出 `RuntimeError`。
可能涉及的目录或文件
  • fastvideo/worker/multiproc_executor.py
验收方式
  • 运行 Issue 提供的纯 Python 多进程测试脚本，确认 MPS 张量能成功通过 `ForkingPickler` 序列化并反序列化为 CPU 张量。
  • 在 Mac 上运行一个极简的 T2I 任务，确认生成结果能成功返回给主进程。
开工前问题与风险

向维护者确认

  • 对于嵌套在复杂数据结构（如 dataclass 或自定义对象）中的张量，是否也需要支持递归转换？
  • 是否需要为其他非 CUDA 设备（如 ROCm、NPU）做类似的 CPU fallback 处理？

风险

  • 如果输出字典结构非常深或包含不支持递归遍历的自定义对象，可能会遗漏部分张量的转换。
  • 将张量拷贝到 CPU 会带来微小的延迟，需确保这不会成为性能瓶颈。

Quickstart example OOMs on 16GB-RAM free-tier environments (Kaggle, Colab)

Issue #1755 · Quickstart example OOMs on 16GB-RAM free-tier environments (Kaggle, Colab) ↗

目标：优化 `VideoGenerator` 的初始化流程，确保在派生 Worker 进程前，主进程释放不必要的模型内存，避免在 16GB 内存环境中发生 OOM。

为什么值得长期做：内存优化对于在受限环境（如 Colab、Kaggle）中推广 FastVideo 至关重要。解决主进程与 Worker 进程交接时的内存翻倍问题，能让你熟悉框架的模型加载与多进程生命周期管理。

第一步：分析 `VideoGenerator.from_pretrained` 和 `MultiProcExecutor` 的启动时序，找出主进程在 fork/spawn 时持有的模型引用。
大致实施方案
  • 调查 `fastvideo` 中 `VideoGenerator` 的初始化代码，特别是模型加载和 `MultiProcExecutor` 启动的顺序。
  • 确认在启动 Worker 子进程时，主进程是否仍然在内存中保留了完整的模型权重（如 Text Encoder）。
  • 修改逻辑：如果使用 spawn 模式，确保主进程在将模型传递给 Worker 后，及时删除自身对权重的引用并调用 `gc.collect()`。
  • 或者，研究是否可以通过按需加载（如在 Worker 进程内部加载权重）来避免主进程加载模型。
  • 在 16GB 内存的机器或限制了内存的 Docker 容器中运行 Quickstart 脚本进行测试。
可能涉及的目录或文件
  • 需先定位 `VideoGenerator` 初始化逻辑
  • fastvideo/worker/multiproc_executor.py
验收方式
  • 在一个限制为 16GB 内存的 Docker 容器中运行 README 中的 Quickstart 示例，监控内存峰值，确保不再触发 OOM 且能成功生成。
开工前问题与风险

向维护者确认

  • 框架目前是否强制要求在主进程中预加载模型？是否可以重构为仅在 Worker 进程中加载？
  • 对于多 GPU 场景，修改加载逻辑是否会影响现有的分布式初始化？

风险

  • 改变模型加载时序可能会引发死锁或导致某些依赖主进程权重的逻辑失效。
  • Python 的垃圾回收可能不够及时，需要显式管理内存释放。

[Bug] VBench SceneMetric loads Qwen2.5-Omni on CPU on any non-CUDA accelerator (device_map hardcodes cuda)

Issue #1815 · [Bug] VBench SceneMetric loads Qwen2.5-Omni on CPU on any non-CUDA accelerator (device_map hardcodes cuda) ↗

目标：将 VBench SceneMetric 中硬编码的 `cuda` 替换为动态获取的当前加速器设备，确保在非 CUDA 硬件上模型能正确加载到加速器。

为什么值得长期做：消除硬编码是实现多硬件兼容（NPU, MPS, ROCm）的基础。这个简单的修复能让你快速熟悉 FastVideo 的评估模块，并建立跨平台开发的意识。

第一步：全局搜索 `device_map="cuda"` 或类似硬编码，特别是在 VBench SceneMetric 相关的代码中，将其替换为动态设备获取逻辑。
大致实施方案
  • 在代码库中搜索 `Qwen2.5-Omni` 加载逻辑或 `device_map` 的硬编码，定位到 SceneMetric 相关文件。
  • 引入 `torch.accelerator.current_accelerator()` 或 FastVideo 提供的设备获取工具函数（如 `get_local_torch_device()`）。
  • 修改 `device_map` 的赋值逻辑：如果当前设备不是 CPU，则将其设置为实际的加速器设备名称（如 `mps`, `npu`, `cuda`）。
  • 检查同一文件中是否有其他类似的硬编码设备字符串，一并修复。
  • 提交前在纯 CPU 或 Mac 环境下运行相关初始化代码，打印 `device_map` 确认其值正确。
可能涉及的目录或文件
  • 需先定位 VBench SceneMetric 相关代码
验收方式
  • 在非 CUDA 环境（如 Mac MPS 或纯 CPU）下，编写一个简短的 Python 脚本导入并初始化该 Metric，断言模型被加载到了正确的设备（如 `mps` 或 `cpu`）而不是强行寻找 `cuda`。
开工前问题与风险

向维护者确认

第一步：在 `fastvideo/pipelines/basic/hunyuan15/hunyuan15_i2v_pipeline.py` 中添加缺失的图像编码器模块，并修复 Stage 的初始化。

[ci] [Bug] Spit out the log from worker process

Issue #1604 · [ci] [Bug] Spit out the log from worker process ↗

目标：在性能 CI 发生硬回归（如超时或性能下降）导致失败时，确保 Worker 进程的详细日志能够被捕获并打印到标准输出。

为什么值得长期做：CI 的可观测性是保障代码质量的关键。完善多进程 Worker 的日志输出，能极大降低其他开发者的调试成本，是参与 AI Infra 维护的绝佳切入点。

第一步：定位 CI 运行脚本和多进程 Worker 的日志配置，确保子进程的 stdout/stderr 被正确重定向或收集。
大致实施方案
  • 调查 FastVideo 的 CI 脚本（可能在 `.github/` 或 `.buildkite/` 下）以及性能测试脚本（如 `fastvideo/tests/`）。
  • 检查 `MultiProcExecutor` 或相关 Worker 启动代码，查看子进程的日志级别和输出流配置。
  • 如果子进程的异常或日志被吞噬，修改代码捕获 `WorkerMultiprocProc` 的异常，并在主进程退出前打印子进程的日志缓冲区。
  • 确保在触发硬回归阈值（如 `dit_time_s exceeded fixed threshold`）时，不仅抛出断言错误，还能附带 Worker 的上下文日志。
  • 在本地人为调低一个性能阈值触发失败，验证日志是否完整输出。
可能涉及的目录或文件
  • fastvideo/worker/multiproc_executor.py
  • 需先定位 CI 测试脚本
验收方式
  • 在本地运行性能测试脚本，人为修改阈值（如将 `threshold` 设为 0.001）触发硬回归，观察终端输出，确认 Worker 进程的日志被清晰打印。
开工前问题与风险

向维护者确认

  • Worker 的日志目前是写入文件还是直接打到 stdout？是否需要引入统一的日志收集机制？
