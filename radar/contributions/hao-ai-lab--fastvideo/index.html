一、项目定位

FastVideo 是一个专注于视频生成模型（DiT）加速的端到端统一推理与后训练框架。它的核心价值在于将前沿的视频生成大模型（如 Wan2.1/2.2、MiniMax-H3）通过稀疏注意力（VSA）、分布匹配蒸馏（DMD2）和量化（Attn-QAT）等技术，压缩并加速到可以在消费级硬件甚至 Apple Silicon 上实时运行。与 Diffusers 等通用框架相比，FastVideo 更加垂直和极致，深度定制了底层算子（fastvideo-kernel）和分布式并行策略（序列并行、FSDP2）。目前项目处于高速迭代的活跃期（v0.2.1），已在生产环境支撑了 Dreamverse 实时视频生成应用。 针对你的切入建议：虽然你目前只有一台 16GB 的 MacBook Air，但这正是你的独特优势。FastVideo 原生支持 macOS 并专门开发了 fastvideo/mlx_runtime（支持 FastMetal-QAD 模型），你完全可以在本地进行 Apple Silicon / Metal 算子的极致优化和端侧部署验证（1.3B 模型在 16GB 内存下完全可跑）。对于你擅长的 CUDA/Triton 和算子融合，你可以通过阅读 fastvideo-kernel/csrc 参与核心逻辑设计，利用项目完善的 CI（.buildkite 和 .github/workflows）进行编译检查，最后借助 Colab 免费 T4（16GB 显存）完成小规模算子正确性验证或 FP8/量化内核的测试。

解决什么问题、给谁用

视频生成模型（如 DiT）参数量巨大、计算复杂度高（长序列注意力），导致推理极慢且显存占用极高，难以实现实时交互（如 Vibe Directing）或在边缘设备/消费级单卡上部署。同时，现有的后训练技术（蒸馏、量化、稀疏化）缺乏一个针对视频模型开箱即用的统一流水线。

1. AI 性能工程师与算子开发者：需要为特定硬件（NVIDIA、Apple Silicon、DGX Spark）编写和集成高性能 Kernel 的开发者。 2. 生成式 AI 研究员：进行视频模型微调、LoRA 训练、DMD2 蒸馏或稀疏注意力研究的算法人员。 3. 下游应用开发者：需要将视频生成能力集成到实时交互产品（如 Dreamverse）中的全栈或后端工程师。

同类项目与差别

  • Hugging Face Diffusers：Diffusers 是大而全的通用扩散模型生态，而 FastVideo 专注于视频 DiT 的极致性能，内置了高度定制的 CUDA 算子（如 VSA、Block Sparse Attention）和特定的后训练蒸馏流水线（DMD2），在特定视频模型的端到端速度上更具优势。
  • vLLM / SGLang：vLLM 等框架主要解决 LLM/VLM 的文本自回归推理加速（PagedAttention），而 FastVideo 解决的是 Diffusion 模型的去噪迭代加速、序列并行（Sequence Parallelism）以及视频特有的时空稀疏注意力问题。
  • NVIDIA FastGen：FastGen 是 NVIDIA 团队的加速方案（README 提及在 FastH3 上有合作），通常深度绑定 NVIDIA 硬件生态；而 FastVideo 强调跨平台，原生支持 Apple Silicon (MLX) 和 DGX Spark (ARM64)。

二、架构与代码地图

FastVideo 的架构设计呈现出高度垂直整合的特点，从最上层的实时流媒体应用一直贯穿到最底层的硬件特定算子。对于只有 MacBook Air 的你来说，理解这种分层至关重要，因为你可以将精力集中在与 Apple Silicon 相关的层级，或者通过纯代码阅读参与 CUDA 层的设计。\n\n1. 应用与服务层 (Application & Serving Layer)：位于 apps/ 和 examples/serving/。核心是 apps/dreamverse，这是一个支持实时视频生成和“Vibe Directing”的流媒体后端，包含 WebSocket 通信、GPU 池化调度和音视频复用逻辑。此外还有 fastvideo_studio 提供任务管理。\n\n2. 入口与 API 层 (Entrypoint & API Layer)：位于 fastvideo/api/ 和 fastvideo/entrypoints/。VideoGenerator 是最核心的对外接口，负责解析 GenerationRequest，加载 PipelineConfig，并将高层请求转化为底层的执行计划。\n\n3. 流水线与调度层 (Pipeline & Scheduling Layer)：位于 fastvideo/pipelines/。这里实现了扩散模型的去噪循环（Diffusion Loop），包括标准的 DDIM/Euler 调度，以及 FastVideo 核心的 DMD2（分布匹配蒸馏）步进逻辑。同时，序列并行（Sequence Parallelism）的切分与通信调度也在此层协调。\n\n4. 模型与网络层 (Model & Network Layer)：位于 fastvideo/models/ 和 fastvideo/layers/。包含 Wan2.1/2.2、MiniMax-H3 等前沿 DiT 模型的 PyTorch 定义。此层深度集成了 FSDP2 和选择性激活重算（Selective Activation Checkpointing）以应对超大参数量。\n\n5. 算子与硬件抽象层 (Kernel & Hardware Abstraction Layer)：这是你的主战场。位于 fastvideo/attention/。它通过 backends/abstract.py 提供统一接口，向下路由到不同的硬件实现。\n\n6. 底层执行层 (Execution Layer)：分为两个分支。NVIDIA 分支位于 fastvideo-kernel/，包含极致优化的 CUDA C++（如 Block Sparse Attention, Attn-QAT）和 Triton 算子；Apple Silicon 分支位于 fastvideo/mlx_runtime/，这是你本地开发的核心，利用 MLX 框架实现了 FastMetal-QAD 等模型在 Mac 上的高效推理。

一次调用怎么流过这些模块

在 FastVideo 中，一次完整的视频生成推理请求（以你在本地 Mac 上运行 FastMetal-QAD 或在 Colab 运行 FastH3 为例）的数据流如下：\n\n1. 初始化与配置解析：用户调用 VideoGenerator.from_pretrained()。系统首先进入 fastvideo/api/parser.py 解析配置，生成 PipelineConfig 和 EngineConfig。此时，系统会根据环境变量（如 FASTVIDEO_ATTENTION_BACKEND）和硬件平台（检测到 MPS/MLX 或 CUDA）初始化对应的权重和后端。如果你在 Mac 上，fastvideo/mlx_runtime 会接管模型权重的加载，将其转换为 MLX 兼容的格式。\n\n2. 请求预处理：调用 generate_video(prompt) 时，请求被封装为 GenerationRequest。文本提示词首先通过 Text Encoder（最近的提交显示 MiniMax H3 的文本编码器已支持 NVFP4 量化，见 basic_minimax_h3_t2v.py 和相关 PR）。如果是图生视频（I2V），图像也会通过 VAE 编码为 Latents。\n\n3. 进入扩散流水线 (Diffusion Pipeline)：数据流入 fastvideo/pipelines/。调度器（Scheduler）根据配置（例如 FastH3 的 8-step 蒸馏配置）生成时间步（Timesteps）。在每个时间步中，Latents、Timesteps 和 Text Embeddings 被送入 DiT 模型。\n\n4. 模型前向与注意力分发 (The Hot Path)：在 fastvideo/models/ 的 DiT Block 中，计算密集型的 Attention 操作被拦截。系统调用 fastvideo/attention/backends/abstract.py。\n - 如果在 NVIDIA GPU 上：请求被路由到 fastvideo-kernel。例如，如果启用了 VSA（Video Sparse Attention），会调用 block_sparse_attn.py，进而触发 csrc/attention/block_sparse_sm100a.cu 等底层 CuTe 算子。如果是量化模型，则调用 attn_qat_infer/api.py 中的 sageattn_blackwell 算子。\n - 如果在 Apple Silicon 上：请求被路由到 fastvideo/mlx_runtime，利用 MLX 的 Metal 算子执行优化的 Attention 计算（如 mlx_fasth3.py 示例所示）。\n\n5. 解码与输出：经过多步去噪后，最终的 Latents 被送入 VAE Decoder 还原为像素空间的视频帧。如果是 Dreamverse 应用，这些帧会被 apps/dreamverse/dreamverse/av_streaming.py 实时编码并推流；如果是普通脚本，则保存为 MP4 文件。

扩展点

  • 新模型 (New DiT Model)：在 fastvideo/models/ 下新建模型定义文件，继承基础 DiT 类，并在 fastvideo/registry.py 中注册模型路径和支持的 Workload (t2v, i2v)。
  • 新注意力算子 (New Attention Kernel)：在 fastvideo-kernel/csrc/ (CUDA) 或 triton_kernels/ (Triton) 实现底层逻辑。然后在 fastvideo/attention/backends/ 下新建 Python 包装类，继承 AttentionBackend，并在工厂方法中注册。
  • 新 Apple Silicon 优化 (New MLX Backend)：在 fastvideo/mlx_runtime/ 中实现基于 MLX 的网络层或算子替换，确保在 VideoGenerator 初始化检测到 MPS 时能够正确劫持 PyTorch 原生模块。
  • 新调度策略/蒸馏算法 (New Pipeline/Scheduler)：在 fastvideo/pipelines/ 中添加新的 Pipeline 类，实现自定义的 __call__ 去噪循环逻辑（如新的 DMD2 步进策略）。

三、本地跑起来（没有 GPU 的 Mac）

安装

  1. uv venv --python 3.12 --seed
  2. source .venv/bin/activate
  3. uv pip install -e '.[mlx]'
  4. pre-commit install --hook-type pre-commit --hook-type commit-msg

哪些路径能真跑

作为 CUDA/Triton 专家，你在本地 Mac 上主要进行代码阅读和架构设计。纯 CUDA C++ 算子（如 fastvideo-kernel/csrc/attention/block_sparse_sm100a.cu、turbodiffusion/）和 Triton 算子（fastvideo-kernel/python/fastvideo_kernel/triton_kernels/）在本地只能作为只读路径。但得益于项目对 Apple Silicon 的原生支持，你可以真正执行 fastvideo/mlx_runtime/ 下的 Metal 算子逻辑，以及 fastvideo/attention/backends/ 中的高层路由逻辑。如果需要验证你手写的 CUDA/Triton 算子正确性，请将 fastvideo-kernel 目录推送到 Colab T4 上，执行 cd fastvideo-kernel && ./build.sh 进行编译和单元测试。

最小可运行

  1. python examples/inference/basic/mlx_wan22_generate.py
  2. python examples/inference/basic/mlx_fasth3.py
  3. python examples/inference/basic/basic_mps.py
  4. pytest fastvideo/tests/ -v

测试

测试框架使用 pytest。测试目录分为三层：fastvideo/tests/（Python 包级别的核心逻辑与流水线测试）、tests/local_tests/（本地组件检查）、以及 fastvideo-kernel/tests/（底层 CUDA/Triton 算子测试）。在你的 Mac 上，只需跑 pytest fastvideo/tests/ -v 即可覆盖大部分 CPU/MPS 兼容的逻辑，耗时在几分钟内。请务必跳过 pytest fastvideo/tests/ssim/，根据 AGENTS.md 记载，SSIM 回归测试是重度依赖 GPU 的（GPU-heavy），在 Mac 上会极慢或失败。算子层的测试（如 test_vsa256_triton.py）需留到 Colab T4 上运行。

CI

CI 体系分为两部分：GitHub Actions (.github/workflows/) 负责常规的 Lint、单元测试和文档构建；Buildkite (.buildkite/pipeline.yml) 负责重度性能基准测试（Performance Benchmarks）。PR 最容易被卡在代码风格检查上。项目严格配置了 pre-commit（包含 yapf, ruff, mypy, codespell）。

坑

  • 依赖陷阱：不要在 Mac 上尝试手动编译 fastvideo-kernel。pyproject.toml 中已经通过 sys_platform == 'linux' 隔离了 fastvideo-kernel 和 flashinfer-python，uv 会自动跳过它们，强行编译会因缺少 nvcc 报错。
  • 内存 OOM 坑：你的 MacBook Air 只有 16GB 统一内存。测试时请务必使用 1.3B 的模型（如 FastVideo/FastMetal-1.3B-QAD 或 FastWan2.1-T2V-1.3B），千万不要尝试加载 14B 模型，否则会直接 OOM 崩溃。
  • 代码格式化坑：根据 AGENTS.md 警告，绝对不要手动执行 yapf 或 ruff。必须通过 pre-commit run --all-files 来执行，因为 .pre-commit-config.yaml 中包含特定的排除规则（例如故意跳过了 fastvideo/tests/），手动执行会破坏这些规则导致 CI 失败。
