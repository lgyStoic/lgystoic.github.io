sgl-project/sglang

候选人擅长 AI Infra，但目前没有高性能 GPU。挑选的任务集中在调度器状态机、权重加载逻辑、API 协议层（OpenAI/Anthropic 兼容性）以及 Tokenizer 编码逻辑。这些任务完全可以在 CPU 环境下通过单元测试或离线推理引擎状态机进行验证，且对 SGLang 的生产环境稳定性至关重要。

当前方向：SGLang 目前在快速迭代支持最新的前沿模型（如 DeepSeek-V4.1, Qwen3 等），同时在完善其生产级 Serving 能力（如 API 兼容性、计费指标、多语言前端对齐）。

Issue #39942 · [Bug] FP8 KV cache scales are silently dropped when loading Qwen3-MoE / Qwen2 / Mixtral and every layer falls back to scale 1.0 ↗

目标：修复 Qwen3-MoE、Qwen2 和 Mixtral 模型加载 FP8 KV cache scales 时因名称映射错误导致 scale 丢失的问题。

为什么值得长期做：权重加载和量化参数映射是推理引擎的基石。修复此问题能避免严重的静默精度损失，是深入模型架构和量化机制的绝佳机会。

第一步：在相关模型文件中引入并使用 `maybe_remap_kv_scale_name` 函数。
大致实施方案
  • 定位 `python/sglang/srt/models/qwen3_moe.py`, `qwen2.py`, `mixtral.py`。
  • 引入 `python/sglang/srt/model_loader/weight_utils.py` 中的 `maybe_remap_kv_scale_name`。
  • 在 `stacked_params_mapping` 循环处理权重名称时，对 scale 相关的 tensor 名称应用该重映射函数，避免被错误的子串替换逻辑破坏。
  • 编写离线测试，加载带有 FP8 KV scale 的 dummy checkpoint，断言加载后的 `k_scale` 和 `v_scale` 不为 1.0。
可能涉及的目录或文件
  • python/sglang/srt/models/qwen3_moe.py
  • python/sglang/srt/models/qwen2.py
  • python/sglang/srt/models/mixtral.py
  • python/sglang/srt/model_loader/weight_utils.py
验收方式
  • 在 CPU 环境下加载一个包含 FP8 KV scale 的小型 Qwen2 模型，打印 `model.layers[0].self_attn.attn.k_scale`，确认其值等于 checkpoint 中的真实值而非 1.0。

Retracted input_embeds requests silently splice two generations into one successful response (send_token_offset survives the discard of output_ids)

Issue #39645 · Retracted input_embeds requests silently splice two generations into one successful response (send_token_offset survives the discard of output_ids) ↗

目标：在请求因 OOM 被 retract 时，彻底重置所有输出流相关的 offset 状态，防止新旧生成结果拼接。

为什么值得长期做：调度器的状态机管理是推理引擎最核心、最复杂的部分。解决请求重试导致的状态泄漏问题，能证明你具备维护核心调度逻辑的能力。

第一步：在 `Req.reset_for_retract()` 中添加对 `send_token_offset` 及相关游标的重置逻辑。
大致实施方案
  • 定位 `python/sglang/srt/managers/schedule_batch.py` 中的 `reset_for_retract` 方法。
  • 在 `self.input_embeds is not None` 分支中，除了清空 `output_ids`，还需将 `send_token_offset`、`send_decode_id_offset` 等输出流游标重置为 0。
  • 检查 `init_incremental_detokenize` 相关的增量 detokenizer 游标（如 `surr_offset`, `read_offset`），确保它们在 retract 时也被正确重置。
  • 编写纯 Python 的状态机单元测试，模拟请求生成一半被 retract 然后重新生成的过程，断言最终输出的 token 序列完整且无截断。
可能涉及的目录或文件
  • python/sglang/srt/managers/schedule_batch.py
  • python/sglang/srt/managers/scheduler_components/output_streamer.py
验收方式
  • 执行 Issue 中描述的状态机复现步骤（无需 GPU），断言 `reset_for_retract()` 执行后，`send_token_offset` 为 0，且后续的 `output_ids_` 切片逻辑能正确获取完整的重新生成序列。
开工前问题与风险

向维护者确认

  • 除了 `send_token_offset` 和 `send_decode_id_offset`，是否还有其他在 request 级别维护的流式状态需要在 retract 时重置？

风险

  • 重置游标可能导致客户端收到重复的 token（如果客户端不具备处理重试的能力），需确认 SGLang 的流式协议对 retract 的预期行为。
