一、项目定位

SGLang 是一个由 LMSYS 孵化的高性能大语言模型（LLM）与多模态模型（VLM、Diffusion）推理服务框架。它的核心存在价值是通过 RadixAttention（前缀缓存）、零开销 CPU 调度器、预填充-解码分离（Prefill-Decode Disaggregation）等架构创新，在单卡到大规模分布式集群中实现极低的延迟与极高的吞吐量。与同类项目相比，SGLang 不仅是一个标准的推理端点，更被广泛作为强化学习（RL）和后训练（Post-Training）的 Rollout 后端（如集成于 AReaL, Miles, verl 等）。目前项目处于高度成熟的生产阶段（v0.5.19），在全球部署了超过 40 万张 GPU，并获得了 a16z 的开源 AI 资助。 对于你（资深 GPU Kernel/训练性能工程师）而言，这个项目与你的技能树**完美契合但硬件条件严重错位**。仓库中充满了你擅长的领域：CuTe DSL 优化（如最近提交 `Coalesce the KDA CuTe DSL decode state transpose`）、CUTLASS MoE 算子（`Guard FlashInfer CUTLASS MoE`）、DeepGEMM 适配（`Include SM121 in DeepGEMM`）以及扩散模型加速（`[diffusion] feat: add metrics support`）。**但是**，由于你只有一台 16GB 的 MacBook Air，你无法在本地开发和验证这些硬核 CUDA/Triton 算子。你的切入策略必须是：1) 关注调度器逻辑（如最近的 `Shortest-prefill-first scheduling`）或 Speculative Decoding 的 Python 控制流，这些可以在 Apple Silicon 上通过 `arm64.Dockerfile` 或 `pyproject_cpu.toml` 进行纯 CPU 单元测试；2) 编写 Triton 算子后，完全依赖 GitHub Actions CI 或在 Colab T4 上做几十分钟的编译与正确性验证，放弃需要极高显存的性能 Profiling 工作。

解决什么问题、给谁用

解决大规模 AI 模型在生产环境推理时面临的显存碎片化、长上下文/多轮对话中的重复计算（通过 RadixAttention 解决）、复杂 MoE 模型（如 DeepSeek V3/R1）的分布式推理效率，以及强化学习（RLHF）训练中 Rollout 阶段的生成瓶颈问题。

企业级 AI 基础设施团队（如 xAI, NVIDIA, OpenAI）、前沿模型研究者（进行 RL 后训练的团队），以及需要高吞吐量结构化输出或多模态/视频生成（Diffusion）服务的 AI 应用开发者。

同类项目与差别

  • vLLM：SGLang 在 README 中致敬了 vLLM，但 SGLang 的核心差异在于其原生的 RadixAttention（更细粒度的前缀缓存树）和零开销 CPU 调度器，且在 RL Rollout 后端集成上生态更深。
  • FlashInfer：FlashInfer 是一个底层的 Kernel 库，SGLang 是调用它的上层服务框架。证据表明 SGLang 深度依赖并定制 FlashInfer（如提交 `Guard FlashInfer CUTLASS MoE against 0-token inputs`）。
  • LightLLM：SGLang 同样致敬了 LightLLM，但 SGLang 提供了更广泛的异构硬件支持（TPU, NPU, AMD MI300, Intel Xeon）以及对多模态和 Diffusion 模型（WAN, Qwen-Image）的原生支持。
  • Guidance / Outlines：这两者偏向于前端提示词控制和结构化输出库。SGLang 吸收了它们的理念，将结构化输出（如压缩有限状态机 JSON 解码）直接下沉到推理引擎 C++/CUDA 层面以获得 3x 加速。

二、架构与代码地图

SGLang 的架构设计高度分层，且为了兼顾极致性能与跨平台开发体验，做出了非常精妙的解耦。对于只有 MacBook Air 的你来说，理解这些分层是决定“哪里可以在本地跑、哪里必须靠 CI”的关键。 1. **前端与接口层 (Frontend & API Layer)**：位于 `python/sglang/lang/`。这是 SGLang 的标志性特性，提供了一套基于 Python 的 Prompt DSL（如 `gen`, `select`, `system`, `user`）。这一层完全是纯 Python 控制流，不依赖任何 GPU 算子，你可以在 Apple Silicon 上毫无障碍地进行本地开发和单元测试。 2. **路由与网关层 (Router & Gateway Layer)**：位于 `experimental/sgl-router/`。这是一个用 Rust (Tokio + Tonic) 编写的高性能网关。它负责多节点/多卡集群的流量分发。核心机制包括基于 `sgl-kv-indexer` 的前缀树（Radix Tree）匹配，以及基于 `engine_load.rs` 中 `LoadStat` 的缓存感知（Cache-Aware）负载均衡。这部分是纯 CPU 逻辑，Rust 跨平台编译极好，完全可以在 Mac 上开发和压测。 3. **调度与控制层 (Scheduling & Control Layer)**：位于 `python/sglang/srt/managers/`（需验证具体路径，基于常识与提交记录推断）。这里是 SGLang 的“大脑”，实现了 RadixAttention 的前缀缓存管理、连续批处理（Continuous Batching）、预填充-解码分离，以及最近提交的 `Shortest-prefill-first scheduling` 和投机解码（`TreeSpeculativeSamplingTargetOnly`）。**这是你切入的最佳甜点区**：调度逻辑复杂但对显存要求低，配合 `arm64.Dockerfile` 或 `pyproject_cpu.toml`，你可以在本地验证调度算法的正确性。 4. **执行与引擎层 (Execution & Engine Layer)**：位于 `python/sglang/srt/`。以 `Engine` 和 `Runtime` 为核心，负责模型权重的加载、分布式通信（NCCL/DeepEP）的协调。为了让你能在 Mac 上跑通这一层的控制流，官方极其贴心地提供了 `python/sglang/_platform_stubs.py`，它会在 ARM64 macOS 上自动 Mock 掉 `torch.mps` 缺失的 API 以及整个 `triton` 库。这意味着你可以“空转”引擎。 5. **内核与算子层 (Kernel Layer)**：散布在 `benchmark/kernels/` 及底层实现中。这里充满了你最擅长的 CuTe DSL、CUTLASS MoE、DeepGEMM、FlashInfer 和 Triton 算子。由于硬件限制，你在这里的开发模式必须是“盲写”：在本地编写 Triton/CUDA 代码，利用 `benchmark/kernels/` 下的脚本构建测试用例，然后推送到 GitHub 依赖 CI 运行，或者在 Colab T4 上做几十分钟的正确性验证，彻底放弃本地 Profiling。

一次调用怎么流过这些模块

一次完整的 LLM 推理请求在 SGLang 中的数据流转如下，特别关注分布式与缓存感知机制： 1. **请求接入与路由 (Ingress & Routing)**： 客户端通过 HTTP 发送请求。在分布式部署下，请求首先命中 `experimental/sgl-router`。Router 解析请求的 Prompt，并通过 `sgl-kv-indexer` (gRPC 客户端位于 `client.rs`) 查询全局前缀树。Indexer 返回 `PrefixMatch`，指出哪个 Worker 拥有最长的前缀缓存。同时，Router 会结合 `engine_load.rs` 中订阅的各个 Worker 的 `LoadStat`（包含 `num_running_reqs`, `num_waiting_reqs`, `num_tokens` 等），综合计算打分，将请求转发给最优的 Worker。 2. **调度与内存分配 (Scheduling & Allocation)**： 请求到达目标 Worker 的 `RuntimeEndpoint`，进入 `python/sglang/srt/` 的调度队列。调度器（如最近优化的 `Shortest-prefill-first scheduling`）会评估当前 GPU 的 Token Pool 碎片情况。如果命中 RadixAttention 缓存，直接复用物理块；否则，分配新的物理块。对于多轮对话或长上下文，这一步极大地减少了重复计算。 3. **预填充阶段 (Prefill)**： 调度器将 Batch 组装好后，下发给 GPU 执行。如果是纯文本，调用 FlashInfer 或 Triton 编写的 Attention 算子；如果是 DeepSeek V3/R1 这种复杂模型，会触发 `benchmark/kernels/deepseek/` 中测试的 DeepGEMM 或 CuTe DSL 优化的 MoE 算子。**注意**：在你的 Mac 上，由于 `_platform_stubs.py` 的存在，这些 Triton 算子会被 Mock 为空操作或直接跳过，从而允许你跑通外层的调度逻辑。 4. **解码阶段 (Decode) 与投机解码 (Speculative Decoding)**： 预填充结束后，请求进入 Decode 阶段。如果开启了投机解码，控制流会进入类似 `TreeSpeculativeSamplingTargetOnly` 的逻辑，先用小模型（Draft Model）生成多个候选 Token 树，再由大模型（Target Model）一次性验证。这里的 CDF 边界处理和树结构控制是纯 Python/PyTorch 逻辑，非常适合你在本地 CPU 上进行算法优化。 5. **状态回传与输出 (Streaming & Output)**： 生成的 Token 通过 `gRPC stream engine state changes` 实时流式返回给 Router，Router 再通过 SSE (Server-Sent Events) 推送给客户端。同时，Worker 会更新自身的 Radix Tree 状态，并通过 ZMQ Monitor 将最新的 `LoadStat` 广播给 Router，完成闭环。

扩展点

  • 新模型 (New Model)：在 `python/sglang/srt/models/` (需验证) 下新建模型文件，实现 PyTorch 的 `nn.Module`，并使用 SGLang 提供的 `Linear`, `Attention` 等定制层替换原生层。最后在模型注册表中注册。由于你没有 GPU，建议只做模型结构的搬运和 CPU 维度的 Shape 对齐测试。
  • 新 Kernel (New Kernel)：在 `python/sglang/srt/layers/` (需验证) 下集成新的 Triton/CUDA 算子，并在 `benchmark/kernels/` 下编写对应的 `bench_*.py`。你的策略是：在 Mac 上盲写 Triton 代码，推送到 PR 依赖 GitHub Actions 编译，或在 Colab T4 上运行 benchmark 脚本验证正确性。
  • 新调度策略 (New Scheduling Policy)：在 `python/sglang/srt/managers/` (需验证) 中修改或新增调度逻辑（如参考 `Shortest-prefill-first` 的实现）。这是你的优势区域，可以直接在 Mac 上通过 `pyproject_cpu.toml` 环境运行单元测试，验证 Batch 组装和 Token Pool 分配的正确性。
  • 新路由策略 (New Routing Policy)：在 `experimental/sgl-router/src/policies/` 下新建 Rust 模块，实现路由 Trait。可以利用 `engine_load.rs` 提供的负载数据和 `sgl-kv-indexer` 提供的前缀数据进行自定义打分。纯 Rust 开发，Mac 完美支持。

三、本地跑起来（没有 GPU 的 Mac）

安装

  1. git clone https://github.com/sgl-project/sglang.git && cd sglang
  2. cp python/pyproject_cpu.toml python/pyproject.toml
  3. pip install -e ./python
  4. cd experimental/sgl-router && cargo build

哪些路径能真跑

在 Apple Silicon 上，由于 `python/sglang/_platform_stubs.py` 会在检测到 `darwin` 和 `arm64` 时自动注入 Mock（替换缺失的 `torch.mps` API 并将 `triton` 替换为 `_MockModule`），你可以完美运行以下纯 CPU 路径：1) `python/sglang/lang/` 下的所有 Prompt DSL 前端逻辑；2) `experimental/sgl-router/` 下的 Rust 高性能网关（完全跨平台）；3) `python/sglang/srt/managers/` 中的调度器控制流（如 `Shortest-prefill-first scheduling`）。相反，`benchmark/kernels/` 下的所有硬核算子（如 `fused_moe_triton`, `deepseek/benchmark_deepgemm_fp8_gemm.py`）在本地完全无法执行，只能当做纯文本阅读，必须依赖 Colab T4 或 CI 环境进行验证。

最小可运行

  1. python3 examples/frontend_language/usage/sgl_gen_min_tokens.py
  2. cd experimental/sgl-router && cargo run -- --model-id dummy --worker-urls http://127.0.0.1:8080
  3. cd experimental/sgl-router && cargo test --lib
  4. python3 .claude/skills/llm-torch-profiler-analysis/scripts/analyze_sglang_torch_profile.py --help

测试

测试分为两部分：Rust 网关层使用标准的 `cargo test`（目录 `experimental/sgl-router/tests/`），这部分完全可以在 Mac 上秒级跑完，包含大量并发与路由策略测试（如 `test_load_based_policy.py` 的底层逻辑）；Python 层使用 `pytest`，但由于你没有 GPU，建议只运行前端 DSL 和调度器的单元测试，跳过 `test/srt/` 下依赖 CUDA 的端到端推理测试。完整 CPU 测试集耗时约在几分钟内。

调试

  • Rust 路由网关调试：启动时注入环境变量 `RUST_LOG=debug cargo run`，根据 `experimental/sgl-router/src/main.rs`，它会输出详细的 JSON 或 Text 格式的 Trace 日志。
  • Triton 算子“盲写”调试：由于 `_platform_stubs.py` 会把 `@triton.jit` 变成一个直接返回原函数的装饰器，本地 Python 解释器**不会**对 Triton kernel 内部做任何编译期语法检查。建议在本地只做逻辑推演，用 Colab T4 跑 `benchmark/kernels/` 下的脚本看报错。
  • 性能 Profiling 分析：虽然本地不能跑 Profiling，但你可以用 Colab 跑出 trace，然后用本地的 `.claude/skills/llm-torch-profiler-analysis/scripts/analyze_sglang_torch_profile.py` 进行离线分析，这是你发挥性能优化特长的关键入口。

CI

项目使用 GitHub Actions (`.github/workflows/`)。PR 会被严格的 Linter（`.pre-commit-config.yaml`, `isort`）卡住。对于 Kernel 工程师，最关键的是 CI 中包含自建的 GPU Runner（依据 `.github/CI_PERMISSIONS.json` 和大规模开源项目的惯例），你的 CUDA/Triton 提交最终需要通过 CI 的 GPU 矩阵测试才能合并。建议提交前确保代码符合 `mechanical_refactor_reproduction_cli.py` 等自动化验证脚本的规范。

坑

  • Triton 幽灵代码陷阱：如前所述，Mac 上的 `_MockModule` 会让所有 Triton 代码“静默通过”本地执行，千万不要以为本地没报错就是算子写对了。
  • Rust Router 优雅退出警告：在本地跑 Router 时，如果不加 `--termination-grace-secs` 参数，`shutdown_drain_secs` 逻辑会疯狂打印 Warning（见 `cli.rs`），这属于正常现象，不影响核心逻辑验证。
  • 依赖冲突：不要直接 `pip install -e .`，默认的 `pyproject.toml` 会拉取 FlashInfer、vLLM 等强依赖 CUDA 的库，在 Mac 上会导致编译失败。务必使用 `pyproject_cpu.toml` 或 Dockerfile (`arm64.Dockerfile`)。
