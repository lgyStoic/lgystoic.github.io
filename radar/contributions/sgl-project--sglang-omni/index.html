一、项目定位

SGLang-Omni 是 sgl-project 下的多阶段（multi-stage）推理服务框架，专门面向 omni 模型、TTS 语音生成、ASR 语音转录以及统一多模态模型。它不是从零重写一个推理引擎，而是在 SGLang 高性能自回归调度/执行之上，把生成流程拆成多个异构阶段（preprocessing / encoders / autoregressive engines / talkers / decoders / vocoders / aggregators），由自己拥有的 pipeline 拓扑、阶段生命周期、跨阶段传输（relay data plane）和 OpenAI 兼容 API 层来编排。项目当前处于活跃迭代期：PyPI 已发布到 v0.1.7（2026-09-28），近一个月内密集提交 CUDA graph 优化、XPU/Apple Silicon/NPU 多后端适配、流式 SSE 输出、codec 与 vocoder 调度等能力；README 明确标注 Apple Silicon 与 Intel XPU 为 Experimental。仓库结构清晰：sglang_omni/ 是主 Python 包（678 文件），sglang_omni_router/ 是 Rust+Python 的多 worker 前端路由，OmniTyper/ 是 Swift 辅助工具，benchmarks/、docs/、examples/、playground/、tests/ 配套齐全。提交热点集中在 sglang_omni/models（52 次）和 tests/unit_test（35 次），说明模型集成与单测是当前重心，platforms/（5 次）和 scheduling/（2 次）次之，符合其多后端扩展阶段。

解决什么问题、给谁用

解决的核心问题是：现代语音/多模态模型（如 Qwen3-Omni、MiniMax Music 3、Higgs Audio v3、Fish Speech S2-Pro 等）的推理管线不再是单一 LLM 自回归解码，而是多阶段异构计算（文本编码 → 自回归/扩散解码 → codec/vocoder → 聚合），各阶段计算模式、依赖结构、资源需求差异巨大，传统单一调度器无法高效编排。目标用户是：需要部署 TTS/ASR/Omni 模型到生产或研究环境的多模态推理工程师、MLSys 研究者、以及希望复用 SGLang 高性能调度但扩展到语音/多模态场景的开发者。典型场景：通过 /v1/audio/speech 提供流式或非流式语音合成、通过 /v1/audio/transcriptions 提供 ASR 与 diarization、通过 /v1/chat/completions 提供多模态对话、以及多 worker 负载均衡的线上服务。

同类项目与差别

  • SGLang (sgl-project/sglang)：SGLang 专注纯文本 LLM 的高性能自回归调度与执行（RadixAttention、CUDA graph、张量并行等）；SGLang-Omni 在其之上扩展多阶段异构管线，拥有独立的 pipeline 拓扑、阶段调度、relay 传输层、vocoder/talker 集成，以及语音/多模态专用 API 端点。
  • vLLM：vLLM 是通用 LLM serving 框架，以 Continuous Batching 和 PagedAttention 见长，但原生不支持 TTS/ASR 多阶段管线、codec/vocoder 调度、以及 SGLang-Omni 的 relay data plane（NIXL/Mooncake 后端）。
  • Triton Inference Server (NVIDIA)：Triton 是通用模型 serving 平台，支持多模型编排与多种后端，但缺乏对 SGLang 自回归调度、RadixAttention、以及 SGLang-Omni 中针对 TTS/Omni 模型定制的多阶段 pipeline 与流式 vocoder 循环的原生支持。
  • Coqui TTS / ChatTTS / Fish Speech 等独立 TTS 项目：这些项目通常提供单一模型的推理脚本或简单 API，缺乏 SGLang-Omni 的多模型统一 serving、多阶段调度、跨阶段传输优化、以及 OpenAI 兼容的多模态 API 表面。

二、架构与代码地图

SGLang-Omni 的代码组织可划分为五层，自上而下分别是：接入层（API 与路由）、调度层（多阶段生命周期与流水线编排）、执行层（模型运行器与 SGLang 后端桥接）、模型层（各模型家族的阶段、engine_builder、sglang_model、payload_types 等）、硬件与传输层（多后端平台抽象与跨阶段 relay data plane）。接入层由 sglang_omni_router（Rust+Python 多 worker 前端路由）和 sglang_omni/http（FastAPI 适配、OpenAI 兼容端点、SSE 流式）组成，负责把外部 HTTP 请求转成内部调度事件。调度层以 sglang_omni/scheduling 为核心，包含 OmniScheduler、engine_factory（AsrEngineBuilder / TtsEngineBuilder）、generation_batch_policy、message 等，决定请求在 preprocessing → encoder → AR engine → talker → decoder → vocoder → aggregator 等多阶段之间的流转。执行层在 sglang_omni/model_runner，定义 ModelRunner 基类以及各模型特化的 runner（如 FunCosyVoice3ModelRunner、FishS2ProModelRunner、DotsTTSModelRunner），通过 sglang_execution 桥接到 SGLang 的 forward_batch/schedule_batch 执行路径。模型层是最大的一层（sglang_omni/models，678 文件中的主体），每个模型目录都按 stages / engine_builder / sglang_model / request_builders / payload_types 等切分，是扩展新模型的主要落点。硬件与传输层包括 sglang_omni/platforms（CUDA/XPU/NPU/ROCm/MPS 检测与能力声明）、sglang_omni/relay（跨阶段 tensor 传输，支持 NCCL、NIXL、Mooncake、共享内存）以及 sglang_omni/mps、sglang_omni/vendor/sglang 等后端适配代码。

一次调用怎么流过这些模块

一次典型的 TTS 请求（如 /v1/audio/speech）数据流如下：(1) 请求进入 sglang_omni_router（Rust 前端路由），经健康/能力发现后转发给 FastAPI 应用；(2) sglang_omni/http 层解析请求体，构造内部调度消息并送入 scheduling 层；(3) scheduling 层的 OmniScheduler 根据模型家族选择对应 pipeline 拓扑（如 preprocessing → AR engine → vocoder → aggregator），通过 engine_factory（TtsEngineBuilder 子类）构造各阶段；(4) preprocessing 阶段调用对应模型的 request_builders 与 payload_types，把文本/参考音频转成 tensor，经 relay data plane（NCCL/NIXL/Mooncake/共享内存）传到 AR engine；(5) AR engine 由 sglang_omni/model_runner 的模型特化 runner（如 FunCosyVoice3ModelRunner）驱动，通过 sglang_execution 桥接到 SGLang 的 forward_batch/schedule_batch 执行路径，每步 decode 产出 semantic token / codec codebook；(6) 中间结果经 comm（ZMQ/msgpack）或 relay 传到 talker/vocoder 阶段（如 streaming_vocoder、HiFT、DAC），由 vocoder_scheduler 控制流式输出节奏；(7) 最终音频由 aggregator 收集，经 http_api 层 SSE 或非流式响应返回客户端。关键数据结构包括 forward_batch、schedule_batch（来自 SGLang）、各模型的 payload_types（请求级数据容器）、OutgoingMessage（阶段间消息）、generation_batch_policy（CUDA graph 策略）。调度点主要在 OmNiScheduler 的阶段分发、engine_builder 的 generation_defaults 注入、model_runner 的 before_prefill/before_decode/post_prefill/post_decode 钩子。

扩展点

  • sglang_omni/models/<new_model>/：新建模型子目录，至少实现 stages.py（阶段定义）、engine_builder.py（继承 AsrEngineBuilder 或 TtsEngineBuilder，重写 generation_defaults/customize_server_args/pre_infra_setup）、sglang_model.py（继承 SGLang 模型基类）、request_builders.py（请求构造）、payload_types.py（请求级数据容器），并在 models/__init__.py 注册

坑

  • # 1. Apple Silicon 上不要手动 pip install sglang==0.5.20 的 PyPI wheel——它带无条件 CUDA 依赖，会直接炸。让 install.sh 或 pyproject 的 sys_platform 标记处理 all_mps 变体。
  • # 2. flashinfer_python[cu13] / flash-attn-4 / nixl-cu13 / mooncake-transfer-engine-cuda13 / kernels 在 Apple Silicon 上不可用，pyproject 已排除，但手动装会破坏环境。
  • # 3. use_mlx() 与 torch MPS 路径是互斥分支——Fun-CosyVoice3 在 Apple Silicon 上走 MLX，其他模型可能走 audio_torch_mps.py，不要混用。
  • # 4. 16GB 统一内存限制：MLX 模型权重 + 推理 buffer 容易 OOM，优先跑小模型（Qwen3-ASR）或子模块单测。
  • # 5. tests/test_model/ 中大量用例硬绑 CUDA graph，Apple Silicon 上 import 即挂，跑前用 -k 或 -x 跳过。
  • # 6. relay 的 NCCL / NIXL / Mooncake 后端在 Apple Silicon 上不可用，只有共享内存后端可跑。
  • # 7. TensorRT 路径（flow_estimator_trt.py）在 Apple Silicon 上不存在，不要尝试。
  • # 8. 提交前必须跑 pre-commit（AGENTS.md/CLAUDE.md 强制要求），否则 CI 卡住。
  • # 9. 改了 pyproject.toml 中的平台标记时，同步检查 install.sh 与 docs/get_started/installation.md 是否一致。
  • # 10. 仓库处于活跃迭代期（v0.1.7 刚发布），main 分支可能不稳定，建议基于 tag 或 release 分支开发。

流程与 Review 风格

仓库没有独立的 CONTRIBUTING.md，但 README 与 docs/README.md 给出了明确流程。docs/README.md 要求：编辑 docs/ 下的 Markdown 或 RST 后，必须在开 PR 前运行 pre-commit run --all-files，若首轮自动修复文件则需再跑一次；新页面必须列入 index.rst 或对应 toctree；本地预览用 bash serve.sh 或 PORT=8080 make serve。AGENTS.md 与 CLAUDE.md 都要求在写、改、审代码前先读 .claude/skills/code-review/coding-style.md。仓库根目录存在 .pre-commit-config.yaml、.editorconfig、.isort.cfg、.github/CODEOWNERS、.github/pull_request_template.md，说明使用 pre-commit、CODEOWNERS 自动分配 reviewer、PR 模板。README 与 docs 中未提到 CLA 或 DCO，LICENSE 为 Apache-2.0。未发现强制先提 Issue 的明文规定，但 roadmap 类工作几乎都以 [Roadmap] / [RFC] Issue 先行。

从近期 PR 与 Issue 评论推断：review 偏重性能证据与可回归性。例如 #2430（Add native MLX Qwen3-TTS CustomVoice serving）与 #1983（[Apple][Fun-ASR] Add native MLX inference）直接对应 Apple Silicon 无 GPU 路径的落地，说明对 CPU/MPS 可运行性的高度关注；#2424（Optimize Torch Compile for PackedDiT）、#2403（Accelerate VoiceChat Perception with CUDA graphs）、#2392（Batch and window the streaming HiFT step）等 Perf PR 要求给出 microbenchmark 或 latency 数据。#2213（refactor(typing): replace explicit Any across core modules）与 #2195（Coding Style roadmap）显示对类型系统与代码风格的持续收紧。#2268（preserve TTS artifacts and cover Nemotron device contracts）显示 CI 需保留产物并覆盖 device contract。响应速度方面，2026-09-30 至 2026-10-01 的提交与 PR 几乎同日合并，活跃 reviewer 响应较快；但 RFC 类 Issue（如 #1967 Apple Silicon roadmap 22 条评论、#1754 Qwen3-TTS roadmap 26 条评论）讨论周期较长，需要充分论证。
