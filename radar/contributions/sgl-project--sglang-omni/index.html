一、项目定位

SGLang-Omni 是 sgl-project 下的多阶段（multi-stage）服务运行时，专门面向 omni 模型、TTS 语音合成、ASR 语音识别以及统一多模态模型。它解决的问题是：现代语音/多模态生成流水线天然由多个异构阶段组成（预处理、编码器、自回归引擎、talker、解码器、vocoder、聚合器），这些阶段的计算模式、依赖结构和资源需求差异很大，传统单一调度器无法高效编排。SGLang-Omni 自己拥有 pipeline 拓扑、stage 生命周期、stage 间传输、模型族集成层和 OpenAI 兼容 API 表面，同时在自回归调度与模型执行层复用 SGLang 的高性能 runtime。项目当前处于早期但快速迭代阶段：已在 PyPI 发布到 v0.1.7（2026-09-28），最近提交密集（2026-10 月初仍有大量模型集成、benchmark、fix 提交），支持 NVIDIA CUDA（默认全模型覆盖）、Apple Silicon（实验性，仅 Qwen3-ASR 通过 MLX/MPS）、Intel XPU（实验性，Qwen3-ASR/TTS、ZONOS2、Qwen3-Omni 端到端可用）等多硬件后端。代码规模上，sglang_omni 主目录约 700 个文件，tests 约 579 个文件，benchmarks 约 87 个文件，sglang_omni_router 约 72 个文件，整体是一个正在快速膨胀的中等规模 Python 项目。

解决什么问题、给谁用

解决多阶段异构生成流水线的编排与高效服务问题。具体包括：1）将 TTS/ASR/Omni 模型拆解为多个 stage（preprocessing、encoder、autoregressive engine、talker、decoder、vocoder、aggregator），每个 stage 需要匹配其 workload 的调度器；2）stage 间 tensor 传输需要支持 shared-memory、NCCL、NIXL、Mooncake 等多种后端；3）提供统一的 OpenAI 兼容 API（/v1/audio/speech、/v1/audio/transcriptions、多模态 chat）来暴露语音生成、批量语音、流式语音、上传语音、转录等能力。目标用户是需要在生产环境部署 TTS/ASR/Omni 模型的研究工程师和系统工程师，典型场景包括：实时语音对话（Qwen3-Omni）、歌词到歌曲生成（MiniMax Music 3）、可控语音合成（Higgs Audio v3、MOSS-TTS）、语音转录与说话人分离（MOSS-Transcribe-Diarize、Qwen3-ASR）。

1）ML/语音系统工程师：需要在生产环境部署 TTS/ASR/Omni 模型，要求高吞吐、低延迟、OpenAI 兼容 API；2）推理系统研究者：关注多阶段调度、stage 间传输、relay 数据平面、KV cache 效率；3）模型集成工程师：为新的语音/多模态模型（如 AuK、MiniCPM-o）添加 Day-0 支持；4）性能工程师：通过 benchmarks 目录下的工具和 configs 评估不同模型在 CUDA/XPU/Apple Silicon 上的表现。典型使用场景：通过 /v1/audio/speech 端点做实时流式 TTS、通过 /v1/audio/transcriptions 做批量 ASR、通过多模态 chat 端点做音视频对话、通过 sglang_omni_router 做多 worker 负载均衡。

同类项目与差别

  • SGLang (sgl-project/sglang)：SGLang 专注自回归 LLM 的调度与模型执行（prefill/decode 调度、RadixAttention、CUDA graph 等），是 SGLang-Omni 在自回归阶段的底层依赖；SGLang-Omni 在其之上扩展了多阶段 pipeline、非自回归 stage 调度、relay 传输层、语音/多模态专用 API。
  • vLLM：vLLM 是通用 LLM serving 框架，核心优势在自回归文本生成的PagedAttention和连续批处理；SGLang-Omni 聚焦语音/多模态多阶段流水线，支持 TTS/ASR 特有的 stage 编排（vocoder、talker、codec decode）和异构传输（NIXL、Mooncake），这些不在 vLLM 的设计范围。
  • Triton Inference Server (NVIDIA)：Triton 是通用模型服务平台，支持多框架后端和 BLS（Business Logic Scripting）编排，但需要用户自行组装多阶段 pipeline；SGLang-Omni 为语音/多模态场景提供开箱即用的多阶段调度、stage 生命周期管理和 OpenAI 兼容 API，集成度更高但领域更聚焦。
  • F5-TTS / CosyVoice 官方 serving：这些项目通常提供单模型的推理脚本或简单 API；SGLang-Omni 提供统一的 serving 框架，支持多模型族（Higgs、MOSS、Fish Speech、Qwen3-TTS 等）共享调度、传输和 API 基础设施。

二、架构与代码地图

SGLang-Omni 的架构自上而下可拆为五层。 1) 接入层（API / Client / Router）：对外暴露 OpenAI 兼容的 HTTP 表面（/v1/audio/speech、/v1/audio/transcriptions、多模态 chat），并把外部请求翻译成内部 StagePayload / SchedulerRequest。核心模块包括 sglang_omni.http、sglang_omni.client，以及独立的 sglang_omni_router（Rust + Python 实现的多 worker 前门，负责 health / readiness / capability discovery / 负载均衡）。 2) 调度层（Pipeline / Scheduling / Admission）：这是 SGLang-Omni 自己真正拥有的部分——多阶段拓扑编排、阶段生命周期、准入控制、阶段间背压。核心模块包括 sglang_omni.pipeline、sglang_omni.scheduling（含 omni_scheduler、engine_factory、generation_batch_policy、sglang_backend 等）、sglang_omni.admission。调度层决定「哪个 stage 在什么时候跑哪些请求」，并把请求派发给执行层。 3) 执行层（Model Runner / Engine）：把调度层的请求落成具体的前向 / 解码 / 编码动作。核心模块包括 sglang_omni.model_runner（base、model_worker、sglang_model_runner、sglang_execution、各模型特化的 runner）和 sglang_omni.models（每个模型族一个子目录，含 engine_builder、stages、request_builders、sglang_model 等）。对自回归阶段，执行层会调用 SGLang 的 runtime；对 encoder / vocoder / talker 等非 AR 阶段，则由自己的轻量循环驱动。 4) 通信与硬件抽象层（Comm / Platforms / Relay）：负责阶段间 tensor 传输与多硬件后端适配。sglang_omni.comm 提供 shared-memory、NCCL、NIXL、Mooncake 等 relay 后端（data_ref、kv_transfer、stage_io、router）；sglang_omni.platforms 做 CUDA / MPS / XPU / NPU / ROCm 的设备抽象；sglang_omni.relay 是数据面实现。 5) 工具与生态层（Config / Diagnostics / Profiler / Preprocessing / Sampling / Quantization / Vendor / Benchmarks / Playground / OmniTyper）：支撑性模块。config 管配置 schema 与解析；diagnostics / profiler 做 GPU 诊断与性能剖析；preprocessing 做音频 / 图像特征抽取；sampling 做采样与 seed 管理；quantization 做量化；vendor 是对 sglang 内部组件的兼容层；benchmarks / playground / OmniTyper 分别覆盖评测、演示 UI 与实时打字服务。 整体原则：SGLang-Omni 自己拥有 pipeline 拓扑、stage 调度、模型族集成和 API 表面；在 AR 调度与模型执行段复用 SGLang 的高性能 runtime，而不是 fork 它。

一次调用怎么流过这些模块

一次典型请求（以 /v1/audio/speech 的 TTS 为例）从客户端到音频输出的完整路径： 1) 接入：客户端通过 sglang_omni.client 或 HTTP POST /v1/audio/speech 到达 sglang_omni.http 层。HTTP router 把请求体与元数据解析成内部 StagePayload（定义在 sglang_omni/proto/request.py），并封装为 SchedulerRequest（sglang_omni/scheduling/types.py）。 2) 准入：SchedulerRequest 先经过 sglang_omni.admission（admission.py），判断当前系统负载是否接受新请求；若过载则拒绝或排队（DeferredAdmission）。 3) 调度：请求进入 sglang_omni.pipeline 定义的阶段图。OmniScheduler（sglang_omni/scheduling/omni_scheduler.py）根据拓扑决定该请求当前应进入哪个 stage（例如 preprocessing → encoder → AR → vocoder）。每个 stage 背后有一个专门的 scheduler：AR 阶段复用 SGLang 的 GenerationBatchScheduler，encoder/vocoder 阶段用轻量循环。engine_factory.py 中的 AsrEngineBuilder / TtsEngineBuilder 在启动时构造这些 scheduler 并绑定对应的 ModelRunner。 4) 执行：当请求被调度到某 stage 时，该 stage 的 ModelRunner（sglang_omni/model_runner/）接管。以 AR 阶段为例，SGLangModelRunner（sglang_model_runner.py）通过 ModelWorker（model_worker.py）调用 SGLang 的 runtime（srt.managers.scheduler）执行 prefill 或 decode；runner 通过钩子（before_prefill、post_prefill、post_decode、custom_prefill_forward）注入模型特有逻辑（如 dots.tts 的 latent recurrence、fishaudio 的 semantic token 收集）。对非 AR 阶段（如 Fun-ASR 的 encoder_service、Higgs TTS 的 vocoder_scheduler），runner 直接驱动 PyTorch / ONNX / MLX 模型。 5) 阶段间传输：当一个 stage 的输出 tensor 需要送到下一 stage 时，通过 sglang_omni.comm 的 StageIO / DataRef 抽象，由 sglang_omni.relay 选择 shared-memory、NCCL、NIXL 或 Mooncake 后端完成拷贝。comm.router 负责路由到目标 stage 的进程/设备。 6) 输出聚合：最终 stage（如 vocoder 或 aggregator）产出音频 tensor，经 SGLangOutputProcessor（sglang_backend/output_processor.py）或模型特化的 collect 函数（如 FishS2Pro 的 collect_s2pro_step_outputs）打包成 RequestOutput，通过 OutgoingMessage（scheduling/message.py）流式或整块回传给 HTTP / WebSocket 客户端。 关键数据结构：StagePayload（跨 stage 载体）、SchedulerRequest（调度单元）、ScheduleBatch（SGLang 的 batch 抽象）、ForwardBatch（SGLang 前向上下文）、GenerationBatchResult（前向结果）、RequestOutput（最终输出）、OutgoingMessage（流式回传）。关键调度点：admission 的准入判断、OmniScheduler 的 stage 选择、engine_factory 的 engine 构建、ModelRunner 的 forward 钩子、relay 的 tensor 拷贝。

扩展点

  • 新模型族（TTS/ASR/Omni）：在 sglang_omni/models/<new_model>/ 下新增子目录，至少实现 engine_builder.py（继承 AsrEngineBuilder 或 TtsEngineBuilder，定义 model_name、model_arch_override、generation_defaults、customize_server_args）、stages.py（定义阶段拓扑）、request_builders.py（定义请求数据类）、sglang_model.py（封装 HF 模型）。可参考 dots_tts、fishaudio_s2_pro、fun_asr 等已有实现。engine_builder 子类会在 scheduling/engine_factory 的注册表中通过模型名被发现（需验证自动注册机制）。
  • 新硬件后端：在 sglang_omni/platforms 新增设备抽象，在 sglang_omni/model_runner 新增对应 runner（如 audio_mlx.py、audio_torch_mps.py 对 Apple Silicon），在 pyproject_*.toml 添加对应构建配置（参考 pyproject_xpu.toml、pyproject_npu.toml）。engine_builder 中通过 current_platform 选择 attention_backend 与 runner 实现分支（如 FishS2ProEngineBuilder 的 resolve_fast_ar_attention_backend）。
  • 新 kernel / 算子融合：在模型子目录内新增 kernels/ 子目录（如 fishaudio_s2_pro/fish_speech/models/kernels/），或在 sglang_omni/models/<model>/ 下新增 fused_*.py（如 auk/fused_qk_norm_rope.py、higgs_tts/reset_kernels.py）。ModelRunner 的 forward 钩子（custom_prefill_forward、before_prefill 等）是注入自定义 kernel 的入口。对 SGLang 内部的 kernel 替换，需通过 vendor 层或 upstream 贡献。
  • 新调度策略：在 sglang_omni/scheduling 下扩展：修改 OmniScheduler（omni_scheduler.py）调整阶段调度顺序；在 generation_batch_policy.py 新增 batch policy；在 engine_factory.py 新增 engine_builder 子类并覆写 generation_defaults；在 sglang_backend/ 下新增 output_processor 处理新类型的 stage 输出。
  • 新传输后端：在 sglang_omni/comm 新增后端实现（参考 data_ref.py、stage_io.py、router.py），在 sglang_omni/relay 添加实际拷贝逻辑。comm 是控制面抽象，relay 是数据面实现。
  • 新 API 端点：在 sglang_omni/http 新增 FastAPI router，定义请求/响应模型，调用 sglang_omni.client 或直接把请求注入 pipeline。
  • 新采样策略：在 sglang_omni/sampling 扩展（参考 seed.py 的 resolve_row_seed），并在对应 ModelRunner 中调用。
  • 新量化方案：在 sglang_omni/quantization.py 扩展，或在 engine_builder 的 customize_server_args 中注入量化相关 ServerArgs。

坑

  • 1. 依赖冲突（最常见）
  • - pyproject.toml 中 sglang 的 Apple Silicon 安装需要从源码编译
  • - 注释明确说：SGLang's PyPI wheel has unconditional CUDA dependencies
  • - 解决：使用 install.sh 或手动指定 --no-deps 安装 sglang
  • 2. MLX 版本要求严格
  • - mlx>=0.32.0 是硬要求（floor enforced by SGLang's MLX runtime gate）
  • - 低于此版本会导致运行时错误
  • 3. 模型权重下载
  • - 首次运行会下载大量模型权重（数 GB）
  • - 确保 huggingface-hub 配置正确
  • - 使用 HF_HOME 环境变量控制缓存位置
  • 4. 内存限制（16GB MacBook）
  • - 大型模型（如 Qwen3-Omni）无法在 16GB 上运行
  • - 只能测试小型模型或使用 Fun-ASR 等轻量级模型
  • - 监控内存使用：export PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.0
  • 5. CUDA 代码路径
  • - 某些代码硬编码了 torch.cuda 调用
  • - 例如：sglang_omni/models/higgs_tts/ 中的 CUDA 特定操作
  • - 需要检查 current_platform.is_cuda() 条件判断
  • 6. 异步执行复杂性
  • - 多阶段管道涉及复杂的异步执行
  • - 调试时使用 asyncio.run() 而不是裸 await
  • - 注意 asyncio.create_task() 的生命周期管理
  • 7. 通信后端选择
  • - 默认可能尝试初始化 NCCL（需要 GPU）
  • - 在 CPU 环境强制使用 shared-memory 后端
  • - 检查 sglang_omni/comm/ 中的后端选择逻辑
  • 8. 测试数据依赖
  • - tests/data/ 可能包含大型测试数据
  • - 某些测试需要下载额外数据集
  • - 使用 --ignore=tests/data/ 跳过或按需下载

流程与 Review 风格

仓库没有独立的 CONTRIBUTING.md，贡献流程主要靠 .github/pull_request_template.md、AGENTS.md / CLAUDE.md 中的编码风格指引，以及 docs/README.md 的文档工作流。AGENTS.md 和 CLAUDE.md 都要求先读 .claude/skills/code-review/coding-style.md 再写代码。docs/README.md 要求：编辑 docs/ 下的 Markdown 或 RST 后必须把新页加入 index.rst 或对应 toctree，并在 PR 前跑 pre-commit run --all-files，若首轮自动修复则再跑一次。仓库根有 .pre-commit-config.yaml，说明 pre-commit 是强制卡点。README 与 docs 中未提及 CLA 或 DCO，推断为常规 GitHub fork → PR 流程，无需额外签署协议。

从近期 PR 与 Issue 看，review 偏「性能 + 正确性 + 硬件可移植性」三审。典型证据：PR #2542（XPU shared accelerator helpers off torch.cuda）、#2447（Qwen3-TTS codec decode path off torch.cuda）显示 reviewer 会专门盯 torch.cuda 硬编码并要求迁到 accelerator 抽象；Issue #2511（Release a failed batch's KV once）和 #2514（CUDA IPC copy waits alive through cancel and close）显示对资源生命周期与 cancel 路径的正确性要求很严；Issue #1754（Qwen3-TTS Optimization）27 条评论、#1967（Apple Silicon RFC）22 条评论，说明路线图类 PR 会经历多轮公开讨论。响应速度上，2026-10-03～05 的 fix PR（#2511、#2514、#2515、#2522）几乎同日合入，主干响应很快。
