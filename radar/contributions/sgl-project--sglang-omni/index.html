sgl-project/sglang-omni

候选人是资深 GPU/性能工程师，但目前无 GPU，只能使用 MacBook Air。计划重点利用其在性能分析、算子数值正确性、多后端适配、构建与测试、以及纯逻辑层（如调度器、API）的深厚经验，选择完全可在 Apple Silicon / CPU 环境下开发和验证的任务。

当前方向：SGLang-Omni 正在快速迭代，重点支持多模态（音频、音乐、视频）模型的高性能服务。近期活跃方向包括 Apple Silicon 和其他非 CUDA 后端（XPU, NPU）的支持、Full-Duplex 实时交互、性能优化（如 `torch.compile`）以及代码质量和文档的提升。对 Apple Silicon 的原生支持是一个明确的投入方向，为候选人提供了大量直接相关的贡献机会。

目标：根据 Issue #179 的分析，将调度器中 O(n) 的队列操作（如 `list.remove()`）替换为 O(1) 的数据结构（如 `dict` 或 `set`），以降低高并发下的 CPU 开销。

为什么值得长期做：调度器是服务框架的核心。优化其性能可以直接提高系统的吞吐量和效率，是展示核心系统工程能力的绝佳机会。

怎么介入：Issue #179 提出了一个明确的性能问题。虽然有一个非常陈旧的开放 PR (#180)，但它很可能已被放弃。在 Issue 中礼貌地询问并提出新的实现方案是合适的介入方式。
第一个 PR 的边界：第一个 PR 应专注于将调度器中的核心数据结构从列表替换为字典/集合，并更新相关操作，同时确保所有测试通过。
第一步：在本地代码库中找到 `sglang_omni/scheduling/` 目录下的调度器实现，并定位 Issue 中提到的 `self.running` 列表和 `_check_feedback` 函数。
