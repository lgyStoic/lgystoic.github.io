Issue #14316 · LTX-2 `_cp_plan` appears copied from LTX-1 and fails under `enable_parallelism()` (crash + one silent-correctness hazard) ↗

无人认领2 条评论更新 2026-09-07

用到的专长：分布式训练性能、Context Parallelism、Transformer 底层架构

目标：修正 `LTX2VideoTransformer3DModel._cp_plan`，确保视频和音频流（包括 timestep 和 RoPE 模块）在 Context Parallelism 下被正确 sharding，解决 crash 和双流交叉注意力计算的静默错误。

为什么值得长期做：修复 Context Parallelism (CP) 在多模态（音视频双流）Transformer 中的分片逻辑，直接关系到大模型分布式推理/训练的正确性。这是深入 Diffusers 底层并行架构和注意力机制切分的绝佳切入点，能展现候选人在分布式系统上的深厚功底。

怎么介入：Issue 处于 open 状态，无 assignee，无 linked PR。维护者尚未回复，非常适合直接认领并提交高质量的修复 PR。
第一个 PR 的边界：仅修改 `LTX2VideoTransformer3DModel._cp_plan` 及相关的并行配置逻辑，不涉及模型权重的改变。
第一步：运行 Issue 中提供的 `repro.py` 脚本复现 crash 和静默错误，分析 LTX-2 的双流注意力机制对 QKV 分片维度的具体要求。
认领留言（英文，可直接贴到 Issue）
Hi! I'd like to help fix this CP plan issue for LTX-2. I understand that the dual-stream architecture requires sharding both video and audio streams, as well as the per-token timesteps and RoPE modules to avoid the silent correctness hazard in cross-attention. I will use the provided `repro.py` to ensure the multi-rank output mathematically matches the single-rank baseline. I can submit a PR within 2-3 days. Let me know if there are any specific collective communication patterns I should be aware of for the v2a attention!
大致实施方案
  • 定位 `src/diffusers/models/transformers/transformer_ltx2.py` 中的 `_cp_plan` 属性。
  • 将 `timestep` 加入分片计划，因为它在 LTX-2 中是 per-token 的 `(B, num_video_tokens)`。
  • 将音频流相关的张量（`audio_hidden_states`, `audio_timestep`, `audio_encoder_hidden_states`, `audio_encoder_attention_mask`, `audio_proj_out`）加入分片计划。
  • 将缺失的 3 个 RoPE 模块（`audio_rope`, `cross_attn_rope`, `cross_attn_audio_rope`）加入分片计划。
  • 检查双流交叉注意力（如 v2a，Q=audio, KV=video）在分片后的逻辑，确保现有的 CP 抽象能正确处理不对称的 QKV 分片，避免静默错误。

验收方式
  • 使用 Issue 提供的 `repro.py` 脚本，确保在 `--mask` 和 `--fixed` 模式下不再 crash。
  • 验证多 rank 分布式执行的输出张量与单 rank 串行执行的输出张量在数值上完全一致（无静默错误）。

Suggestion for speeding up `index_for_timestep` by removing sequential `nonzero()` calls in samplers

Issue #9417 · Suggestion for speeding up `index_for_timestep` by removing sequential `nonzero()` calls in samplers ↗

无人认领11 条评论help wantedwipcontributions-welcome更新 2025-02-08

用到的专长：PyTorch 算子优化、消除 CPU-GPU 同步、性能 Profiling

目标：将 `FlowMatchEulerDiscreteScheduler`（及其他潜在调度器）中的 `nonzero()` 查找替换为无同步的数学计算或更高效的搜索算子，提升大 batch size 下的执行速度。

为什么值得长期做：消除调度器中的 CPU-GPU 同步或慢速算子（如 `nonzero()`）是提升扩散模型推理和训练吞吐量的经典性能优化。这能直接改善用户的开箱体验，并建立候选人在 PyTorch 算子级优化领域的信誉。

怎么介入：Issue 处于 open 状态，无 assignee，无 linked PR。这是一个社区提出的优化建议，非常适合性能工程师接手并用更严谨的方式（如 searchsorted）实现。
第一个 PR 的边界：优化 `FlowMatchEulerDiscreteScheduler` 及其他相关调度器中的 `index_for_timestep` 方法，确保数值等价并提升性能。
第一步：编写一个微基准测试（micro-benchmark），对比原始 `nonzero()` 方法和 Issue 中提出的数学计算方法在不同 batch size 和 device（CPU/CUDA）下的耗时与同步开销。
认领留言（英文，可直接贴到 Issue）
Hi! I'd love to implement this performance optimization. Replacing `nonzero()` is a great catch to avoid potential device synchronization and graph breaks. Before applying the linear interpolation math suggested, I will verify if it holds for non-linear timestep schedules. If not, I plan to use `torch.searchsorted`, which is mathematically safe for monotonic schedules and still much faster than `nonzero()`. I'll profile the changes and submit a PR with the speedup metrics within a couple of days. Does this approach sound good?
大致实施方案
  • 定位 `src/diffusers/schedulers/scheduling_flow_match_euler_discrete.py` 中的 `index_for_timestep` 方法。
  • 审查 Issue 中提出的线性插值逻辑。由于某些调度器的 timesteps 可能不是线性等距的，直接使用线性插值可能导致索引错误。
  • 如果线性插值不安全，考虑使用 `torch.searchsorted` 替代 `nonzero()`。`searchsorted` 在 GPU 上执行更快且不会触发隐式的 CPU-GPU 同步（如 `len(indices)` 导致的同步）。
  • 替换实现，并处理 `begin_index` 相关的逻辑，确保向后兼容。
  • 检查其他调度器（如 `EulerDiscreteScheduler` 等）是否存在类似的 `nonzero()` 性能瓶颈，并一并优化。
可能涉及的目录或文件
  • src/diffusers/schedulers/scheduling_flow_match_euler_discrete.py
  • src/diffusers/schedulers/
验收方式
  • 运行 `pytest tests/schedulers/` 确保所有调度器测试通过，索引结果与原来完全一致。
  • 运行微基准测试，使用 PyTorch Profiler 证明在 CUDA 上的耗时显著降低，且消除了 CPU-GPU 同步等待。
开工前问题与风险

向维护者确认

  • 考虑到某些调度器的 timesteps 序列可能是非线性的，直接使用 Issue 中建议的线性插值公式是否安全？如果为了数学上的绝对安全，我使用 `torch.searchsorted` 来替代 `nonzero()` 是否更符合库的设计原则？

风险

  • 直接采用 Issue 提议的线性插值可能在非线性 schedule 下返回错误的索引，导致生成质量下降。必须确保替换方案在所有 schedule 类型下具有绝对的数学等价性。
