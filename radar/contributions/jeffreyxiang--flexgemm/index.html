JeffreyXiang/FlexGEMM

FlexGEMM 是一个基于 Triton 的高性能稀疏卷积 GEMM 后端，核心挑战在于 3D 稀疏张量的内存访问模式优化与算子融合。候选人作为资深 GPU kernel / 训练性能工程师，精通 CUDA 和 Triton，完美契合该项目从 CUDA 扩展向纯 Triton 架构演进（FlexGEMM 2.0）的战略方向，能够直接解决底层哈希表优化、新架构（Blackwell）适配及 Triton 运行时缓存等硬核问题。

当前方向：项目正处于向 FlexGEMM 2.0 演进的关键期，核心目标是实现纯 Triton 替代（消除 CUDA 编译依赖）、底层 Neighbor Map 与 Index GEMM 的完全解耦，以及提升在最新 GPU 架构（如 RTX 50 系列）上的稳定性。

FlexGEMM 2.0：改进计划 (Roadmap)

Issue #23 · FlexGEMM 2.0：改进计划 (Roadmap) ↗

无人认领0 条评论更新 2026-05-11

用到的专长：发挥候选人在 CUDA kernel 优化和底层数据结构设计上的专长。

目标：改进 CUDA hashmap 为基于坐标向量的哈希，解除对 W/H/D 边界的依赖，支持至少 4D（含 batch）以上的坐标。

为什么值得长期做：重构核心的 CUDA Hashmap 或解耦 Neighbor Map 是 FlexGEMM 2.0 的基石，直接决定了库的泛化能力和未来维护成本。完成此任务将确立你在项目核心架构设计上的话语权。

怎么介入：Issue 仍开放，无 assignee，无 linked PR。维护者明确列出了子任务，非常欢迎社区参与。
第一个 PR 的边界：仅包含 CUDA hashmap 的向量化哈希重构及对应的 Python 绑定和单元测试。
第一步：阅读 `dev/all_triton` 分支中 Triton 版本的 `_vec_hash_32bit` 实现，并定位当前 CUDA hashmap 的源码位置。
认领留言（英文，可直接贴到 Issue）
Hi @JeffreyXiang, I'm very interested in the FlexGEMM 2.0 roadmap, specifically the 'CUDA Hashmap Improvement' subtask. I have extensive experience in CUDA kernel optimization and would like to implement the vector-based hash (similar to the Triton `_vec_hash_32bit` approach) to support >=4D coordinates and remove the W/H/D boundary restrictions. I plan to draft a PR within a week. Should I target the `main` branch or `dev/all_triton` for this specific CUDA C++ change?
大致实施方案
  • 在 Issue #23 下留言，明确认领『CUDA Hashmap 改进』子任务。
  • 分析当前 CUDA hashmap 的实现，移除硬编码的 `[M, 4]` 坐标限制和 `b*W*H*D + x*H*D + y*D + z` 的平铺逻辑。
  • 参考 Triton 的 `_vec_hash_32bit` 算法，在 CUDA 中实现支持任意维度（≤8D）和任意坐标范围的向量哈希函数。
  • 修改相关的 CUDA kernel 接口，使其接受动态维度的坐标输入。
  • 在 `tests/` 目录下编写针对高维（>4D）和无界坐标的单元测试，对比重构前后的正确性与性能。
可能涉及的目录或文件
  • flex_gemm/kernels/cuda/spconv/
验收方式
  • 编译 CUDA extension 成功。
  • 运行现有的 spconv 测试通过。
  • 新增的高维坐标 hashmap 测试通过，且性能不低于旧版本。
开工前问题与风险

向维护者确认

  • 对于 CUDA hashmap 的改进，是否需要保持与旧版完全一致的 Python API？
  • 是否有特定的 benchmark 脚本用于评估 hashmap 的性能退化？

风险

  • 向量化哈希可能引入额外的寄存器压力或计算开销，导致在标准 3D 场景下性能微降。
  • CUDA 模板元编程处理动态维度可能增加编译时间。
任务 2优先 · Medium · 需要按小时租用 RTX 50 系列 GPU (如 5090) 进行复现和验证 · 1-2 个晚上（假设能顺利租到 50 系 GPU）

CUDA driver error: device not ready on RTX 50-series (Blackwell, sm_120)

用到的专长：利用候选人在 CUDA 硬件架构（特别是 warp 调度和同步机制）方面的深厚经验。

目标：修复在 RTX 50 系列 (Blackwell) GPU 上运行 TRELLIS.2 时出现的 `CUDA driver error: device not ready` 崩溃问题。

为什么值得长期做：新一代 GPU 架构的适配是高性能算子库的生命线。解决 Blackwell 上的隐式同步问题能展现你对 CUDA 硬件执行模型的深刻理解，建立维护者对你底层调试能力的信任。

怎么介入：Issue 刚提出不久，无 assignee，无 linked PR。明确的硬件兼容性 Bug，急需修复。
第一个 PR 的边界：在 CUDA kernel 中添加缺失的 warp 同步原语，修复 Blackwell 架构上的运行时崩溃。
第一步：审查 `flex_gemm/kernels/cuda/spconv/` 下的 neighbor-map 构建和 reduction kernel，寻找缺失 `__syncwarp()` 或存在 warp 级竞争条件的代码。
认领留言（英文，可直接贴到 Issue）

  • 在可疑的 reduction 步骤或 warp 协作代码后插入 `__syncwarp()`，或使用更安全的 warp 原语（如 `__shfl_down_sync`）。
  • 重新编译 FlexGEMM，运行 TRELLIS.2 的 `shape_slat_decoder` 前向传播，确认崩溃不再发生。
