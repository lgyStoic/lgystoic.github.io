一、项目定位

FlexGEMM 是一个专为 3D 稀疏卷积（Sparse Convolutions）设计的高性能、跨平台底层算子库。其核心架构采用了「混合编程」范式：利用自定义 CUDA/C++ 扩展（如 hash.cu, subm_neighbor_map.cu）处理高度不规则的稀疏哈希映射和邻居索引，同时利用 Triton (flex_gemm/kernels/triton) 实现极致优化的 GEMM 计算。项目实现了 Explicit、Implicit 和 Masked Implicit 三种算法变体，并支持 Split-K 并行优化。根据 README，它在 FP16 和 TF32 精度下比现有的 SOTA 方案快约 2 倍，且已被微软 TRELLIS.2 等 3D 生成模型项目采用。 对于你（资深 GPU kernel 工程师）而言，这个库的切入价值极高，代码库集中在 flex_gemm/kernels（近期有 49 个 commit 热点），涉及底层同步（如 __syncwarp 修复）、指针计算（int64 转换）以及跨硬件适配（近期合并了 ROCm/HIP 支持）。 硬约束警告：由于你目前只有 MacBook Air (Apple Silicon)，你无法在本地完成该项目的构建与测试。setup.py 强依赖 torch.utils.cpp_extension.CUDAExtension 编译 .cu 文件，且 Triton 算子无法在 CPU/MPS 上运行。你的开发流必须是：在 Mac 上阅读源码/编写 Python 侧逻辑，然后依赖 Colab T4 实例进行编译和验证。需要注意的是，README 的 Benchmark 是在 A100 上测的（支持 TF32），你在 T4（Turing 架构，不支持 TF32，且 Triton 性能表现不同）上只能做功能性验证，无法复现其极致的性能数据。

解决什么问题、给谁用

3D 稀疏张量（如体素化点云）具有高度不规则的稀疏模式，传统的稀疏卷积实现在内存访问和计算单元利用率上存在瓶颈。FlexGEMM 旨在解决稀疏卷积在训练和推理时的高吞吐需求，同时避免显存开销的增加。

3D 计算机视觉研究员、自动驾驶（LiDAR 点云处理）工程师、以及 3D 生成式 AI（如 3D 扩散模型、体素网络）的底层性能优化工程师。典型场景包括高分辨率体素化点云处理和大规模 3D 神经网络的训练与推理。

同类项目与差别

  • spconv：业界最老牌、最常用的稀疏卷积库，主要基于 CUDA/C++ 实现。FlexGEMM 将其作为主要 Baseline，声称在训练吞吐量上持续超越它。
  • torchsparse：MIT 开发的高性能稀疏卷积库。FlexGEMM 在 README 的 Benchmark 中同样将其作为对比对象，并展示了更高的 FP16/TF32 训练速度。
  • fvdb：深度学习框架中的稀疏体积数据结构库。FlexGEMM 宣称在速度上超越了它，并提供更高效的数据格式支持。

二、架构与代码地图

FlexGEMM 的架构设计采用了经典的「控制流与数据流分离」及「混合编程」范式，将高度不规则的稀疏索引计算与高度规则的稠密矩阵乘法（GEMM）解耦。对于只有 Mac 的你来说，这种分层极其友好：你可以完全在本地阅读和修改 Python/Triton 层，只需将 CUDA 层的编译和最终的端到端测试放到 Colab T4 上。 1. Python 接口与调度层 (flex_gemm/ops)：这是 PyTorch 用户的直接入口。通过 torch.autograd.Function 封装前向与反向传播逻辑。该层负责输入张量的校验、哈希表内存的初始化（根据体积动态选择 uint32/uint64），以及根据用户配置（如 Algorithm.MASKED_IMPLICIT_GEMM_SPLITK）分发到具体的底层 Kernel。这部分是纯 Python，完全可以在 Mac 上开发与调试。 2. 稀疏索引与内存层 (CUDA C++, flex_gemm/kernels/cuda)：这是处理 3D 稀疏卷积「不规则性」的核心。包含空间哈希表 (hash.cu)、Z-order/Hilbert 空间序列化 (serialize/api.cu) 和邻居映射 (subm_neighbor_map.cu)。由于 3D 点云的稀疏性，必须先通过哈希表找到输入输出体素的对应关系。注意：这部分强依赖 nvcc 和 PyTorch C++ Extension，你的 Mac 无法本地编译，必须依赖 Colab T4 环境。 3. 高性能计算层 (Triton, flex_gemm/kernels/triton)：这是 FlexGEMM 性能霸榜的关键。在 CUDA 层准备好 neighbor_map 后，Triton 层接管实际的乘加计算。实现了 Implicit GEMM、Masked Implicit GEMM 以及 Split-K 变体。Triton 代码本质上是 Python AST，你可以在 Mac 上无障碍阅读其 Block 划分、内存 Coalescing 和 Shared Memory 调度逻辑，但运行验证需上 GPU。 4. 构建与跨平台适配层 (setup.py, autotuner.py)：负责处理 CUDA/ROCm 的编译标志（如近期加入的 --offload-arch 和 IS_HIP_EXTENSION），以及 Triton Kernel 的 Autotune 缓存合并。

一次调用怎么流过这些模块

以一次 sparse_submanifold_conv3d 的前向与反向传播为例，完整的数据流如下： 1. 入口与预处理 (Mac 可调试)：用户在 Python 侧传入稀疏特征 feats (N, C)、坐标 coords (N, 4)、空间形状 shape 以及权重 weight。flex_gemm/ops/spconv/submanifold_conv3d.py 中的 Autograd Function 接收这些输入。首先调用 flex_gemm.ops.utils.init_hashmap，根据空间体积（N*W*H*D）决定分配 uint32 还是 uint64 的哈希表张量。 2. 构建哈希与邻居映射 (CUDA 层，需 T4 验证)：Python 侧通过 pybind11 调用 flex_gemm.kernels.cuda。首先执行 hashmap_insert_3d，将所有输入坐标插入哈希表。接着，启动 subm_neighbor_map.cu Kernel。该 Kernel 遍历每个输入点，根据卷积核大小（如 3x3x3 的 27 个偏移量）计算其邻居坐标，并通过 hashmap_lookup_3d 查找邻居在 feats 中的实际内存索引，最终生成 neighbor_map（记录输入到输出的索引映射）。 3. 算法分发与 Triton 计算 (Triton 层)：根据用户通过 set_algorithm 设置的策略（如 MASKED_IMPLICIT_GEMM_SPLITK），Python 调度层选择对应的 Triton Kernel（例如 sparse_conv_masked_implicit_gemm_splitk.py）。Triton Kernel 启动后，利用 neighbor_map 作为指针偏移，直接从 feats 中 Gather 数据，与 weight 进行 Block 级别的矩阵乘法（GEMM）。如果启用了 Split-K，Triton 会在 K 维度上切分计算，最后通过 Atomic Add 或额外的 Reduction Kernel 将部分和累加到 out_feats。 4. 缓存与反向传播：前向计算完成后，返回 out_feats 和 neighbor_cache。在训练场景下，当调用 out_feats.backward() 时，Autograd 会触发反向逻辑。此时不再重新计算哈希表和邻居映射，而是直接复用 neighbor_cache，并调用对应的 Triton _bwd Kernels 计算 grad_weight 和 grad_feats。这种缓存机制极大提升了训练吞吐量。

三、本地跑起来（没有 GPU 的 Mac）

安装

  1. git clone https://github.com/JeffreyXiang/FlexGEMM.git
  2. cd FlexGEMM
  3. # [Mac 本地环境] 由于 setup.py 强依赖 CUDAExtension，Mac 上直接 pip install . 会报错。建议仅安装 Python 依赖用于阅读和编写代码：
  4. pip install torch>=2.4.0 filelock
  5. export PYTHONPATH=$(pwd):$PYTHONPATH # 将项目加入环境变量，以便在 Mac 上进行 Python 层的静态分析和开发
  6. # [Colab T4 验证环境] 必须在带有 GPU 的 Linux 环境下执行完整安装：
  7. pip install . --no-build-isolation

哪些路径能真跑

在 Mac (CPU/MPS) 上，你只能执行 flex_gemm/ops/ 下的纯 Python 调度逻辑（例如 utils.py 中的 init_hashmap 动态选择 uint32/uint64）。虽然 api.cu 源码中存在 cpu::z_order_encode 的分支，但由于 setup.py 强制使用 CUDAExtension 编译，Mac 上无法构建出底层 .so 文件，因此任何涉及 flex_gemm.kernels 的调用都会直接报错。所有实际的计算（CUDA 哈希表构建、Triton GEMM 乘加）必须在 Colab T4 上运行验证。

最小可运行

  1. python examples/submconv.py
  2. python examples/spconv.py
  3. python tests/spconv/fwd.py
  4. python tests/submconv/bwd.py

测试

测试用例集中在 tests/ 目录下，按模块划分为 spconv/, submconv/, grid_sample.py, hashmap.py, serialize.py。项目没有使用 pytest 配置文件，直接通过原生的 Python 脚本运行（如 python tests/hashmap.py）。由于核心算子全在 GPU 上，没有任何纯 CPU 测试子集，所有测试必须在 Colab T4 上运行。单个脚本的耗时通常在几秒到几十秒不等（主要取决于 Triton 首次运行时的 Autotune 编译时间）。

调试

  • Python 层断点：在 flex_gemm/ops/spconv/sparse_conv3d.py 打断点，观察 coords 的形状校验和 Algorithm（如 MASKED_IMPLICIT_GEMM_SPLITK）的分发逻辑。
  • Triton 模拟执行：在 Colab 上设置环境变量 TRITON_INTERPRET=1，可以在 CPU 上模拟执行 Triton kernel，用于排查显存越界或逻辑错误（执行极慢，仅限极小数据量）。
  • Autotune 缓存清理：Triton 的 autotune 结果会缓存在 ~/.flex_gemm/autotune_cache.json（见 setup.py 逻辑）。如果你修改了 Triton kernel 的配置，务必删除该文件以强制重新 tune，否则修改可能不生效。
  • CUDA 编译排错：如果修改了 .cu 文件，在 Colab 上重新安装时需加上 --no-build-isolation。若遇到 ABI 问题，可检查 setup.py 中的 _GLIBCXX_USE_CXX11_ABI 设置。

坑

  • T4 性能陷阱：README 的 Benchmark 是在 A100 上测的，且依赖 TF32 精度。Colab 的 T4 是 Turing 架构，不支持 TF32（最近 commit c8939d6 也提到了精度支持问题），且 Triton 在老架构上性能表现一般。在 T4 上只能做功能正确性验证，绝对无法复现 README 中的 2 倍加速。
  • 指针溢出与类型转换：处理大规模点云时，注意 utils.py 中 VOL < 2**32 的判断。最近的 commit (c0a6ab0) 刚修复了稀疏卷积 kernel 中转换为 int64 的指针计算问题，修改相关逻辑时极易踩坑。
  • 跨硬件同步原语：最近的 commit (778e1db) 为兼容 ROCm/HIP，修改了 __syncwarp 的逻辑。如果你在 CUDA 层添加新的 warp 级规约，必须注意 AMD 架构的兼容性，不能盲目使用纯 CUDA 的同步指令。
