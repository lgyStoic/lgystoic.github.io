[dev/all_triton branch] Inconsistent autotune cache keys for kernels wrapped with `@triton.heuristics`

Issue #26 · [dev/all_triton branch] Inconsistent autotune cache keys for kernels wrapped with `@triton.heuristics` ↗

无人认领0 条评论更新 2026-05-09

用到的专长：Triton 编译期机制与 Python 元编程

目标：修复 `_get_function_cache_key`，使其能正确穿透 `@triton.heuristics` 装饰器，获取底层 JITFunction 的真实 `__module__`，从而生成一致的 cache key。

为什么值得长期做：修复 autotuner 缓存机制是保证 Triton 算子库性能稳定性和加载速度的关键，能展现对 Triton 编译期机制的深入理解。

怎么介入：Issue 开放且无 assignee，维护者明确指出了 bug 根因，可直接认领并快速修复。
第一个 PR 的边界：仅修改 `autotuner.py` 中的 cache key 生成逻辑并添加对应的轻量级测试。
第一步：检查 `flex_gemm/utils/autotuner.py` 中的 `_get_function_cache_key` 实现逻辑。
认领留言（英文，可直接贴到 Issue）

大致实施方案
  • 在 `_get_function_cache_key` 中增加对 `triton.runtime.autotuner.Heuristics` 对象的类型判断。
  • 如果是 Heuristics 对象，通过其内部属性（如 `.fn`）递归解包，获取底层的 `JITFunction`。
  • 提取正确的 `__module__` 和 `__name__` 以生成一致的 cache key。
  • 编写单元测试，在 CPU 上模拟带有和不带有 `@triton.heuristics` 的空 Triton kernel，断言生成的 cache key 命名空间一致。
可能涉及的目录或文件

验收方式
  • 在 CPU 环境下运行 pytest，验证带有 heuristics 的 kernel 生成的 cache key 包含 `flex_gemm.kernels.triton` 而不是 `triton.runtime.autotuner`。

FlexGEMM 2.0：改进计划 (Roadmap) - 核心架构解耦

目标：重构 `SubMConvNeighborCache`，使其仅持有 `neighbor_map`，并将 Index GEMM 逻辑与 forward/backward 完全解耦。

为什么值得长期做：这是 FlexGEMM 2.0 架构升级的核心，直接决定了未来支持更多稀疏算子（如 Strided Conv, Pooling）的扩展性，是成为核心贡献者的绝佳机会。

怎么介入：Roadmap 核心重构项，影响深远，需先与维护者对齐设计细节再动手。
第一个 PR 的边界：纯 Python 层的类结构与函数路由重构，不涉及底层 kernel 的修改。
第一步：梳理当前 `SubMConvNeighborCache` 中与 GEMM 强耦合的属性（如 `gray_code`, `sorted_idx` 等）。
认领留言（英文，可直接贴到 Issue）

Before diving into the code, should we cache the derived tensors (like `gray_code`) in a context object for the backward pass, or recompute them? I can draft a PR for the Python logic first.
大致实施方案
  • 在 `dev/all_triton` 分支上，将 `SubMConvNeighborCache` 瘦身，移除 GEMM 相关的中间缓存生成逻辑。
  • 创建独立的 `index_gemm` 接口，接收 `feats_in`, `neighbor_map`, `weight`，并在内部根据 `algorithm` 派生所需的缓存。
  • 重构 forward/backward 逻辑，使 symmetric kernel 的 backward 直接复用 `flip(neighbor_map)` 和 `index_gemm`，消除独立的 backward 函数。
  • 编写纯 CPU 的 mock 测试，验证解耦后的路由逻辑和缓存生成逻辑是否正确。

向维护者确认
