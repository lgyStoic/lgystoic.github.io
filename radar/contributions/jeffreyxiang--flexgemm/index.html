补全 CPU Fallback 算子 (Issue #30)

Issue #30 · Feature Proposal: CPU fallbacks for CUDA kernels (low VRAM support) ↗

目标：实现 `hashmap_build_sparse_conv_neighbour_map` 和 `hashmap_build_submanifold_conv_neighbour_map` 的 CPU 版本，并确保与 CUDA 版本结果一致。

为什么值得长期做：实现 CPU fallback 能极大降低项目的使用门槛（尤其对于端侧和低显存设备），这与候选人端侧部署的经验高度契合，是接手核心算子调度的绝佳切入点。

第一步：阅读 PR #29 的代码，了解现有的 CPU fallback 架构和集成方式。
大致实施方案
  • 在 PR #29 的基础上，定位 `hashmap_build_sparse_conv_neighbour_map` 和 `hashmap_build_submanifold_conv_neighbour_map` 的 CUDA 实现逻辑。
  • 使用 PyTorch 原生 CPU 操作（如 `torch.unique`, `torch.isin`, 循环或向量化操作）等价实现这两个函数。
  • 在 Python 侧的调度逻辑中，增加当 `device.type == 'cpu'` 时路由到新实现的 CPU 函数的逻辑。
  • 编写单元测试，构造随机的稀疏坐标输入，断言 CPU 输出与预期的 neighbor map 一致。
可能涉及的目录或文件
  • flex_gemm/ops/spconv.py
  • 需先定位 (CPU fallback 具体文件)
验收方式
  • 在纯 CPU 环境下运行新增的单元测试，确保 `hashmap_build_sparse_conv_neighbour_map` 和 `hashmap_build_submanifold_conv_neighbour_map` 的输出正确无误。

修复 Triton Autotune 缓存 Key 不一致问题 (Issue #26)

Issue #26 · [dev/all_triton branch] Inconsistent autotune cache keys for kernels wrapped with `@triton.heuristics` ↗

目标：修改 `flex_gemm/utils/autotuner.py`，使得被 `@triton.heuristics` 包装的 kernel 也能生成正确的 `flex_gemm.kernels...` 命名空间的 cache key。

为什么值得长期做：Autotuner 是 AI Infra 的核心组件。修复缓存机制可以深入理解 Triton 的编译与缓存生命周期，为后续优化 Triton 算子打下基础。

第一步：查看 `flex_gemm/utils/autotuner.py` 中 `_get_function_cache_key` 的实现。
大致实施方案
  • 定位 `flex_gemm/utils/autotuner.py` 的 `_get_function_cache_key` 函数。
  • 增加对传入 `fn` 类型的判断：如果 `fn` 是 `triton.runtime.autotuner.Heuristics` 实例，则提取其底层的 `fn`（通常是 `fn.fn`）来获取 `__module__` 和 `__name__`。
  • 确保修改后，无论是否被 `@triton.heuristics` 包装，提取到的 `module` 都是原始定义的模块（如 `flex_gemm.kernels.triton.spconv...`）。
  • 运行现有的 Triton 测试，检查生成的 `autotune_cache.json` 中的 key 是否符合预期。
可能涉及的目录或文件
  • flex_gemm/utils/autotuner.py
  • autotune_cache.json
验收方式
  • 运行包含 `@triton.heuristics` 包装的 kernel 的测试脚本，检查生成的 `autotune_cache.json`，确认不再出现 `triton.runtime.autotuner.<kernel_name>` 格式的 key。
开工前问题与风险

向维护者确认

  • 除了 `@triton.heuristics`，项目中是否还有其他 Triton 装饰器（如 `@triton.jit` 的特定用法）可能导致类似问题，需要一并处理？

风险

  • Triton 内部 API（如 `Heuristics` 对象的属性）可能在不同 Triton 版本间有差异，需要确保兼容 Triton ≥ 3.2.0。

Issue #23 · FlexGEMM 2.0：改进计划 (Roadmap) ↗

为什么值得长期做：推动 FlexGEMM 2.0 的核心重构，消除 CUDA 依赖，实现纯 Triton 化。这直接切中 AI Infra 的演进方向，是成为核心维护者的必经之路。

第一步：对比 `main` 分支的 CUDA 接口和 `dev/all_triton` 分支的 Triton 接口返回值。
大致实施方案

  • 定位 `neighbor_map_post_process_for_masked_implicit_gemm_1` 的 Triton 实现。
  • 分析 CUDA 路径返回的第 5 个值 `valid_signal_seg` 的计算逻辑。
  • 在 Triton 路径中补充计算并返回 `valid_signal_seg`，使返回值数量和语义与 CUDA 路径完全一致。
  • 修改 `SubMConvNeighborCache`，移除针对 Triton 和 CUDA 返回值数量不同的 `if-else` 分支。
  • 运行 `tests/triton_neighbor_cache.py` 等测试确保逻辑正确。

验收方式
  • 运行 `tests/triton_neighbor_cache.py` 和 `tests/triton_spconv.py`，确保所有测试通过，且代码中不再有针对返回参数数量的条件分支。

Neighbor Map 与 Index GEMM 解耦重构 (Issue #23)

Issue #23 · FlexGEMM 2.0：改进计划 (Roadmap) ↗

目标：重构 `SubMConvNeighborCache`，使其仅持有 `neighbor_map`，并将 GEMM 算法所需的中间缓存派生逻辑下放到具体的 GEMM 算法实现中。

为什么值得长期做：架构级重构，涉及核心算子的抽象与解耦。完成此任务将深刻理解稀疏卷积的底层数学模型，是掌控整个项目架构的关键。

第一步：阅读 Issue #23 中关于“统一坐标模型”和“接口层设计”的描述，梳理当前 `SubMConvNeighborCache` 的属性。
大致实施方案
  • 审查 `SubMConvNeighborCache` 类，识别出哪些属性是特定 GEMM 算法（如 `gray_code`, `sorted_idx`）专用的。
  • 将这些专用属性的计算逻辑从 Neighbor Map 构建阶段剥离。
  • 在 Index GEMM 的调度层（或具体的 forward/backward 函数中），增加从基础 `neighbor_map` 动态派生这些缓存的逻辑。
  • 统一 symmetric 和 non-symmetric kernel 的接口，使得 backward 统一通过传入 backward neighbor map（如 `flip(neighbor_map, dim=1)`）来实现，移除独立的 backward 函数。
  • 确保所有现有的单元测试（特别是 `tests/spconv_fwd.py` 等）在重构后依然通过。
可能涉及的目录或文件
  • flex_gemm/ops/spconv.py
  • 需先定位 (Index GEMM 调度文件)
验收方式
  • 运行 `tests/` 目录下的所有稀疏卷积测试，确保重构前后前向和反向传播的数值结果完全一致。
开工前问题与风险

向维护者确认

  • 解耦后，中间缓存的生命周期将由谁管理？是否需要引入一个新的 Context 对象来避免在 forward 和 backward 之间重复计算这些缓存？

风险

  • 重构涉及核心调度逻辑，容易破坏现有的 autograd 连通性或引入显存泄漏，需仔细处理 PyTorch 的 `ctx.save_for_backward`。
