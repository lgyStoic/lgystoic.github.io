JeffreyXiang/FlexGEMM

FlexGEMM 是一个基于 Triton 的高性能稀疏卷积后端。虽然候选人目前没有 GPU，但该项目正在向纯 Triton 架构演进（`dev/all_triton` 分支），且包含大量纯逻辑层的重构与 CPU Fallback 需求。候选人可以利用 Triton 解释器模式（`TRITON_INTERPRET=1`）在 CPU 上进行开发和验证，发挥在 PyTorch 内核、Triton 编译期问题及架构设计上的专长。

当前方向：项目正处于 2.0 版本的重大重构期，核心方向是：1) 合并 `dev/all_triton` 分支，实现纯 Triton 替代以摆脱 CUDA 编译依赖；2) 底层架构重构，将 Neighbor Map 与 Index GEMM 完全解耦；3) 增强跨平台与低显存设备的兼容性（如 CPU fallback）。

  • Triton 相关的修改可以通过设置 `TRITON_INTERPRET=1` 在 CPU 上进行初步的逻辑验证。

Decouple Neighbor Map and Index GEMM in `SubMConvNeighborCache`

Issue #23 · FlexGEMM 2.0：改进计划 (Roadmap) ↗

无人认领0 条评论更新 2026-05-11

用到的专长：深度学习框架底层架构设计与 PyTorch 算子融合逻辑。

目标：重构 `SubMConvNeighborCache`，使其仅持有 `neighbor_map`，并将 GEMM 算法所需的中间缓存（如 `gray_code`, `sorted_idx`）的派生逻辑下放到具体的 GEMM 算法层。

为什么值得长期做：这是 2.0 架构重构的核心。解耦后将极大简化代码库，使得后续添加新算法或新硬件后端变得更加容易，是成为核心维护者的关键战役。

怎么介入：Roadmap 核心重构任务，需先沟通确认目标分支和设计细节。
第一个 PR 的边界：第一步仅重构 `SubMConvNeighborCache` 的数据结构和 `index_gemm` 的接口签名，不改变底层 kernel 实现。
第一步：梳理 `SubMConvNeighborCache` 当前的属性，区分哪些是纯 neighbor map 属性，哪些是特定 GEMM 算法需要的。

大致实施方案
  • 定义统一的 `index_gemm` 接口，接收 `feats_in`, `neighbor_map`, `weight` 和 `algorithm` 参数。
