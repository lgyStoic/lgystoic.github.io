一、项目定位

FlexGEMM 是一个专为 3D 稀疏卷积设计的高性能底层后端库，其核心架构采用了「混合编程模型」：控制流、哈希表构建与稀疏邻居映射（Neighbor Mapping）由高度优化的定制 CUDA/HIP C++ 算子完成，而核心的矩阵乘法（GEMM）计算则完全基于 OpenAI Triton 实现。项目实现了显式（Explicit）、隐式（Implicit）以及掩码隐式（Masked Implicit）等多种稀疏卷积算法变体，并支持 Split-K 并行优化，旨在解决 3D 体素化神经网络中高度不规则稀疏模式带来的计算瓶颈。 对于你（资深 GPU kernel 工程师）而言，这个项目非常契合你的技术栈（Triton、CUDA、算子融合）。但必须严正警告你的硬件约束：根据 setup.py 源码，该项目强依赖 torch.utils.cpp_extension.CUDAExtension，并硬编码了大量 .cu 源码（如 hash.cu, subm_neighbor_map.cu），且完全没有提供 CPU 或 Apple Silicon 的 Fallback 实现。这意味着你无法在 MacBook Air 上完成编译和本地运行。你的切入策略只能是：在 Mac 上静态阅读 flex_gemm/kernels/triton/ 下的 Triton 源码和 flex_gemm/kernels/cuda/ 下的 CUDA 源码，分析其 Masked Implicit GEMM 与 Split-K 的分块逻辑；随后将代码推送到 Colab T4 实例上进行编译和 tests/ 目录的单元测试。需要注意的是，README 中的性能基准是在 A100（支持 TF32/FP16 硬件加速）上测得的，Colab 的 T4（Turing 架构，不支持 TF32）只能用于功能验证，无法复现其极致性能。

解决什么问题、给谁用

3D 点云和体素数据具有极高的空间稀疏性，传统的密集卷积（Dense Convolution）会带来不可接受的内存和算力浪费。现有的稀疏卷积库在处理高度不规则的稀疏模式时，往往受限于手写的 CUDA 算子，难以充分利用最新 GPU 架构的 Tensor Core 算力，且跨平台（如 AMD ROCm）移植成本极高。

3D 计算机视觉研究员、自动驾驶感知算法工程师、3D 生成模型（如 TRELLIS.2）开发者，以及需要在大规模体素化点云上进行高性能训练与推理的 AI 系统工程师。

同类项目与差别

  • spconv：业界最经典的稀疏卷积库。FlexGEMM 在 README 中明确将其作为主要对比基线，并宣称在 FP16 和 TF32 精度下，训练吞吐量达到了 spconv 的约 2 倍。
  • torchsparse：MIT 开发的高性能稀疏卷积库。FlexGEMM 同样在基准测试中超越了它，主要差异在于 FlexGEMM 采用了 Triton-First 架构，在 GEMM 核心计算上迭代和调优速度更快。
  • fvdb：NVIDIA 推出的稀疏体积数据深度学习框架。FlexGEMM 在 README 的性能总结中明确指出其速度持续优于 fvdb，且 FlexGEMM 的轻量化和跨平台（支持 ROCm）特性更强。

二、架构与代码地图

FlexGEMM 的架构设计采用了经典的「Python 调度 + C++/CUDA 拓扑构建 + Triton 矩阵计算」三层分离模型。这种设计既保证了极高的执行效率，又兼顾了跨平台（CUDA/ROCm）的灵活性。 1. API 与调度层 (Python, flex_gemm/ops/)：这是直接面向用户的接口层。它通过 PyTorch 的 torch.autograd.Function 封装了前向与反向传播逻辑。该层负责输入张量的形状与设备校验、哈希表的初始化（init_hashmap），并根据用户配置的 Algorithm 枚举（如 Explicit, Implicit, Masked Implicit, Split-K）将计算图分发到对应的底层 Kernel。 2. 拓扑与元数据层 (C++/CUDA, flex_gemm/kernels/cuda/)：这是 3D 稀疏卷积的「控制流」核心。由于 3D 点云的高度稀疏性，必须先建立输入体素与输出体素之间的邻居映射关系（Neighbor Mapping）。该层通过高度优化的定制 CUDA 算子实现了空间哈希表（hash.cu）、Z-Order/Hilbert 曲线空间序列化（serialize/api.cu）以及邻居索引构建（subm_neighbor_map.cu）。对于只有 Mac 的你来说，这是最大的痛点：这部分代码完全依赖 torch.utils.cpp_extension.CUDAExtension，没有提供 CPU Fallback，因此你无法在本地运行任何涉及拓扑构建的代码。 3. 核心计算层 (Triton, flex_gemm/kernels/triton/)：这是 FlexGEMM 的「数据流」与算力核心。在获取了 C++ 层生成的邻居索引后，实际的特征矩阵乘法（GEMM）全部交由 OpenAI Triton 实现。这里包含了多种稀疏 GEMM 变体，例如在 Triton Kernel 内部动态加载稀疏数据的 Implicit GEMM，以及利用掩码优化内存访问的 Masked Implicit GEMM。这是你本地静态阅读的重点，你可以充分发挥你在 Triton 和算子融合方面的经验，在 Mac 上分析其 Block 划分、Shared Memory 调度以及 Split-K 的跨 Block 归约逻辑。 4. 构建与工具层 (setup.py, flex_gemm/utils/)：负责跨平台编译（通过环境变量 BUILD_TARGET 区分 CUDA 和 AMD ROCm/HIP），以及 Triton Kernel 的 Autotune 缓存管理。

一次调用怎么流过这些模块

以 README 中展示的 sparse_submanifold_conv3d（子流形稀疏卷积）前向传播为例，完整的数据流如下： 1. 输入准备与预处理 (Python)：用户传入稀疏特征 feats (形状为 [N, Ci])、对应的 3D 坐标 coords (形状为 [N, 4]，包含 batch_idx, x, y, z) 以及空间形状 shape。Python 层的 sparse_submanifold_conv3d 接收这些数据，并检查数据类型（如 FP16）和设备（必须为 CUDA）。 2. 哈希表初始化 (Python -> CUDA)：调用 flex_gemm.ops.utils.init_hashmap。根据空间体积 VOL 的大小，在 GPU 上分配一个全为最大值的 uint32 或 uint64 张量作为哈希表的 Keys，并分配对应的 Values 张量。 3. 构建邻居映射 (CUDA C++)：这是控制流的核心。系统调用 flex_gemm.kernels.cuda 中的 subm_neighbor_map。首先，将输入的 coords 插入哈希表。接着，对于卷积核的每一个空间偏移（例如 3x3x3 的卷积核有 27 个偏移量），CUDA Kernel 会遍历所有输入坐标，加上偏移量后在哈希表中查询。查询命中的结果将被写入一个名为 neighbor_cache 的索引矩阵中。这个矩阵记录了「哪个输入特征行」应该与「哪个输出特征行」在特定的卷积核权重下进行计算。 4. 算法路由与分发 (Python)：Python 层读取全局配置 flex_gemm.ops.spconv.Algorithm。假设用户设置为 MASKED_IMPLICIT_GEMM_SPLITK，调度器将选择对应的 Triton Kernel 包装器。 5. Triton GEMM 计算 (Triton)：数据流进入 flex_gemm.kernels.triton.spconv.sparse_submanifold_conv_fwd_masked_implicit_gemm_splitk.py。在这个阶段，Triton Kernel 不会像传统 Explicit 算法那样先将稀疏特征 gather 成庞大的密集矩阵（这会消耗大量显存），而是采用 Implicit 策略：在 Triton 的 Block 内部，利用上一步生成的 neighbor_cache 索引，直接从全局内存中按需加载 feats 的对应行到 Shared Memory 中，同时加载对应的 weight。随后利用 Tensor Core 执行块级别的矩阵乘法。由于启用了 Split-K，K 维度（输入通道 Ci）会被切分到不同的 Thread Block 中并行计算，最后通过原子加（Atomic Add）或专门的 Reduction Kernel 将部分和（Partial Sums）累加到最终的 out_feats 中。 6. 输出与缓存保留 (Python)：返回计算好的 out_feats，同时将 neighbor_cache 一并返回。这个 Cache 会被保存在 PyTorch 的 Autograd 上下文中，供反向传播（Backward Pass）直接复用，从而避免在反向时重复构建哈希表和查询邻居，极大提升了训练吞吐量。

三、本地跑起来（没有 GPU 的 Mac）

安装

  1. git clone https://github.com/JeffreyXiang/FlexGEMM.git
  2. cd FlexGEMM
  3. sed -i '' '/ext_modules=\[/,/\],/d' setup.py
  4. pip install -e . --no-build-isolation --no-dependencies
  5. pip install torch>=2.4.0 filelock

哪些路径能真跑

在你的 Mac (Apple Silicon) 上，没有任何端到端路径可以真正执行。虽然 flex_gemm/kernels/cuda/serialize/api.cu 中存在 cpu::z_order_encode 这样的 CPU Fallback 分支，但由于 setup.py 强绑定了 torch.utils.cpp_extension.CUDAExtension，在没有 nvcc 的 Mac 上连 C++ 扩展的编译这一关都过不去。你本地的唯一作用是作为「静态代码阅读器」：利用修改 setup.py 后的伪安装获得 IDE 补全，重点阅读 flex_gemm/kernels/triton/spconv/ 下的纯 Python Triton 源码（如 sparse_conv_masked_implicit_gemm_splitk.py），分析其 Block 划分与 Split-K 归约逻辑。

最小可运行

  1. pip install . --no-build-isolation
  2. python tests/hashmap.py
  3. python tests/serialize.py
  4. python tests/spconv/fwd.py
  5. python tests/submconv/fwd.py

测试

测试套件位于 tests/ 目录下，没有使用 pytest 等第三方框架，而是按模块划分的独立 Python 脚本（如 tests/submconv/fwd.py, tests/submconv/bwd.py）。无法只跑 CPU 子集，因为所有测试均隐式或显式依赖 CUDA 拓扑构建算子。你必须将代码推送到 Colab T4 实例上执行。单个前向/反向功能测试脚本耗时极短（几秒到十几秒），而 tests/submconv/train_benchmark.py 这种性能基准测试耗时会稍长。

调试

  • TRITON_INTERPRET=1 python tests/submconv/fwd.py (在 Colab 上强制 Triton 使用 CPU 解释器运行，极慢，但支持 print 调试和精准的越界内存访问报错，是你分析 Masked Implicit GEMM 边界条件的神器)
  • TORCH_SHOW_CPP_STACKTRACES=1 (用于在 Colab 上调试 C++ 拓扑构建算子崩溃时的堆栈)

坑

  • Mac 强行编译必挂：不要试图在 Mac 上通过安装各种工具链来解决 CUDAExtension 的报错，项目底层强依赖 CUDA API，直接修改 setup.py 绕过编译仅做静态分析是最优解。
  • Colab T4 性能幻觉：README 中的 2 倍加速基准是在 A100 (支持 TF32/FP16 硬件加速) 上测得的。Colab 的 T4 是 Turing 架构，不支持 TF32，且 Triton 在旧架构上的指令调度优化较差。在 T4 上跑 tests/submconv/train_benchmark.py 绝对无法复现 README 中的极致性能，请仅将其用于功能验证。
  • Triton 版本陷阱：pyproject.toml 明确要求 triton>=3.2.0。如果 Colab 默认环境的 Triton 版本过低，会导致隐式 GEMM 脚本中的高级 Block Pointer 语法或特定 API 报错，务必在测试前确认环境版本。
