修复 Triton Heuristics 包装导致的 Autotune Cache Key 不一致

Issue #26 · [dev/all_triton branch] Inconsistent autotune cache keys for kernels wrapped with `@triton.heuristics` ↗

无人认领0 条评论更新 2026-05-09

用到的专长：Triton 代码生成与编译期问题

目标：修改 `autotuner.py`，使其在遇到 `@triton.heuristics` 包装的函数时，能够正确提取原始 kernel 的 `__module__`，生成一致的 cache key。

为什么值得长期做：Autotune 缓存的正确命中对于 Triton kernel 的启动延迟至关重要。修复此问题能展现对 Triton 内部机制的熟悉度，是深入 FlexGEMM 编译与调优系统的绝佳切入点。

怎么介入：Issue 处于 open 状态，无 assignee，无 linked PR。适合直接认领。
第一个 PR 的边界：仅修改 `autotuner.py` 中的 key 生成逻辑并添加对应测试。
第一步：定位 `flex_gemm/utils/autotuner.py` 中的 `_get_function_cache_key` 函数。
认领留言（英文，可直接贴到 Issue）
Hi @JeffreyXiang, I'd like to fix this issue. I plan to update `_get_function_cache_key` in `autotuner.py` to unwrap `triton.runtime.autotuner.Heuristics` objects and extract the `__module__` from the underlying `JITFunction`. I can submit a PR to the `dev/all_triton` branch within a day. Let me know if there are other wrappers I should handle!
大致实施方案
  • 在 `_get_function_cache_key` 中，检查传入的 `fn` 是否为 `triton.runtime.autotuner.Heuristics` 的实例。
  • 如果是，通过 `fn.fn` (或相应的底层属性) 获取被包装的原始 `JITFunction`。
  • 使用原始函数的 `__module__` 和 `__name__` 来生成 cache key，确保与未包装的 kernel 保持一致的命名空间 (`flex_gemm.kernels.triton.spconv...`)。
  • 编写一个简单的单元测试，分别对带有和不带有 `@triton.heuristics` 的 mock kernel 调用该函数，断言生成的 key 前缀一致。
可能涉及的目录或文件
  • flex_gemm/utils/autotuner.py
  • tests/
验收方式
  • 在 Mac 上运行新增的单元测试；或者在 Python REPL 中导入 `flex_gemm`，手动 mock 一个带有 `@triton.heuristics` 的函数并打印其 cache key，确认前缀正确。
开工前问题与风险

向维护者确认

  • Is the target branch for this fix `dev/all_triton` or `main`?
  • Are there any other Triton wrapper classes (like `Autotuner`) that we should unwrap similarly in `_get_function_cache_key`?

风险

  • 修复后可能会导致旧的、命名错误的 cache 文件失效，这是预期的，但需在 PR 描述中说明。

重构 SubMConvNeighborCache 以解耦 Neighbor Map 与 Index GEMM

Issue #23 · FlexGEMM 2.0：改进计划 (Roadmap) ↗

无人认领0 条评论更新 2026-05-11

用到的专长：PyTorch 内核与算子融合、纯逻辑层重构

目标：按照 Roadmap 规划，将 `SubMConvNeighborCache` 瘦身，使其仅负责持有 `neighbor_map`，并将 GEMM 算法所需的中间缓存逻辑下放到具体的 GEMM 实现中；统一 forward/backward 接口。

为什么值得长期做：这是 FlexGEMM 2.0 架构升级的核心部分。解耦后将极大提升代码的可维护性，并为后续支持更多稀疏卷积变体奠定基础。完成此任务能确立你在该项目核心架构上的影响力。

怎么介入：这是一个 Roadmap Issue，维护者列出了详细的计划但尚未分配。适合资深工程师主动承担其中一个子模块。
第一个 PR 的边界：重构 `SubMConvNeighborCache` 及相关的 Python 路由层，不修改底层 CUDA/Triton kernel 的核心计算逻辑。
第一步：梳理 `SubMConvNeighborCache` 当前的属性，区分哪些属于纯坐标映射，哪些属于特定 GEMM 算法的缓存。
认领留言（英文，可直接贴到 Issue）
Hi @JeffreyXiang, I'm very interested in the FlexGEMM 2.0 roadmap, specifically the decoupling of Neighbor Map and Index GEMM. I'd like to take on this refactoring task. I plan to strip `SubMConvNeighborCache` down to just the `neighbor_map` and move the algorithm-specific cache generation into the respective GEMM modules. I'll verify the logic using `TRITON_INTERPRET=1` on CPU. Should I target the `dev/all_triton` branch for this?
大致实施方案
  • 修改 `SubMConvNeighborCache` 类，移除 `gray_code`, `sorted_idx`, `valid_signal_*` 等与 GEMM 强相关的属性，仅保留 `neighbor_map`。
  • 在具体的 GEMM 算法模块（如 explicit / implicit / masked_implicit）中，按需从 `neighbor_map` 动态派生或缓存所需的辅助数据结构。
  • 重构 `index_gemm` 接口，使其不区分 forward/backward，通过传入不同的 `neighbor_map` (如 flipped) 和 `algorithm` 参数来路由。
  • 统一 `sparse_submanifold_conv3d` 等对外 API，使其调用新的解耦架构。
  • 在 CPU 上使用 Triton 解释器模式 (`TRITON_INTERPRET=1`) 运行现有的 `tests/`，确保重构没有破坏逻辑正确性。
可能涉及的目录或文件
  • flex_gemm/ops/spconv.py
  • flex_gemm/kernels/triton/
  • tests/
验收方式
  • 设置环境变量 `TRITON_INTERPRET=1`，在 Mac 上运行 `pytest tests/`，确保所有稀疏卷积的 forward 和 backward 数值测试通过。
开工前问题与风险

向维护者确认

  • Should this refactoring be based on the `main` branch or `dev/all_triton`?
  • Are there any specific performance regressions I should watch out for when moving the cache generation into the GEMM routing layer?

风险

  • 涉及核心路由逻辑的修改，容易引入细微的数值错误或性能回退；需要仔细对比重构前后的测试结果。

用到的专长：CPU 参考实现、性能建模

目标：协助原作者优化 PR #29 中的 CPU fallback 实现，解决 `masked_select` 等 PyTorch 原生算子在 CPU 上性能低下的问题。

为什么值得长期做：提升 CPU fallback 的性能可以极大改善在无 GPU 或低显存环境下的开发和调试体验，扩大项目的受众。

怎么介入：Issue 已有 linked PR #29 且原作者正在开发。得体的介入方式是提供性能优化协助和 Code Review，而不是直接抢占任务。
第一个 PR 的边界：提交针对 PR #29 的优化 commit，或提供详细的 Code Review 建议。
