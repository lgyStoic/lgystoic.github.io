一、项目定位

FlexGEMM 是一个专为 3D 稀疏卷积设计的高性能、跨平台底层计算库。它的核心架构是「Triton 计算 + CUDA/C++ 辅助」，通过引入显式（Explicit）、隐式（Implicit）和掩码隐式（Masked Implicit）等现代 GEMM 算法变体，以及 Split-K 并行优化，来解决 3D 稀疏张量中高度不规则的内存访问问题。对于你（资深 Kernel 工程师）而言，这个项目非常对口：它的核心算力层完全基于 Triton（>=3.2.0）实现，这与你擅长的算子融合和前沿加速技术高度契合。但你需要特别注意硬约束冲突：根据 setup.py 源码，该项目强依赖 torch.utils.cpp_extension.CUDAExtension 来编译哈希表（hash.cu）、序列化（api.cu）和邻居映射（subm_neighbor_map.cu 等）的底层 C++ 模块。这意味着在你的 MacBook Air 上直接 pip install . 会因为缺少 NVCC 而失败。你的切入路径应该是：在 Mac 上仅做源码阅读、Triton Kernel 逻辑推演（flex_gemm/kernels/triton/），如果需要本地跑通 Python 逻辑，可能需要先 Mock 掉 flex_gemm.kernels.cuda 的导入，最终的正确性验证与 Autotune 调优则必须依赖那台免费的 Colab T4 实例。项目目前处于活跃迭代期，最近的提交热点集中在跨平台（AMD ROCm/HIP 支持）和底层同步原语（__syncwarp）的修复上。

解决什么问题、给谁用

3D 稀疏卷积（如体素化点云处理）存在极度不规则的稀疏模式，导致传统基于手写 CUDA 的实现（如早期 spconv）在显存带宽和计算单元利用率上面临瓶颈，难以充分发挥现代 GPU 的 Tensor Core 算力（如 FP16/TF32）。

3D 深度学习研究员、自动驾驶感知算法工程师、以及 3D 生成式 AI 开发者（如 README 中提到的微软 TRELLIS.2 项目）。典型场景包括高分辨率体素化点云处理、子流形卷积（Submanifold Convolution）以及大规模 3D 神经网络的训练与推理加速。

同类项目与差别

  • spconv：传统的行业标杆，底层重度依赖手写 CUDA 和 CUTLASS。FlexGEMM 宣称通过 Triton 和掩码隐式 GEMM 算法，在 FP16/TF32 训练吞吐量上比其快约 2 倍。
  • torchsparse：MIT 开发的稀疏计算库。FlexGEMM 在 README 的 Benchmark 中宣称在训练速度上持续超越它。
  • fvdb：NVIDIA 推出的较新的稀疏体积框架。FlexGEMM 同样在 README 中声明其性能（SOTA Speed）优于 fvdb。

二、架构与代码地图

FlexGEMM 的架构设计非常清晰，呈现出典型的「Python 接口 + C++ 拓扑映射 + Triton 核心计算」三层结构。对于只有 MacBook Air 的你来说，理解这种分层至关重要，因为它决定了你能在本地做什么、不能做什么。 1. 用户接口与调度层 (Python/PyTorch)：位于 flex_gemm/ops/。这一层是纯 Python 实现，负责接收用户的 PyTorch Tensor（如 feats, coords），进行参数校验，并根据用户配置（如 Algorithm.MASKED_IMPLICIT_GEMM_SPLITK）将任务分发给底层的 Kernel。你可以在 Mac 上毫无障碍地阅读和修改这一层。 2. 拓扑映射与辅助计算层 (C++/CUDA)：位于 flex_gemm/kernels/cuda/。这是 3D 稀疏卷积的基石，也是阻碍你在 Mac 上直接运行的硬约束所在。稀疏卷积需要知道「哪些输入点与哪些输出点相邻」，该层通过 Z-order/Hilbert 空间编码（serialize/）、哈希表（hash/）和邻居映射（spconv/）来构建这些索引。setup.py 强依赖 nvcc 或 hipcc 来编译这些 .cu 文件。在 Mac 上，你只能阅读源码，若要单测 Python 逻辑，必须 Mock 掉 flex_gemm.kernels.cuda 的导入。 3. 核心算力层 (Triton)：位于 flex_gemm/kernels/triton/。这是 FlexGEMM 宣称比传统手写 CUDA（如 spconv）快 2 倍的核心秘密，也是你作为资深 Kernel 工程师的主战场。作者将复杂的稀疏卷积转化为 Implicit GEMM 或 Masked Implicit GEMM，并利用 Triton 编译器自动优化 Tensor Core 的调用。这一层完全是 Python 代码，你可以在 Mac 上进行深度的逻辑推演、算子融合设计和访存模式分析。 4. 工具与调优层：位于 flex_gemm/utils/ 和根目录的 autotune_cache.json。Triton 强依赖 Autotune 来寻找最佳的 Block Size 和 Warps 组合。项目在 setup.py 中实现了安装时合并本地 Cache 的逻辑，这表明性能调优是该项目的核心日常。

一次调用怎么流过这些模块

以 README 中展示的 sparse_submanifold_conv3d 前向推理/训练过程为例，数据在 FlexGEMM 中的流转路径如下，请特别注意哪些步骤在你的 Mac 上会失败： 1. 数据准备与编码 (Python -> CUDA)：用户传入稀疏特征 feats 和 3D 坐标 coords。首先，系统会调用 flex_gemm.ops.serialize.encode_seq。该函数计算坐标的 bit length，并调用底层的 kernels.cuda.z_order_encode（或 hilbert），将 3D 坐标降维编码为 1D 的 Z-order codes，以提升后续内存访问的局部性。*注意：这一步在 Mac 上会因为缺少 CUDA 扩展而报错。* 2. 哈希表初始化 (Python)：调用 flex_gemm.ops.utils.init_hashmap，根据空间体积（Volume）大小，在 GPU 上分配 uint32 或 uint64 类型的哈希表内存（hashmap_keys 和 hashmap_vals）。 3. 构建邻居映射 (CUDA)：这是稀疏卷积最复杂的一步。系统调用 flex_gemm/kernels/cuda/spconv/subm_neighbor_map.cu 中的逻辑。它将编码后的坐标插入哈希表，并根据卷积核大小（如 Ks=3），查找每个输入点周围的邻居，最终生成 neighbor_map。这个映射表记录了参与计算的输入索引和输出索引的对应关系。 4. 算法路由 (Python)：回到 flex_gemm/ops/spconv/submanifold_conv3d.py，系统检查用户通过 set_algorithm 设置的策略（例如 MASKED_IMPLICIT_GEMM_SPLITK）。 5. Triton GEMM 执行 (Triton)：这是算力消耗的大头。任务被分发到 flex_gemm/kernels/triton/spconv/sparse_submanifold_conv_fwd_masked_implicit_gemm_splitk.py。Triton Kernel 启动，每个 Block 负责计算输出特征的一部分。Kernel 内部会读取 neighbor_map，利用掩码（Mask）处理不规则的稀疏边界，从显存中加载 feats 和 weight 到 SRAM，然后调用 Triton 的 tl.dot 触发硬件 Tensor Core 进行矩阵乘法。如果启用了 Split-K，还会跨 Block 进行规约（Reduction）。 6. 输出与缓存 (Python)：计算完成后，返回 out_feats。同时，生成的 neighbor_map 等中间数据会被打包成 neighbor_cache 一并返回，供反向传播（Backward Pass）复用，避免重复构建哈希表。

扩展点

  • flex_gemm/ops/spconv/__init__.py (需验证) & flex_gemm/kernels/triton/spconv/：新增 GEMM 算法变体：在 Python 层的 Algorithm 枚举中添加新类型，在 Triton 目录下编写新的 Kernel（如针对特定稀疏度优化的 Kernel），并在 flex_gemm/ops/spconv/ 的分发逻辑中增加对应的分支。
  • setup.py & flex_gemm/kernels/cuda/：新增硬件后端（如 Intel XPU）：修改 setup.py 中的 BUILD_TARGET 逻辑，添加对应的编译器标志。检查 CUDA C++ 代码中的同步原语（如近期修复的 __syncwarp 对应 AMD 的 wave_barrier），确保跨平台兼容性。
  • flex_gemm/ops/serialize.py & flex_gemm/kernels/cuda/serialize/：新增空间编码方式（如 Morton Code）：在 CUDA 层实现编码/解码逻辑，在 api.h 和 api.cu 中暴露接口，最后在 Python 层的 encode_seq 函数中增加新的 mode 分支。

三、本地跑起来（没有 GPU 的 Mac）

安装

  1. git clone https://github.com/JeffreyXiang/FlexGEMM.git
  2. cd FlexGEMM
  3. pip install torch>=2.4.0 filelock
  4. export PYTHONPATH=$(pwd):$PYTHONPATH

哪些路径能真跑

在你的 Mac 上，你可以毫无障碍地阅读和静态分析 flex_gemm/ops/ 下的纯 Python 调度逻辑（如 sparse_conv3d.py）以及 flex_gemm/utils/autotuner.py。虽然 flex_gemm/kernels/cuda/serialize/api.cu 中写有 cpu::z_order_encode 的 CPU fallback 分支，但由于你无法在 Mac 上编译 CUDAExtension，这部分代码在本地无法被 Python 调用。所有的 Triton 核心算力层（flex_gemm/kernels/triton/）和 C++ 拓扑映射层（flex_gemm/kernels/cuda/）都必须依赖 Colab T4 实例来真正执行和验证。

测试

测试用例集中在 tests/ 目录下，按模块划分为 spconv/, submconv/, hashmap.py 等。项目似乎没有使用 pytest，而是通过直接运行独立的 Python 脚本来进行测试和基准评估（如 tests/submconv/train_benchmark.py）。由于底层强依赖 CUDA 扩展和 Triton，你无法在 Mac 上运行任何 CPU 测试子集。在 Colab T4 上运行单个 benchmark 脚本大概需要几分钟（主要耗时在 CUDA 扩展的编译和 Triton Kernel 的 JIT 编译上）。

调试

  • 编译控制：通过环境变量 BUILD_TARGET=cuda 或 BUILD_TARGET=rocm 强制指定编译后端，使用 GPU_ARCHS 指定目标架构（见 setup.py）。
  • Triton 模拟：在 Mac 上推演逻辑时，可以尝试设置环境变量 TRITON_INTERPRET=1 来在 CPU 上模拟运行 Triton kernel（速度极慢，仅限验证基础逻辑，且可能不支持某些高级硬件指令）。
  • 缓存清理：项目在安装时会将 autotune_cache.json 合并到 ~/.flex_gemm/autotune_cache.json。如果你在调优 Block Size 或 Warps 时发现修改未生效，务必手动删除该缓存文件。
