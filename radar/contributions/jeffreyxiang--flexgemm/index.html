一、项目定位

FlexGEMM 是一个专为 3D 稀疏卷积（3D sparse convolutions）设计的高性能、基于 Triton 的 GEMM 后端。在 3D 深度学习（如体素化点云、3D 生成模型）中，数据通常具有高度不规则的稀疏性，传统的密集矩阵乘法会造成巨大的算力浪费，而现有的稀疏卷积库在底层算子优化上仍有瓶颈。FlexGEMM 的核心价值在于采用“Triton-First”架构，结合 Explicit、Implicit 和 Masked Implicit 等多种算法变体，以及 Split-K 并行优化，实现了对 3D 稀疏张量的高效处理。根据 README 的基准测试，在 A100 上使用 FP16 和 TF32 精度时，其训练吞吐量比现有的 SOTA 方案（如 spconv）快约 2 倍。 目前项目处于活跃且相对成熟的阶段（已发布 v1.1.0），并已被微软的 TRELLIS.2（3D 生成模型）作为真实业务场景的依赖使用。近期提交记录显示，项目正在积极扩展跨平台支持，包括 AMD ROCm/HIP 的适配（如修复 __syncwarp 和禁用 TF32）以及 Windows 平台的支持。 对候选人的切入建议与硬件警告： 作为资深 Kernel 工程师，你的背景与该项目高度契合（Triton、算子融合、3D/扩散模型加速）。但你的硬件约束（仅有 Apple Silicon Mac）是致命的。通过分析 setup.py 可知，该项目不仅包含 Triton 代码，还通过 CUDAExtension 强依赖并编译大量原生 CUDA C++ 代码（如 hash.cu, grid_sample.cu, subm_neighbor_map.cu 等）。这意味着你完全无法在 Mac 上进行本地编译、构建或单元测试。你只能在 Mac 上进行纯文本级别的源码阅读和 Triton 逻辑推演。此外，你计划使用的免费 Colab T4（Turing 架构）不支持 TF32，且缺乏 Ampere 架构的异步拷贝等高级特性，这会导致你无法复现 README 中基于 A100 的 TF32 性能基准，也无法验证针对 Ampere 及以上架构的极致 Triton 优化。建议切入策略：在 Mac 上专注于 flex_gemm/kernels/triton 目录下的 Triton 源码阅读与理论优化，利用 Colab T4 仅做功能性验证（FP16/FP32），避免在 T4 上死磕极致性能。

解决什么问题、给谁用

解决 3D 体素化数据和点云处理中，高度不规则稀疏模式下的卷积计算效率问题。传统的稀疏卷积实现（如基于规则哈希表或低效内存布局）在现代 GPU 上难以充分利用 Tensor Core 的算力，导致训练和推理吞吐量受限。

3D 计算机视觉研究员、自动驾驶感知算法工程师、3D 生成模型（如 DiT 架构的 3D 扩散模型）开发者。典型场景包括：高分辨率体素化点云处理、子流形卷积（Submanifold Convolutions）计算、大规模 3D 神经网络的训练与推理加速（如 TRELLIS.2 项目）。

同类项目与差别

  • spconv：业界最经典的稀疏卷积库。FlexGEMM 在 README 中明确将其作为主要对比基线，声称在 FP16/TF32 训练速度上比 spconv 快约 2 倍，且 FlexGEMM 更重度依赖 Triton 进行跨平台和高性能内核生成。
  • torchsparse：MIT 开发的高性能稀疏卷积库。FlexGEMM 同样在基准测试中将其列为超越对象，强调在不同通道宽度（C=64 到 1024）和分辨率下具有更好的一致性和更高的吞吐量。
  • fvdb：NVIDIA 推出的用于稀疏体积数据的深度学习框架。FlexGEMM 在 README 的 Performance Summary 中声明其速度持续优于 fvdb。

二、架构与代码地图

FlexGEMM 的架构设计体现了典型的“Python 接口 + Triton 计算 + CUDA 辅助”的三层混合范式，这种设计在现代高性能算子库中非常流行。 1. 用户接口层 (User Interface Layer)：位于 flex_gemm/ops 目录下。这一层直接面向模型开发者，提供与 PyTorch 高度兼容的 API（如 sparse_submanifold_conv3d）。它负责接收 PyTorch Tensor，进行参数校验，并根据用户配置（如 Algorithm.MASKED_IMPLICIT_GEMM_SPLITK）进行算法路由。 2. 调度与工具层 (Dispatch & Utility Layer)：主要由 flex_gemm/utils/autotuner.py 和 setup.py 构成。调度器负责在运行时为 Triton kernel 选择最佳的 block size、num_warps 等超参数。setup.py 不仅负责编译，还包含了一个巧妙的 autotune_cache.json 合并逻辑，使得预调优的参数可以随包分发，减少用户首次运行的预热时间。 3. Triton 核心计算层 (Triton Kernel Layer)：位于 flex_gemm/kernels/triton 目录下。这是 FlexGEMM 的性能引擎，实现了 Explicit、Implicit 和 Masked Implicit 等多种稀疏 GEMM 变体，并支持 Split-K 并行。作为只有 Mac 的开发者，这里是你唯一可以进行纯文本推演和理论优化的主战场。 4. CUDA 辅助计算层 (CUDA Auxiliary Layer)：位于 flex_gemm/kernels/cuda 目录下。由于 Triton 擅长规则的块状矩阵乘法，但不擅长复杂的指针跳转和原子操作，FlexGEMM 将哈希表维护 (hash.cu)、空间曲线编码 (serialize/api.cu 中的 Z-order/Hilbert)、以及稀疏邻居映射表的构建 (spconv/subm_neighbor_map.cu) 交给了原生 CUDA C++。这一层是你无法在 Mac 上编译的“禁区”，但理解其暴露的 API（如 api.h）对于理清数据流至关重要。

一次调用怎么流过这些模块

以一次典型的 3D 稀疏子流形卷积（Submanifold Convolution）前向传播为例，数据在 FlexGEMM 中的流转路径如下： 1. 数据准备与接口调用：用户在 PyTorch 中准备好稀疏特征 feats、坐标 coords 和空间形状 shape，调用 flex_gemm.ops.spconv.sparse_submanifold_conv3d。此时，数据进入用户接口层。 2. 空间编码与哈希初始化：为了高效查找稀疏坐标的邻居，系统首先可能调用 flex_gemm.ops.serialize.encode_seq，底层触发 flex_gemm/kernels/cuda/serialize/api.cu 中的 z_order_encode 或 hilbert_encode，将 3D 坐标降维为 1D 编码以提升内存局部性。接着，调用 flex_gemm.ops.utils.init_hashmap 分配哈希表内存。 3. 构建邻居映射表 (Neighbor Map)：这是稀疏卷积的核心准备工作。系统调用 flex_gemm/kernels/cuda/hash/hash.cu 将当前坐标插入哈希表，然后通过 flex_gemm/kernels/cuda/spconv/subm_neighbor_map.cu 查询卷积核覆盖范围内的有效邻居，生成输入与输出特征之间的索引映射关系（Neighbor Map）。这一步完全在 CUDA C++ 层完成。 4. 算法路由与 Autotune 调度：接口层根据全局设置的 Algorithm 枚举（例如 MASKED_IMPLICIT_GEMM_SPLITK），准备分发到对应的 Triton kernel。在启动前，flex_gemm/utils/autotuner.py 会介入，根据输入特征的维度（如通道数、非零元素数量）查询 autotune_cache.json，获取最优的 Triton 编译参数（如 BLOCK_M, BLOCK_N, num_stages）。 5. Triton Kernel 执行：调度器最终启动 flex_gemm/kernels/triton/spconv/sparse_submanifold_conv_fwd_masked_implicit_gemm_splitk.py。在这个 kernel 中，Triton 程序利用上一步生成的 Neighbor Map，将不规则的稀疏特征拉取到 SRAM 中，利用 Tensor Cores 执行密集的矩阵乘法（GEMM）。Split-K 优化会将 K 维度切分到不同的 block 中并行归约，进一步压榨 GPU 算力。 6. 结果返回与缓存：计算完成后，输出特征张量返回给 Python 层。同时，为了加速反向传播，前向过程中构建的哈希表和 Neighbor Map 会被打包成 neighbor_cache 一并返回。反向传播时，PyTorch 的 Autograd 机制会直接复用这些缓存，调用对应的 _bwd_ Triton kernel 计算梯度。

扩展点

  • 用户代码中直接调用 flex_gemm.ops.spconv：新模型接入：替换原有的 spconv 或 torchsparse 卷积层，传入相同的 feats 和 coords 即可。
  • setup.py 与 flex_gemm/kernels/cuda：新后端接入：修改 setup.py 中的编译标志（如已有的 ROCm 适配），并在 C++ 代码中处理硬件差异（如将 __syncwarp 替换为 wave_barrier）。
  • flex_gemm/kernels/triton/spconv/ 与 flex_gemm/ops/spconv/：新 kernel 接入：在 triton 目录下编写新的 .py kernel，然后在 ops 层的 Algorithm 枚举中注册并添加分发逻辑。
  • flex_gemm/utils/autotuner.py：新调度策略接入：修改 autotuner 的启发式搜索空间或缓存键生成逻辑，以适应新的硬件架构（如 Apple Silicon 的特定 block size）。

三、本地跑起来（没有 GPU 的 Mac）

安装

  1. git clone https://github.com/JeffreyXiang/FlexGEMM.git
  2. cd FlexGEMM
  3. conda create -n flexgemm python=3.10 -y && conda activate flexgemm
  4. pip install torch>=2.4.0
  5. pip install triton>=3.2.0
  6. echo '警告：绝不要在 Mac 上执行 pip install . 或 python setup.py install。setup.py 中硬编码了 CUDAExtension，在 Apple Silicon 上会直接抛出编译错误。你的本地环境仅用于代码阅读和 IDE 补全。'

哪些路径能真跑

在 Apple Silicon (Mac) 上，没有任何核心计算路径可以真正执行。虽然 flex_gemm/kernels/cuda/serialize/api.cu 中存在 if (coords.device().type() == torch::kCUDA) 的分支判断并暗示了 cpu::z_order_encode 的存在，但整个库的底层哈希表 (hash.cu) 和稀疏邻居映射 (subm_neighbor_map.cu) 强依赖原生 CUDA C++，且 Triton 算子不支持 MPS。你只能在 Mac 上纯文本阅读 flex_gemm/kernels/triton/ 下的源码，或者利用 TRITON_INTERPRET=1 环境变量在 CPU 上模拟执行极小规模的 Triton kernel 逻辑推演。真正的功能验证必须在 Colab T4 上进行。

最小可运行

  1. python examples/submconv.py
  2. python examples/spconv.py
  3. python tests/submconv/fwd.py
  4. python tests/spconv/fwd.py

测试

项目没有使用标准的 pytest 或 unittest 框架，测试用例以独立的 Python 脚本形式散落在 tests/ 目录下（如 tests/submconv/fwd.py, tests/spconv/bwd.py, tests/hashmap.py）。不存在 CPU 子集，所有测试脚本内部均硬编码了 CUDA 设备（如 README 示例中的 device='cuda'）。在 Colab T4 上运行单个测试脚本大概耗时几秒到十几秒（主要开销在于 Triton JIT 编译和 Autotuner 预热）。

调试

  • TRITON_INTERPRET=1 : 这是你在 Mac 上唯一能用的神器。它允许你在 CPU 上以纯 Python 模式解释执行 Triton kernel，支持标准的 pdb 断点，非常适合你用来推演 sparse_conv_implicit_gemm.py 中的指针偏移和 Block 划分逻辑。
  • TRITON_PRINT_AUTOTUNING=1 : 在 Colab 上验证时开启，用于观察 flex_gemm/utils/autotuner.py 是如何为不同稀疏度选择 block_size 和 num_warps 的。
  • 清理 Autotune 缓存 : 调度层会在 ~/.flex_gemm/autotune_cache.json 生成缓存（近期 commit 6dd94a8 刚修改了合并逻辑）。如果你在调试时修改了 Triton kernel 的签名或 shape，务必手动删除该文件，否则会触发难以排查的 shape mismatch 错误。
  • 性能 Profiling : 在 Colab T4 上，使用 torch.profiler.profile 包装前向/反向调用，重点观察 Triton kernel 的执行时间和 CUDA 原生算子（如 hashmap_insert）的开销占比。
