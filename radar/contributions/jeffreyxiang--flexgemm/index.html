一、项目定位

FlexGEMM 是一个基于 Triton 的 3D 稀疏卷积 GEMM 后端，核心目标是在 Submanifold Convolution 与体素稀疏卷积的训练/推理路径上，用 Triton 重写高性能稀疏 GEMM kernel，从而在 A100 等 GPU 上稳定超越 spconv、torchsparse、fvdb 等现有方案。项目名字里的 'Flex' 来自它对 Explicit / Implicit / Masked Implicit 三类稀疏卷积算法的统一抽象，以及可选的 Split-K 并行策略；README 明确把 'Triton-First Architecture' 作为第一卖点，强调跨平台（CUDA + ROCm）兼容性。当前版本为 v1.1.0（2026-04-02），距离 v1.0.0（2026-01-13）仅三个月即发版，说明作者仍在快速迭代但已进入对外可交付阶段。代码结构上，Python 包位于 flex_gemm/，其中 ops/ 暴露 sparse_submanifold_conv3d 等高层算子，kernels/ 下同时存在 Triton kernel（flex_gemm/kernels/triton/）与手写 CUDA 扩展（flex_gemm/kernels/cuda/，通过 torch.utils.cpp_extension.CUDAExtension 编译），后者承载 hashmap、serialize、grid_sample、neighbor_map 等底层原语。从 commit 热点看，flex_gemm/kernels 以 49 次提交遥遥领先，说明性能核心仍在频繁调整；tests/submconv（7 次）和 setup.py（6 次）次之，反映 ROCm 适配与构建系统是新近重点。整体判断：这是一个处于 '可用但仍在打磨' 阶段的研究型性能库，作者同时维护算法、kernel、构建、跨平台兼容与 autotune cache，单人主导但已有外部 PR 合入（gustavomassa、cuzelac、ZJLi2013）。

解决什么问题、给谁用

解决 3D 稀疏卷积（尤其是 Submanifold Convolution 与常规稀疏卷积）在训练阶段的吞吐瓶颈。现有方案（spconv 2.x/3.x、torchsparse、fvdb）在 FP16/TF32 下仍存在 kernel launch 开销大、Split-K 并行不充分、对不规则稀疏模式适配差等问题。FlexGEMM 用 Triton 重写 GEMM 核心，配合 Explicit / Implicit / Masked Implicit 三种算法变体与可选 Split-K，在 A100 80GB 上对 C=64~1024、RES=8~1024 的体素数据实现约 2× 训练加速，且不增加显存占用。目标用户是做 3D 视觉 / 点云 / 辐射场 / 3D 生成模型（如 TRELLIS.2）的工程师与研究员，典型场景包括：高分辨率体素化点云训练、Submanifold Sparse ConvNet（如 SparseUNet、MinkowskiNet 风格）的前向与反向、以及需要自定义稀疏卷积算子的扩散式 3D 生成管线。

1) 3D 深度学习研究员：需要在 MinkowskiNet / SparseUNet / VoxelNet 等 backbone 上获得更高训练吞吐，或在 TRELLIS.2 这类 3D 生成框架中替换默认稀疏卷积后端。2) 点云感知工程师：在自动驾驶、机器人场景下处理大规模体素化点云，需要 FP16/TF32 下稳定训练。3) 性能库开发者 / 编译器工程师：关注 Triton 在稀疏 GEMM 上的工程实践，想借鉴 Explicit / Implicit / Masked Implicit 算法抽象与 Split-K 实现。4) 跨平台用户：需要在 NVIDIA CUDA 与 AMD ROCm 双栈上获得统一接口（项目已合入 ROCm PR 并处理 __syncwarp / tf32 兼容）。典型使用方式如 README 示例：调用 flex_gemm.ops.spconv.sparse_submanifold_conv3d，通过 set_algorithm() 选择 Algorithm.MASKED_IMPLICIT_GEMM_SPLITK，传入体素坐标、特征与卷积核完成前向与反向。

同类项目与差别

  • spconv（GitHub: traveller59/spconv）：spconv 是事实标准，提供 C++/CUDA 实现与 PyTorch 绑定，覆盖 2D/3D 稀疏卷积、反卷积、SubM 卷积等完整算子集，生态成熟；FlexGEMM 则聚焦训练路径的 GEMM 核心，用 Triton 重写以换取跨平台与更高吞吐，但算子覆盖面更窄，更像 '可插拔后端' 而非完整库。
  • torchsparse（GitHub: mit-han-lab/torchsparse）：torchsparse 同样面向 3D 稀疏卷积，强调与 PyTorch 生态集成；FlexGEMM 在 README 给出的 benchmark 中声称训练吞吐优于 torchsparse，且通过 Triton 而非纯 CUDA kernel 实现，便于在 ROCm 等新平台移植。
  • fvdb（GitHub: AcademySoftwareFoundation/fvdb）：fvdb 是 NVIDIA 维护的 Voxel DB，基于 CuTe/CUTLASS 构建，面向大规模稀疏体素网格与可微渲染；FlexGEMM 更聚焦卷积算子的 GEMM 性能，不追求通用 Voxel DB 抽象，但同样强调对不规则稀疏模式的高效处理。
  • MinkowskiEngine（GitHub: StanfordVL/MinkowskiEngine）：MinkowskiEngine 是 Submanifold 稀疏卷积的经典实现，使用 CUDA 手写 kernel 与坐标管理；FlexGEMM 在算法层面与之高度重叠（SubM 卷积），但用 Triton 重写 kernel 并引入 Split-K，目标是在 A100 上取得 2× 训练加速。

二、架构与代码地图

FlexGEMM 的代码组织可划分为五层。最上层是接入层（ops/），对外暴露 sparse_submanifold_conv3d、sparse_conv3d、grid_sample、serialize 等高层 PyTorch 友好算子，内部维护算法选择（Algorithm 枚举）、neighbor_cache 复用与 autotune 配置分发。往下是调度层（ops/spconv/ 与 ops/grid_sample/ 下的 wrapper 文件），负责把输入的稀疏坐标、特征、权重张量规整为 Triton kernel 所需的 indice、pointer、neighbor_map 等索引结构，并决定走 Explicit / Implicit / Masked Implicit 中哪条路径、是否启用 Split-K。第三层是执行层，即 Triton kernel 集合（flex_gemm/kernels/triton/spconv/ 与 grid_sample/），全部用 @triton.jit 写成，承担实际的 GEMM 计算与前后向累加，是性能核心；提交热点 49 次集中在此。第四层是硬件原语层（flex_gemm/kernels/cuda/），通过 torch.utils.cpp_extension.CUDAExtension 编译，提供 hashmap、z_order/hilbert 编码、grid_sample、neighbor_map 等底层 CUDA 例程，被 ops 层与 Triton kernel 共同调用。最底层是工具层（flex_gemm/utils/ 与 autotune_cache.json），承载 Autotuner、构建期 cache 合并、跨平台编译标志等支撑逻辑。整体数据流从上到下依次流经 ops → triton/cuda kernels → GPU，返回时沿原路回传梯度。

一次调用怎么流过这些模块

以训练阶段一次 Submanifold Convolution 前向为例。用户调用 flex_gemm.ops.spconv.sparse_submanifold_conv3d(feats, coords, shape, weight, bias)，进入 ops 层 wrapper；wrapper 先通过 set_algorithm 选定的 Algorithm 枚举（如 MASKED_IMPLICIT_GEMM_SPLITK）决定调度路径，同时借助 ops.utils.init_hashmap 或 kernels.cuda.hash 查询 / 构建 neighbor_cache，避免重复生成邻居索引。接着 ops 层把 feats、weight 与坐标索引打包，转成 Triton kernel 所需的 indice、pointer、neighbor_map 等稀疏结构——这一步会调用 kernels.cuda.spconv 的 subm_neighbor_map / sparse_neighbor_map 原语。随后调度层根据算法变体把请求分派到 kernels.triton.spconv 中对应的 @triton.jit 函数（如 sparse_submanifold_conv_fwd_masked_implicit_gemm_splitk），Triton kernel 在 GPU 上执行 GEMM 与累加，并利用 kernels/triton/utils.py 中的共享宏完成指针加载与 Split-K 规约。计算结果 out_feats 沿原路返回 ops 层并透传给调用者，neighbor_cache 被缓存以供下次复用。反向传播时，梯度沿相同链路回传，ops 层调用对应 bwd 版本的 Triton kernel（如 sparse_submanifold_conv_bwd_masked_implicit_gemm_splitk），最终更新 weight.grad 与 feats.grad。整个流程的关键数据结构包括：Algorithm 枚举（调度选择）、neighbor_cache（索引复用）、autotune_cache.json（kernel 配置缓存）、以及 Triton kernel 内部的 indice/pointer 隐式张量。
