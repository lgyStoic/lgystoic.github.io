修复 PyTorch 2.9+ 分布式张量并行模块兼容性问题

Issue #199 · Pytorch version problem ↗

目标：使引擎在 PyTorch 2.9.0+ 环境下能够正常导入并运行，消除 `_validate_tp_mesh_dim` 导入错误。

为什么值得长期做：解决底层依赖兼容性是 AI Infra 维护者的基本功，此修复能保障引擎在最新 PyTorch 生态下的可用性，是深入分布式推理模块的第一步。

第一步：调查 PyTorch 2.9 中 `torch.distributed.tensor.parallel._utils` 的变更情况。
大致实施方案
  • 查阅 PyTorch 2.9 Release Notes，确认 `_validate_tp_mesh_dim` 是否被重命名或移动。
  • 在 `diffsynth_engine/utils/parallel.py` 中，使用 `try...except ImportError` 或 `torch.__version__` 判断来实现向后兼容的导入逻辑。
  • 如果该内部函数已被移除且无替代，评估是否可以自行实现该验证逻辑或安全地绕过。
  • 在本地安装 PyTorch 2.9.0，运行 `python -c 'import diffsynth_engine.utils.parallel'` 验证是否报错。
可能涉及的目录或文件
  • diffsynth_engine/utils/parallel.py
验收方式
  • 在 PyTorch 2.9.0 环境下，成功运行 `examples/wan_text_to_video.py` 的 import 阶段而不抛出 `ModuleNotFoundError`。
开工前问题与风险

向维护者确认

  • 如果该内部 API 在 PyTorch 2.9 中被彻底废弃，是否接受在代码中直接 copy 一份旧版实现以保持兼容？

风险

  • 依赖内部 API (`_utils`) 本身具有脆弱性，未来可能需要重构张量并行的初始化逻辑。

修复 Mac MPS 环境下 QwenImageDiT 加载 LoRA 时的属性错误

Issue #224 · MAC Ultra pipe.load_lora raise an error "AttributeError: QwenImageDiT has no attribute `diffusion_model`" ↗

目标：修复 `QwenImagePipeline` 加载 LoRA 时因层级映射错误导致的崩溃。

为什么值得长期做：完善端侧（Mac MPS）和 LoRA 生态的支持，是提升引擎易用性的关键，有助于深入理解引擎的模型抽象架构和权重映射机制。

第一步：检查 `QwenImageDiT` 的类定义，确认其网络层的实际挂载属性名。
大致实施方案
  • 阅读 `diffsynth_engine/pipelines/qwen_image.py` 和 `diffsynth_engine/models/base.py`，理解 LoRA 权重的 key 映射逻辑。
  • 定位 `QwenImageDiT` 的实现，发现其可能没有名为 `diffusion_model` 的子模块（其他模型可能有）。
  • 在 `QwenImagePipeline.load_loras` 中重写或调整 key 的前缀映射规则，使其匹配 `QwenImageDiT` 真实的模块结构。
  • 编写一个仅加载模型和 LoRA 权重的测试脚本，指定 `device='cpu'` 进行验证。
可能涉及的目录或文件
  • diffsynth_engine/pipelines/qwen_image.py
  • diffsynth_engine/models/base.py
  • 需先定位 QwenImageDiT 的定义文件
验收方式
  • 在 CPU 或 MPS 设备上，成功执行 Issue 描述中的 `pipe.load_lora` 代码段，不抛出 `AttributeError`。
开工前问题与风险

向维护者确认

  • QwenImageDiT 的 LoRA key 映射规则是否应该与其他模型统一？是否需要在 `QwenImageDiT` 中增加一个 `diffusion_model` 的 alias？

风险

  • 修改基础的 `load_loras` 可能会影响其他模型的 LoRA 加载，需确保修改仅针对 QwenImage 生效或具有通用性。

第一步：在 `diffsynth_engine/pipelines/wan_s2v.py` 中搜索硬编码的 `16`。
大致实施方案
  • 在 `WanS2VPipeline.__call__` 方法的参数列表中增加 `fps: int = 16`。
  • 将管道内部处理视频保存或时间步计算时用到的硬编码 `16` 替换为 `fps` 变量。
  • 检查是否有其他依赖固定 FPS 的逻辑（如音频对齐），确保同步更新。
  • 编写测试脚本，传入 `fps=24`，验证输出视频的元数据是否正确。
可能涉及的目录或文件
  • diffsynth_engine/pipelines/wan_s2v.py
验收方式
  • 调用 `WanS2VPipeline` 时传入 `fps=24`，生成的视频文件属性显示帧率为 24fps。
开工前问题与风险

向维护者确认

修复 Wan2.2-I2V GGUF 权重加载的 Shape 不匹配问题

Issue #193 · May I ask if the gguf inference for wan2.2-i2v is supported? ↗

目标：使引擎能够成功加载 Wan2.2-I2V 的 GGUF 权重，解决 `patch_embedding.weight` 的 shape 冲突。

为什么值得长期做：GGUF 量化支持是端侧部署的核心特性，解决权重解析问题能展现对模型结构和量化格式的深刻理解，通向模型量化维护者的角色。

第一步：对比 Wan2.2 T2V 和 I2V 模型在 `patch_embedding` 层的通道数差异。
大致实施方案
  • 分析报错：GGUF 权重 shape 为 `[5120, 36, 1, 2, 2]`，而当前模型初始化为 `[5120, 16, 1, 2, 2]`。
  • 确认 I2V 模型因为需要输入条件图像（如 concat 潜变量），导致输入通道数从 16 增加到 36。
  • 在 `diffsynth_engine/models/wan/wan_dit.py` 的 `WanDiT` 初始化逻辑中，增加对 I2V 变体的判断，动态设置 `in_channels`。
  • 或者在 `from_state_dict` 中，根据传入的 `state_dict` 中 `patch_embedding.weight` 的 shape 动态调整模型结构。
  • 使用 CPU 模式加载 Issue 提供的 GGUF 权重路径进行验证。
可能涉及的目录或文件
  • diffsynth_engine/models/wan/wan_dit.py
  • diffsynth_engine/pipelines/wan_video.py
验收方式
  • 在 CPU 环境下，运行 Issue 中的代码片段，成功实例化 `WanVideoPipeline` 而不抛出 `size mismatch` 异常。
开工前问题与风险

向维护者确认

  • 对于 I2V 模型，除了 `patch_embedding` 通道数不同，是否还有其他结构差异需要在 `WanDiT` 中特殊处理？

风险

  • 动态修改模型结构可能会影响 TorchScript 导出或编译优化，需确保修改方式优雅。

实现支持 Batch Inference 的 HTTP API Server

Issue #235 · Question about batch inference support ↗

目标：提供一个基于 FastAPI 的 HTTP 服务端示例，支持接收 API 请求并进行 Batch 推理。

为什么值得长期做：构建高并发推理服务是 AI Infra 的核心领域，此功能将极大拓宽引擎在生产环境的应用场景，是成为核心架构贡献者的绝佳切入点。

第一步：设计 API 路由和 Batching 队列的架构方案。
大致实施方案
  • 在 `examples/` 目录下新建 `api_server.py`。
  • 引入 `FastAPI`，定义类似 OpenAI Image Generation 的请求和响应 Pydantic 模型。
  • 实现一个后台任务或队列机制（如使用 `asyncio.Queue`），收集短时间内的并发请求。
  • 当队列达到 `batch_size` 或超时时，将请求合并，调用 Pipeline 的 batch 推理接口（需确认 Pipeline 是否原生支持 batch prompt，若不支持需在 Pipeline 层增加支持）。
  • 将生成的图像拆分并返回给对应的 HTTP 响应。
  • 编写一个简单的 Python 客户端脚本，并发发送多个请求以测试 Batching 效果。
可能涉及的目录或文件
  • examples/需新建 api_server.py
  • diffsynth_engine/pipelines/base.py
验收方式
  • 启动 `api_server.py`，使用并发脚本发送 4 个生图请求，服务端日志显示它们被合并为 1 个 Batch 进行推理，且客户端均正确收到图像。
开工前问题与风险

向维护者确认

  • 目前各模型的 Pipeline 对 Batch Prompt 的支持程度如何？是否需要先在 Pipeline 层面统一完善 Batch 推理逻辑？
  • 是否希望 API 格式完全对齐 OpenAI 的 `/v1/images/generations` 规范？

风险

  • 动态 Batching 逻辑较为复杂，可能引入死锁或显存 OOM，需设置合理的超时和最大 Batch 限制。
