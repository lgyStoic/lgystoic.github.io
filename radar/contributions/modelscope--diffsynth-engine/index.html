修复 QwenImageDiT 在 Mac MPS 上的 LoRA 加载错误

Issue #224 · MAC Ultra pipe.load_lora raise an error "AttributeError: QwenImageDiT has no attribute `diffusion_model`" ↗

无人认领2 条评论更新 2026-01-19

用到的专长：PyTorch 模型结构解析与端侧部署调试。

目标：修复 `QwenImageDiT` 在调用 `load_lora` 时因缺少 `diffusion_model` 属性导致的 `AttributeError`。

为什么值得长期做：修复核心模型的 LoRA 加载逻辑，提升 Mac 用户的端侧部署体验，这是推理引擎的基础能力。

怎么介入：Issue 开放且无 assignee，无 linked PR，适合直接认领。
第一个 PR 的边界：仅修复 `QwenImageDiT` 的 LoRA 加载模块映射逻辑，并添加对应的轻量级测试。
第一步：检查 `diffsynth_engine/models/base.py` 和 `diffsynth_engine/pipelines/qwen_image.py` 中关于 LoRA 加载的逻辑，确认 `QwenImageDiT` 的层级结构。
认领留言（英文，可直接贴到 Issue）
Hi! I can help fix this issue. Since I'm working on Apple Silicon, I can easily reproduce and debug this MPS-related error. It seems `QwenImageDiT` has a different module hierarchy compared to what `load_loras` expects (`diffusion_model`). I will adjust the module mapping for Qwen models to correctly apply the LoRA weights. Could you confirm if the LoRA should be applied directly to the `QwenImageDiT` root module? I can submit a PR within 2 days.
大致实施方案
  • 在 Mac 上使用 CPU 或 MPS 模式初始化 `QwenImagePipeline`。
  • 追踪 `load_lora` 调用栈，发现 `QwenImageDiT` 继承或实现了 `load_loras`，但其内部结构与基类预期的 `diffusion_model` 不一致。
  • 修改 `QwenImageDiT` 的 `load_loras` 方法，或者在 `QwenImagePipeline` 中重写 `load_loras`，使其正确映射到 `QwenImageDiT` 的实际子模块。
  • 编写一个轻量级的单元测试，加载 dummy 权重验证 `load_lora` 不再抛出异常。
可能涉及的目录或文件
  • diffsynth_engine/pipelines/qwen_image.py
  • diffsynth_engine/models/base.py
  • diffsynth_engine/models/qwen/qwen_image_dit.py
验收方式
  • 在 Mac 上运行 Issue 中的复现脚本（可将模型替换为极小尺寸的 dummy 模型或仅初始化结构），断言 `pipe.load_lora` 成功执行且无报错。
开工前问题与风险

向维护者确认

  • `QwenImageDiT` 的 LoRA 权重应该直接应用在 `QwenImageDiT` 本身，还是其某个特定的子模块上？
  • 是否有推荐的 dummy 模型用于 CI 测试 LoRA 加载逻辑？

风险

  • 修复后可能导致其他模型的 LoRA 加载逻辑受影响，需确保修改仅针对 `QwenImageDiT` 或兼容所有模型。

修复 PyTorch 2.9+ 分布式模块导入兼容性

Issue #199 · Pytorch version problem ↗

无人认领6 条评论更新 2026-02-03

用到的专长：PyTorch 分布式底层机制与多版本兼容性适配。

目标：解决在 PyTorch 2.9.0+ 环境下 `torch.distributed.tensor.parallel._utils` 模块找不到的问题。

为什么值得长期做：保持对最新 PyTorch 版本的兼容性是推理引擎长期维护的关键，涉及分布式训练/推理的底层逻辑。

怎么介入：Issue 开放，有多个用户遇到（Issue 223 也是同类问题），无 linked PR，适合直接认领。
第一个 PR 的边界：修改 `parallel.py` 中的导入逻辑，增加对 PyTorch 2.9+ 的兼容。
第一步：调查 PyTorch 2.9.0 中 `_validate_tp_mesh_dim` 函数的最新位置或替代方案。
认领留言（英文，可直接贴到 Issue）
Hello! I'd like to fix this PyTorch 2.9 compatibility issue. It looks like the internal API `_validate_tp_mesh_dim` was moved or refactored in PyTorch 2.9. I will investigate its new location and implement a fallback/version-check mechanism in `diffsynth_engine/utils/parallel.py` to ensure compatibility across PyTorch versions. I can test this locally on my Mac with PyTorch nightly and submit a PR within a day.
大致实施方案
  • 在 Mac 上创建一个安装了 PyTorch 2.9.0 (nightly) 的虚拟环境。
  • 运行 `examples/wan_text_to_video.py` 触发 `ModuleNotFoundError`。
  • 查阅 PyTorch 源码，找到 `_validate_tp_mesh_dim` 在 2.9.0 中的新路径（可能是被重构或移动到了其他内部模块）。
  • 在 `diffsynth_engine/utils/parallel.py` 中使用 `try...except ImportError` 或版本检查 (`torch.__version__`) 来兼容不同版本的 PyTorch 导入路径。
  • 确保在 CPU/Mac 环境下，即使不实际运行分布式推理，导入阶段也不会报错。
可能涉及的目录或文件
  • diffsynth_engine/utils/parallel.py
验收方式
  • 在 PyTorch 2.9.0 环境下执行 `python -c "from diffsynth_engine.utils.parallel import *"` 无报错。
开工前问题与风险

向维护者确认

  • 除了 `_validate_tp_mesh_dim`，是否还有其他依赖的内部 API 在 PyTorch 2.9 中发生了变化？

风险

  • 依赖 PyTorch 内部 API (`_utils`) 容易在版本更新时断裂，建议寻找公开 API 替代。

提供基于 FastAPI 的 Batch Inference HTTP Server 示例

Issue #235 · Question about batch inference support ↗

无人认领0 条评论更新 2026-02-12

用到的专长：纯逻辑层开发与服务端部署架构。

目标：提供一个基于 FastAPI 的 HTTP Server 示例脚本，支持接收请求并调用 Pipeline 进行 Batch Inference。

为什么值得长期做：扩展引擎的服务化部署能力，帮助用户将 DiffSynth-Engine 投入生产环境，提升项目的生态价值。

怎么介入：Issue 开放，属于功能咨询，无 assignee，适合通过贡献示例代码来响应。
第一个 PR 的边界：新增 `examples/fastapi_batch_server.py` 及其使用文档，不涉及核心引擎的破坏性修改。
第一步：检查现有 Pipeline 的 `__call__` 方法是否原生支持 batch size > 1 的 prompt 列表输入。
认领留言（英文，可直接贴到 Issue）
Hi! I can contribute an example script for this. I plan to create a FastAPI-based HTTP server in the `examples/` directory that demonstrates how to wrap the pipeline for batch inference. Could you clarify if the current pipelines natively support passing a list of prompts (e.g., `prompt=["cat", "dog"]`) for batching, or should I implement dynamic batching at the server level? I can get a draft PR ready in a few days.
大致实施方案
  • 编写一个简单的 FastAPI 应用，定义 `/generate` 接口，接收 JSON 格式的 prompt 列表。
  • 在服务端初始化一个轻量级的 Pipeline（如使用 dummy 模型或极小模型以便在 CPU 上测试）。
  • 验证 Pipeline 是否支持传入 `List[str]` 作为 prompt。如果不支持，在 HTTP server 中实现简单的请求批处理（Dynamic Batching）或循环处理。
  • 将代码整理为 `examples/fastapi_batch_server.py`，并添加对应的 README 说明。
可能涉及的目录或文件
  • examples/
  • diffsynth_engine/pipelines/base.py
验收方式
  • 在 CPU 上启动 FastAPI server，使用 `curl` 发送包含多个 prompt 的请求，验证返回多张图片（或图片的 base64 编码）。
开工前问题与风险

向维护者确认

  • 目前的 Pipeline 是否原生支持传入 `List[str]` 作为 prompt 来实现 batch inference？如果不支持，是否希望我在 Pipeline 层面添加支持，还是仅在 server 示例中通过循环处理？

风险

  • 如果底层模型或调度器硬编码了 batch size = 1，可能需要较多修改。建议先在 server 层实现请求队列和批处理逻辑。
