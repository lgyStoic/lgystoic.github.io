modelscope/DiffSynth-Engine

高度匹配。候选人具备资深的 GPU kernel、分布式训练性能和量化部署经验，非常契合 DiffSynth-Engine 作为高性能扩散模型推理引擎的定位。候选人可以在核心算子优化（如 Flash Attention）、分布式推理（Ring SP）以及量化模型（GGUF）支持方面发挥巨大价值。

当前方向：从最近的 Release 和 Commit 来看，项目正集中于支持最新的 DiT 视频/图像生成模型（如 Wan2.2, Qwen-Image），并积极优化底层推理性能（如引入 NPU 支持、Ulysses/Ring SP 分布式推理、Flash Attention 优化）。

修复 Wan2.2-I2V GGUF 模型加载的维度不匹配问题

Issue #193 · May I ask if the gguf inference for wan2.2-i2v is supported? ↗

无人认领2 条评论更新 2025-11-05

用到的专长：端侧部署（量化）、PyTorch 模型架构

目标：修复 `WanDiT` 加载 Wan2.2-I2V GGUF 权重时 `patch_embedding.weight` 的 shape mismatch 问题（36 vs 16），使其能成功运行推理。

为什么值得长期做：完善对主流开源模型（Wan2.2）及量化格式（GGUF）的支持，是推理引擎扩大用户基础的关键。解决此类问题能帮助你快速熟悉引擎的模型加载与转换架构，为后续的量化算子优化打下基础。

怎么介入：Issue 处于 open 状态，无 assignee，无 linked PR。可直接认领并提交修复 PR。
第一个 PR 的边界：修改 `wan_dit.py` 和 `wan_video.py`，修复 I2V 模型的通道数配置逻辑。
第一步：调查 Wan2.2-I2V 模型的 patch_embedding 维度定义，定位代码中写死或计算错误的输入通道数。
认领留言（英文，可直接贴到 Issue）
Hi! I'd like to look into this issue. The shape mismatch (36 vs 16) suggests the `patch_embedding` in `WanDiT` needs to handle the additional input channels for the I2V task (likely concatenated reference image latents). I will investigate the config parsing in `wan_video.py` and submit a PR to dynamically adjust the channels based on the GGUF weights. Expect a PR in 2-3 days.
大致实施方案
  • 下载 Issue 中提到的 GGUF 模型权重（Wan2.2-I2V-A14B-LowNoise-Q4_K_S.gguf）。
  • 检查 `diffsynth_engine/models/wan/wan_dit.py` 中 `WanDiT` 的初始化逻辑，特别是 `patch_embedding` 的 `in_channels` 计算。
  • 对比 Wan2.2-I2V 和 T2V 模型的结构差异，确认 I2V 的输入通道数（36）是因为拼接了参考图像或噪声。
  • 修改 `WanVideoPipeline._from_state_dict` 或 `WanDiT` 的配置解析逻辑，根据权重 shape 动态推断 `in_channels`，或在 config 中增加区分 I2V/T2V 的标志。
  • 编写测试脚本，验证 GGUF 权重加载成功并能正常生成视频张量。
可能涉及的目录或文件
  • diffsynth_engine/models/wan/wan_dit.py
  • diffsynth_engine/pipelines/wan_video.py
验收方式
  • 运行 Issue 提供的代码片段，不再抛出 `RuntimeError: Error(s) in loading state_dict`。
  • 模型能够成功加载并完成一次 dummy 推理，输出正确 shape 的张量。
开工前问题与风险

向维护者确认

  • 目前引擎内是否有区分 Wan2.2 T2V 和 I2V 的标准配置字段？
  • Wan2.2-I2V 的 GGUF 支持是否需要特殊的反量化算子，还是复用现有的即可？

风险

  • GGUF 格式可能不仅是 shape 问题，还可能涉及特定的量化反量化逻辑，需确认引擎现有的 GGUF loader 是否完全兼容 Wan2.2 的量化方式。
