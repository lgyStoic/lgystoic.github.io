vllm-project/vllm

候选人作为资深 GPU kernel 与训练性能工程师，虽然目前受限于无 GPU 硬件（仅有 Mac 和 Colab T4），但完全可以利用其在 PyTorch 底层、算子数值正确性、内存管理、Triton 编译期分析以及调度器逻辑方面的深厚积累，在 vLLM 的纯逻辑层、CPU 参考实现和测试基建中发挥巨大价值。推荐的任务均避开了需要高端 GPU 复现的场景，专注于 CPU/Mac 可验证的硬核逻辑与性能优化。

当前方向：vLLM 目前正致力于多硬件后端的扩展（如 CPU、AMD、XPU）、复杂模型架构的支持（如 DeepSeek V4、GLM-5）、以及调度器和内存管理的精细化（如 Chunked Prefill、优先级调度、PD 分离）。

目标：修改调度器逻辑，使得当 running queue 满时，waiting queue 中的高优先级请求能够抢占 running queue 中的低优先级请求。

为什么值得长期做：调度器是 vLLM 的心脏，实现高级抢占逻辑能够显著提升引擎在复杂生产环境下的 QoS（服务质量），是核心调度逻辑的深度参与。

怎么介入：Issue 开放，无 assignee，无 linked PR。这是一个纯逻辑层的硬核功能，非常适合资深工程师。
第一个 PR 的边界：在调度器中实现基于优先级的 running queue 抢占逻辑，并附带完整的单元测试。
第一步：深入阅读 vllm/core/scheduler.py，特别是 _schedule() 和抢占（preemption）相关的逻辑。
认领留言（英文，可直接贴到 Issue）
Hello! I'd like to implement this priority preemption feature. I will modify `vllm/core/scheduler.py` so that when the running queue is full, the scheduler evaluates if high-priority waiting requests can preempt lower-priority running ones. I'll implement the logic to swap/recompute the preempted requests and add comprehensive unit tests to verify the state machine transitions. Could you confirm if this behavior should be gated behind a new scheduler config flag?
大致实施方案
  • 在调度 waiting queue 时，如果因资源不足（如达到 max_num_seqs 或 KV cache 不足）无法调度高优先级请求，扫描 running queue。
  • 找出 running queue 中优先级低于当前 waiting 请求的 sequence groups。
  • 触发抢占（如 recompute 或 swap），将低优先级请求移回 waiting queue。
  • 为高优先级请求分配资源并将其移入 running queue。
  • 编写详尽的单元测试，模拟不同优先级的请求到达顺序，验证抢占逻辑的正确性。
可能涉及的目录或文件

验收方式

向维护者确认
