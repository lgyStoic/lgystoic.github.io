一、项目定位

edge-dit.cpp 是清华大学 THU-MIG 实验室在 2026 年推出的一个面向 Diffusion Transformer（DiT）的原生 C/C++ 推理引擎，底层直接复用 ggml 的张量与图执行基础设施，目标是在本地和资源受限设备上跑通 FLUX.1/FLUX.2、SD3/SD3.5、Qwen-Image、Wan 2.1、MiniMax-H3 等主流 DiT 家族，覆盖文生图、图像编辑、视频生成三类任务。项目定位非常明确：把原本依赖 PyTorch + Python 的 DiT 推理栈，下沉到无 Python 运行时、显存受限、需要显式控制张量/图/内存/设备位置的端侧场景。 从 README 的徽章和措辞看，项目目前处于 alpha / public preview 阶段（v0.1.0-alpha，2026-07-11 首次公开），API、ABI、CLI 与 HTTP schema 都声明为 public but not yet stable。后端成熟度分层明显：CUDA 是一等公民（first-class），CPU 可用（可选 oneDNN bf16 AMX matmul），Vulkan 可用但比 CUDA 慢约 1.3×，Metal 标为 experimental。 与同类的关系：它不是从零写一套 DiT 推理，而是站在 ggml 之上做 DiT-first 的垂直整合——相当于把 stable-diffusion.cpp 的思路从 UNet 时代推进到 DiT 时代，同时把 FLUX/Qwen-Image/Wan/MiniMax-H3 这些新架构统一到一个运行时里。项目在 RTX 4090 和 H200 上给出了与 Diffusers、stable-diffusion.cpp 的逐模型对比，证明它已经越过「能跑」阶段，进入「比 PyTorch 参考实现更快且更省显存」的工程化区间。 从提交热点看，最近一个月的工作集中在 src/dit_models（39 次） 和 src/core（12 次），说明模型覆盖和核心执行路径仍在快速迭代；bindings/python、examples/server、examples/cli 也在同步跟进，整体处于「先把 CUDA 打磨到 production-ready，再把 Metal/Vulkan 追上来」的节奏。

解决什么问题、给谁用

解决的核心问题是：DiT 类扩散模型（FLUX、SD3、Qwen-Image、Wan、MiniMax-H3 等）在端侧、本地、显存受限设备上难以高效、无 Python 依赖地运行。具体痛点包括： 1. 显存墙：20GB+ 的 DiT 权重在 24GB 甚至更小的 GPU 上无法常驻，需要 layered offload、per-component offload、VAE tiling、自动量化（--auto-fit）等显式内存管理。 2. 运行时依赖：主流参考实现（Diffusers）强依赖 PyTorch + Python，在嵌入式、移动端、桌面原生应用里部署成本高。 3. 模型碎片化：不同 DiT 家族（SD3、FLUX、Qwen-Image、Wan、MiniMax-H3）各自有独立的加载、调度、量化路径，缺乏统一运行时。 4. 少步蒸馏模型：Turbo/Lightning/schnell 等 few-step 变体需要自动识别并切换到 4–8 step schedule。 5. 多后端一致性：需要在 CUDA、CPU、Vulkan、Metal 之间提供同一套 C API / CLI / HTTP / Python 接口。 目标用户：需要在本地或资源受限设备上部署 DiT 推理的工程师——包括桌面应用开发者、端侧 AI 工程师、需要把生成式 AI 嵌入到 C/C++ 产品中的团队，以及研究 DiT 推理优化的性能工程师。 典型使用场景： - 桌面/移动端原生应用里跑 FLUX.1、Qwen-Image、Wan 2.1 文生图/视频 - 服务端用 C API 或 HTTP server 集成到现有 C++ 管线 - 用 Python bindings 做快速原型，再切到原生部署 - 用 ed-convert 离线量化 GGUF，避免每次加载都做 CPU 量化 - 多卡场景用 NCCL/MPI 做 CFG parallelism 或 sequence parallelism

同类项目与差别

  • stable-diffusion.cpp (leejet/stable-diffusion.cpp)：edge-dit.cpp 的直接上游参考之一，同样基于 ggml。但 sd.cpp 主要覆盖 UNet 时代的 SD1.5/SD2/SDXL/SD3，对 FLUX.1/FLUX.2、Qwen-Image、Wan 2.1、MiniMax-H3 等新一代 DiT 家族的覆盖不如 edge-dit.cpp 完整。edge-dit.cpp 在 README 的性能对比中直接以 sd.cpp 为 baseline，并在多数任务上取得更低的 DiT 采样延迟和峰值 VRAM。
  • Diffusers (huggingface/diffusers)：PyTorch 参考实现，功能最全但依赖 Python + PyTorch 运行时。edge-dit.cpp 的目标是在端侧/原生场景替代 Diffusers，消除 Python 依赖，并通过 layered offload、auto-fit、VAE tiling 等手段在 24GB 显存下跑通 Diffusers 需要更大显存的模型。README 中 4090/H200 对比表显示 edge-dit.cpp 在多数任务上比 Diffusers 更快且更省显存。
  • ComfyUI (Comfy-Org/ComfyUI)：面向工作流编排的 Python 前端，底层仍依赖 PyTorch/Diffusers。edge-dit.cpp 不是前端/工作流工具，而是底层原生推理引擎，可被 ComfyUI 之类的前端通过 C API 或 HTTP server 调用。
  • ggml (ggml-org/ggml)：edge-dit.cpp 的底层 tensor/graph 运行时。edge-dit.cpp 在 ggml 之上添加了 DiT 专用的模型加载、调度、量化、offload、CUDA 算子（cuDNN SDPA、fused modulation、RoPE、norm、SageAttention 等）以及多后端统一接口。
  • TensorRT / ONNX Runtime：NVIDIA 官方的推理优化栈，需要模型导出和构建阶段。edge-dit.cpp 走的是「直接加载 Diffusers/safetensors/GGUF 权重、运行时即时执行」的路线，更接近 llama.cpp/sd.cpp 的生态，不需要提前导出 ONNX/TRT engine。

二、架构与代码地图

edge-dit.cpp 在 ggml 之上构建了一个 DiT-first 的垂直推理栈，可划分为五层。 1) 接入层（Access Layer）：统一对外暴露 C API、CLI、HTTP Server、Python bindings 四种入口，所有请求最终汇聚到同一个 C++ 引擎对象。关键文件包括 include/edge-dit.h、src/edge_dit.cpp、examples/cli、examples/server、bindings/python。 2) 调度层（Scheduling Layer）：以 EdgeDitEngine 为核心，负责把用户参数翻译成运行时配置、选择并初始化 ggml 后端、加载模型权重、构造具体的 DiTPipeline（Flux/SD3/Qwen-Image/Wan/MiniMax-H3/LTX2 等），并把生成请求派发到对应 pipeline。关键文件集中在 src/core/runtime（edge_dit_engine.cpp/hpp、model_runtime.cpp/hpp、model_loader.cpp/h）和 src/dit_models/pipelines。 3) 执行层（Execution Layer）：每个 DiTPipeline 子类实现一次扩散采样循环——文本编码、VAE 编解码、扩散主干前向、scheduler 步进、CFG/parallel 切分；同时通过 ModelRuntime 管理 ggml 后端、内存规划与张量注册。关键文件为 src/dit_models/pipelines/*_pipeline.cpp/hpp 与 src/dit_models/diffusion_model.hpp。 4) Kernel / 算子层（Kernel Layer）：在 ggml 后端之上提供 DiT 专属算子扩展——CUDA 上的 fused modulation、RoPE、norm、SageAttention、cuDNN SDPA、async offload，以及图切分（ggml_graph_cut）、量化 GGUF IO、imatrix 校准。关键文件在 src/core/backend（ggml/、cuDNN/）和 src/utils/model_io。 5) 工具与基础设施层（Tooling & Infra）：提供构建脚本、benchmark 套件、Python 测试、权重转换/量化工具、第三方依赖（ggml、httplib、json、stb、oneDNN）。关键目录为 scripts、benchmark、tools/imatrix、third_party、bindings/python/tests。

一次调用怎么流过这些模块

一次典型文生图请求从 CLI/Python/HTTP 进入，最终由 EdgeDitEngine 统一调度。 1) 参数接入：用户通过 ed-cli 命令行或 Python edge_dit.Engine 传入 ed_ctx_params_t（模型路径、backend、设备、offload 策略、quant 等）和 ed_image_generation_params_t（prompt、size、steps、seed、cfg scale 等）。C API 层把这些结构体跨语言边界传到引擎。 2) 引擎初始化（EdgeDitEngine::init）：引擎根据 ed_ctx_params_t 构造 ModelRuntime，调用 ggml_backend_load_all_once 枚举设备，按 ED_BACKEND 选择 CPU/CUDA/Metal/Vulkan 并初始化 RuntimeBackends（主后端 + clip/vae/control_net 独立后端）。随后构造 ModelLoader 读取 safetensors/GGUF 权重，得到 TensorMap。再通过 create_dit_pipeline 按 SDVersion 选择具体 DiTPipeline（如 FluxPipeline），调用 pipeline->prepare() 把权重注册到 ggml 张量、构建计算图骨架。若启用 parallel，还会构造 ParallelContext 并配置 CFG/SP/TP 切分。 3) 生成请求（EdgeDitEngine::generate_image）：引擎调用对应 pipeline->generate_image()。以 FLUX 为例，FluxPipeline 先通过 Conditioner（CLIP-L + T5XXL 或 FLUX.2 的 LLM）把 prompt 编码为 context tensor，经 scheduler（如 flow match Euler）在 timestep 循环中反复执行 diffusion 主干：对每个 step，构建 ggml 图（modulation → RoPE → attention → norm → FFN），在 CUDA 上可能走 ed_cuda_* 扩展算子或 cuDNN SDPA，并通过 GraphCut 实现 block-by-block layered offload；CacheEngine 在相邻 step 间复用 attention 结果。CFG 并行时 cfg_parallel 会把 batch 拆成 conditional/unconditional 两路。 4) 输出：扩散循环结束后得到 latent，经 VAE 解码为像素图像，填入 ed_image_batch_t 返回给调用方；CLI 进一步通过 stb_image_write 落盘，HTTP server 经 httplib 返回，Python binding 包装成 PIL/numpy。 5) 进度与取消：GenerationControl 原子变量在每一步更新 current_step/total_steps，并支持 request_cancel 中断。 关键调度点包括：create_dit_pipeline 的版本分派、ModelRuntime 的后端选择、DiTPipeline::prepare 的图构建、CacheEngine 的 capability negotiation、cfg_parallel 的 batch 切分、GraphCut 的图块边界。

坑

  • submodule 缺失：未 --recursive 克隆后必须 git submodule update --init --recursive 或 bash scripts/bootstrap.sh，否则 ggml/oneDNN 缺失导致 CMake 失败。
  • Metal 是 experimental：README 与 CMakeLists.txt ED_GGML_METAL 默认 OFF，性能与稳定性不及 CUDA，不要假设能跑通所有模型。
  • CPU 推理极慢且耗内存：FLUX/Qwen-Image/Wan 在 CPU 上 16GB 统一内存易 OOM 或耗时数十分钟，仅用于功能验证；真实性能验证必须 Colab T4。
  • 真实推理测试默认跳过：test_optional_real_smoke.py / test_optional_real_server_smoke.py 需 EDGE_DIT_RUN_INTEGRATION=1 + 本地模型路径，否则 skip，勿误判为失败。
  • CUDA 相关选项在 macOS 不可用：ED_GGML_CUDA / ED_ENABLE_NCCL / ED_ENABLE_CUDNN_ED 等需 NVIDIA GPU，本地只能读代码。
  • oneDNN bf16 AMX 需预编译：build_cpu.sh 仅在 third_party/onednn/install 存在时启用，否则回退纯 CPU matmul；可用 ED_ONEDNN=0 强制关闭。
  • v0.x API/ABI/CLI/HTTP schema 不稳定（README 明确声明），绑定与脚本可能随提交变化。
