一、项目定位

edge-dit.cpp 是 THU-MIG 实验室在 2026 年 5 月底启动的 C/C++ 原生 DiT 推理引擎，定位为「把 Diffusion Transformer 搬到本地和资源受限设备上」。它基于 ggml 张量/图运行时构建，不依赖 Python 或 PyTorch 即可运行，覆盖文本到图像、图像编辑、视频生成三类任务，支持 FLUX.1/FLUX.2、SD3/SD3.5、Qwen-Image、Wan 2.1、MiniMax-H3 等主流 DiT 家族。项目 2026-07-11 发布 v0.1.0-alpha 公开预览，README 顶部徽章明确标为 alpha，Metal 标 Experimental、Vulkan 标 Functional 但仍在优化。核心卖点是 VRAM 感知的自动精度/分层 offload：--auto-fit 一条 flag 自动选择 DiT 量化档位（q8_0→q4_K）和组件放置，layered offload 在 CUDA 上以 async double-buffered 方式逐 block 流式搬运，使 20GB+ 模型能在 24GB 卡上跑。性能上，README 给出 RTX 4090 和 H200 两张对比表，显示它在多数任务上比 Diffusers 和 stable-diffusion.cpp 更快且更省 VRAM。项目非常年轻，提交热点集中在 src/dit_models（39 次）、src/core（12 次）、bindings/python（8 次），说明仍在快速扩展模型覆盖和打磨核心路径。

解决什么问题、给谁用

解决的具体问题：把原本依赖 PyTorch + 高端 GPU 的 DiT 推理搬到本地/边缘设备，在有限 VRAM 下仍能跑大模型。目标用户：需要在端侧、桌面或单卡服务器上部署 DiT 的工程师——包括端侧 AI 应用开发者、扩散模型应用产品化团队、想把推理从 Python 栈迁到 C/C++ 原生运行时的性能工程师。典型场景：在 24GB 消费卡上跑 FLUX.1-dev / Qwen-Image / MiniMax-H3 视频生成；在 macOS 上用 Metal 做本地原型；在跨平台设备上走 Vulkan；通过 Python bindings 或 HTTP server 把推理嵌入产品；用 ed-convert 离线量化一次 GGUF 避免每次加载都做 CPU 量化。

1) 端侧/桌面 AI 应用开发者——需要无 Python 依赖、可嵌入 C/C++ 或 Python 的 DiT 运行时；2) 扩散模型应用产品化团队——需要 CLI、HTTP server、Python 多接口，以及 VRAM 预算可控的自动 offload；3) 推理性能工程师——关注 CUDA 算子、分层 offload、量化、并行执行，想在一个干净 C/C++ 代码库里做 kernel 级优化；4) 学术/工业研究人员——想在资源受限设备上跑 FLUX / SD3 / Qwen-Image / Wan / MiniMax-H3 并对比不同精度/放置策略。

同类项目与差别

  • stable-diffusion.cpp (leejet)：edge-dit.cpp 直接 fork/参考了它的 DiT 实现，但把重心转到 DiT-first：更激进的 VRAM-aware auto-fit、layered block-level offload、CUDA 专用 RoPE/modulation/norm 快路径、SageAttention、NCCL/MPI 多 worker 并行；sd.cpp 更偏 UNet 传统扩散模型，DiT 支持相对基础。
  • ComfyUI + Diffusers (Python 生态)：edge-dit.cpp 是纯 C/C++ 原生运行时，无 Python/PyTorch 依赖，面向部署而非研究原型；Diffusers 灵活但重，ComfyUI 是工作流 UI。edge-dit.cpp 在 4090/H200 上比 Diffusers 更快且 VRAM 更低，代价是生态和灵活性。
  • GGML/llama.cpp 生态：edge-dit.cpp 基于 ggml 张量/图基础设施，但专门为 DiT 设计——引入 diffusion 专用调度、DiT 块、VAE tiling、text encoder offload、few-step distilled 自动调度等，是 ggml 在 LLM 之外的扩散模型延伸。
  • TensorRT / ONNX Runtime：TensorRT 是 NVIDIA 官方高性能推理栈，需构建 engine、平台锁定；edge-dit.cpp 是开源跨平台 C/C++ 运行时，支持 CUDA/Vulkan/Metal/CPU，自带 GGUF 量化与 auto-fit，更易在非 NVIDIA 平台移植。

二、架构与代码地图

edge-dit.cpp 的架构可以清晰地划分为五层，自顶向下分别是：接入层（Access Layer）、调度层（Scheduling Layer）、执行层（Execution Layer）、后端层（Backend Layer）和工具层（Tooling Layer）。 接入层负责接收外部请求并转化为内部统一的生成任务。它包含 CLI（examples/cli）、HTTP Server（examples/server）、Python bindings（bindings/python）以及底层的 C API（include/edge-dit.h）。这一层将用户输入的 prompt、图像、配置参数等，封装成 ed_ctx_params_t、ed_image_generation_params_t 等 C 结构体，向下传递给调度层。 调度层是整个引擎的大脑，核心是 EdgeDitEngine（src/core/runtime/edge_dit_engine.cpp）。它负责生命周期管理、模型加载调度、并行上下文初始化、以及将请求分派到正确的 Pipeline。调度层会根据模型版本（SDVersion）通过 create_dit_pipeline 工厂方法创建对应的 Pipeline 实例（如 FluxPipeline、SD3Pipeline、WanPipeline 等），并协调 ModelRuntime 和 ModelLoader 完成权重加载与后端初始化。 执行层由各个具体的 Pipeline 实现构成（src/dit_models/pipelines/），每个 Pipeline 封装了特定模型家族的完整推理流程，包括文本编码、扩散采样、VAE 解码等步骤。执行层还包含 dit_models/components/ 下的可复用组件（如 text encoders、VAEs、super resolution、adaptors 等），以及 diffusion_model.hpp 等扩散模型抽象。 后端层基于 ggml 张量运行时构建，提供实际的计算能力。它包括 ggml 后端封装（src/core/backend/ggml/）、CUDA 优化算子（src/core/backend/ggml/cuda/，如 ed_cuda_attention、ed_cuda_rope、ed_cuda_norm、ed_async_offload 等）、cuDNN 后端（src/core/backend/cuDNN/）、以及并行通信模块（src/core/parallel/，支持 NCCL、CPU、CFG/SP 并行）。这一层直接与硬件交互，管理显存分配、kernel 执行和跨设备通信。 工具层提供离线转换、量化、基准测试等辅助功能。包括 ed-convert（src/utils/model_io/convert.cpp）、imatrix 校准（tools/imatrix/）、benchmark 框架（benchmark/）、以及各类构建脚本（scripts/）。 这种分层设计使得上层接口可以统一处理不同模型家族，而下层后端可以独立优化，同时保持模型特定逻辑的隔离性。

一次调用怎么流过这些模块

一次典型的文本到图像推理请求（以 FLUX.1-dev 为例）的数据流如下： 1. 请求入口：用户通过 CLI（examples/cli/main.cpp）或 HTTP Server（examples/server/main.cpp）发起请求，传入 prompt、分辨率、步数等参数。这些参数被封装为 ed_ctx_params_t（引擎配置）和 ed_image_generation_params_t（生成参数）结构体。 2. 引擎初始化：EdgeDitEngine::init() 被调用。该方法首先解析 ed_ctx_params_t，检测并行配置（从 WORLD_SIZE、RANK 等环境变量推断），创建 ParallelContext。然后初始化 ModelRuntime，根据 ED_BACKEND 环境变量或配置选择 ggml 后端（CPU/CUDA/Metal/Vulkan），创建 RuntimeBackends（可能为 CLIP、VAE、DiT 使用不同后端）。接着创建 ModelLoader 并开始加载权重（从 Diffusers 目录、safetensors 或 GGUF）。 3. Pipeline 创建与准备：根据模型版本（SDVersion），通过 create_dit_pipeline() 工厂方法创建 FluxPipeline。调用 DiTPipeline::prepare()，该方法协调 ModelLoader 加载权重到 PipelineTensorRegistry（tensor 注册表），初始化内部组件（FluxRunner、Conditioner、VAE），并调用 prepare_memory_plan() 进行显存规划（auto-fit 或手动配置）。 4. 文本编码：EdgeDitEngine::generate_image() 调用 dit_pipeline_->generate_image()。Pipeline 首先通过 Conditioner（text_encoders/conditioner.hpp）对 prompt 进行编码。FLUX 使用 CLIP-L 和 T5XXL 两个文本编码器，分别加载到 clip_backend 和 conditioner_backend 上。Tokenizer（如 T5 unigram tokenizer）将文本转为 token IDs，然后通过 LLM/T5 encoder 生成 text embeddings。 5. 扩散采样循环：这是核心推理步骤。Pipeline 进入采样循环（通常 20 步），每步执行： - 噪声调度：根据 scheduler（如 Euler、Flow Match）计算当前 timestep 的噪声尺度 - DiT Forward：通过 FluxRunner 执行 DiT transformer 的前向计算。这一步涉及多个 CUDA kernel（如 ed_cuda_attention_v_prep、ed_cuda_rope、ed_cuda_norm、ed_cuda_modulation），如果使用 layered offload，还会通过 ggml_graph_cut 和 ed_async_offload 逐 block 在 CPU 和 GPU 之间流式搬运权重 - CFG Parallel：如果启用 cfg_parallel，通过 CFGParallel 模块一次前向同时处理 conditional 和 unconditional 预测 - Cache Reuse：如果启用 cache 策略（如 EasyCache、MagCache），通过 CacheEngine 跳过某些 block 或 timestep 的计算 - 进度更新：更新 GenerationControl.current_step 6. VAE 解码：采样完成后，通过 VAE（autoencoders/auto_encoder_kl.hpp）将 latent 图像解码为像素图像。VAE 可能运行在独立的 vae_backend 上，支持 tiling 以降低显存占用。 7. 输出：生成的图像通过 ed_image_batch_t 返回给调用方。CLI 将其保存为 PNG（通过 stb_image_write），HTTP Server 通过 httplib.h 返回，Python bindings 转为 numpy array。 关键调度点包括：EdgeDitEngine::generate_image/video（请求分发）、DiTPipeline::generate_image（Pipeline 内部调度）、ModelRuntime::select_backend（设备选择）、ggml_graph_cut（图切割用于 offload）、CacheEngine（计算复用决策）。关键数据结构包括 ed_ctx_params_t（引擎配置）、RuntimeBackends（后端管理）、PipelineTensorRegistry（tensor 注册表）、GenerationControl（进度/取消控制）。

  • submodule 没拉齐：缺少 ggml / onednn / json.hpp / httplib.h / stb 任一都会直接编译失败；务必先 bash scripts/bootstrap.sh 或 git submodule update --init --recursive

  • CPU 推理极慢：16GB MacBook Air 跑 1024×1024 / 20 steps 的 FLUX.1-dev 不现实；冒烟测试务必用 ≤64×64 / 4 steps 或已经量化到 q4_K 的小模型，否则会触发 OOM 或等到超时
  • 真实模型集成测试默认关闭：EDGE_DIT_RUN_INTEGRATION 相关用例（test_optional_real_smoke.py、test_optional_real_server_smoke.py）需要显式环境变量 + 本地 GGUF 路径，不要在没准备权重时直接跑全量 pytest 然后误判为失败
  • ed-convert 离线量化是独立可执行文件（examples/cli/convert_main.cpp 编译出的 ed-convert），不要和 ed-cli 混淆；量化一次 GGUF 可避免每次加载都做 CPU 量化

  • 模型加载支持 Diffusers 目录 / safetensors / GGUF，但 GGUF 是推荐的生产格式（跳过 CPU 量化）；safetensors 每次加载都会做 CPU 量化，首次加载很慢
  • 并行（CFG/TP/SP）需要 ED_ENABLE_PARALLEL=ON 且配合 WORLD_SIZE/RANK 环境变量，单 Mac 上这些路径基本只能读代码，无法本地验证
  • 项目非常年轻（v0.1.0-alpha，2026-07-11 公开预览），API/ABI/CLI flag/HTTP schema 都不稳定，读代码时不要过度依赖当前命名
