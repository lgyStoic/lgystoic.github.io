一、项目定位

edge-dit.cpp 是一个专为资源受限设备和边缘计算设计的轻量级、原生 C/C++ 扩散式 Transformer (DiT) 推理引擎。它基于 ggml 构建，完全脱离 Python 和 PyTorch 运行时，旨在统一图像生成、图像编辑以及复杂的视频/音频生成（如 FLUX、SD3、Wan、MiniMax-H3）的本地部署。项目目前处于 v0.1.0-alpha 公开预览阶段，正处于快速迭代期。 对于你这位资深 GPU kernel 与训练性能工程师而言，该项目的底层架构高度契合你的技能树：它在 CMakeLists.txt 中显式暴露了大量 CUDA 深度优化选项（如融合 Norm、RoPE、cuDNN SDPA 以及 SageAttention），并罕见地在端侧引擎中引入了基于 NCCL/MPI 的分布式并行推理（ED_ENABLE_PARALLEL）。同时，它原生支持 GGUF 离线量化（含 imatrix 激活校准）与细粒度的张量级显存卸载。 针对你的硬件硬约束（仅有 16GB Apple Silicon Mac，无本地 GPU，仅能短暂使用 Colab T4）：这是你切入该项目的核心策略。虽然项目将 CUDA 视为一等公民，但它通过 ggml 提供了 CPU 和 Metal 后端。你的日常开发与逻辑验证将完全依赖 scripts/build_metal.sh 和 scripts/build_cpu.sh。由于 Mac 和 Colab T4 都只有 16GB 内存/显存，项目核心的 --auto-fit（自动 VRAM 感知量化与放置）和分层卸载（Layered offload）机制将是你最常测试的模块。你可以利用 Mac 的统一内存优化目前仍处于“实验性”的 Metal 后端算子，随后在 Colab T4 上通过 --max-vram 验证 CUDA 显存天花板下的异步双缓冲卸载逻辑。你的算子融合与量化经验，可以直接用于补齐 Metal 后端的性能短板。

解决什么问题、给谁用

解决超大参数量 DiT 模型（如 20GB+ 的 FLUX 或 MiniMax-H3）在显存受限的消费级 GPU 或边缘设备（如 24GB 4090、16GB Mac/T4）上无法完整加载运行的问题，同时消除 Python/PyTorch 带来的运行时开销与依赖臃肿。

边缘设备开发者、本地 AI 部署工程师、以及需要在消费级硬件上进行高性能图像/视频/音频生成（Text-to-image, Video+Audio generation）的研究人员与极客。

同类项目与差别

  • stable-diffusion.cpp：两者均基于 ggml 构建。但 edge-dit.cpp 是纯粹的“DiT-first”，支持最新且更复杂的视频/音频多模态模型（如 MiniMax-H3、Wan 2.1），并且在 README 的 RTX 4090 基准测试中，edge-dit.cpp 在端到端延迟和峰值显存控制上均优于 sd.cpp。
  • Diffusers (HuggingFace)：Diffusers 依赖庞大的 Python/PyTorch 生态，而 edge-dit.cpp 是纯 C/C++ 原生运行时，零 Python 依赖。在同等精度（w8 vs q8_0）下，edge-dit.cpp 提供了更快的推理速度和更低的显存占用，并支持离线 GGUF 量化。
  • TensorRT：TensorRT 深度绑定 NVIDIA 硬件且缺乏跨平台便携性。edge-dit.cpp 强调多后端（CUDA, Metal, Vulkan, CPU）统一，并通过 --auto-fit 和分层卸载在极低显存下动态调度，更适合异构和资源受限环境。

二、架构与代码地图

edge-dit.cpp 的架构设计呈现出典型的「C API 驱动 + 核心引擎 + 算子后端」三层加两翼（并行与优化）的结构，高度解耦了模型逻辑与底层硬件。这种设计对你非常有利：你可以在 Apple Silicon 上调试上层的显存调度与计算图逻辑，而将 CUDA 特有的 Kernel 优化隔离在特定目录中。 1. 接口与应用层 (Interface & App Layer)：位于 include/edge-dit.h、examples/ 和 bindings/python/。项目以纯 C API 作为唯一事实标准，向上暴露给 C++ CLI (ed-cli)、HTTP Server (ed-server) 和 Python 绑定。这保证了跨语言调用的零开销。 2. 调度与流水线层 (Pipeline & Scheduling Layer)：位于 src/dit_models/pipelines/。这是 DiT 模型的业务中枢，定义了 DiTPipeline 基类。每种模型（如 FLUX、SD3、MiniMax-H3）在此实现自己的子类，负责文本编码、扩散步数调度（Scheduler）、以及最关键的显存规划（Memory Plan）。你的 --auto-fit 逻辑主要在这里与底层交互。 3. 模型与组件层 (Model & Component Layer)：位于 src/dit_models/models/ 和 src/dit_models/components/。这里将 DiT 拆解为可复用的积木：Transformer Block、VAE、CLIP/T5 Text Encoders。这种组件化设计是实现细粒度卸载（如 --text-encoder-offload）的基础。 4. 核心引擎与优化层 (Core Engine & Optimization Layer)：位于 src/core/。这是你日常打交道最多的地方。runtime/ 负责生命周期和后端设备管理；optimization/cache/ 实现了计算复用（CacheEngine）；parallel/ 实现了基于 NCCL/MPI/CPU 的分布式推理。对于只有 16GB Mac 的你，这里的分层卸载（Layered Offload）和显存水位控制逻辑是你验证端侧极限部署的核心。 5. 算子与后端层 (Kernel & Backend Layer)：位于 src/core/backend/ 和 third_party/ggml/。项目基于 ggml 构建计算图，但在 backend/ 下大量扩展了自定义算子。CUDA 后端（ggml/cuda/ 和 cuDNN/）包含了高度优化的 RoPE、Norm、cuDNN SDPA 和 SageAttention。你在 Mac 上开发时，将依赖 Metal 后端（通过 scripts/build_metal.sh 编译），而在 Colab T4 上验证时，则会切入这些 CUDA 专有路径。

一次调用怎么流过这些模块

一次完整的 Text-to-Image 推理数据流（以 FLUX 为例，结合 16GB 显存限制的场景）： 1. 初始化与显存规划 (Initialization & Memory Planning)： 用户通过 CLI 或 Python 发起请求，调用 EdgeDitEngine::init。引擎解析 ed_ctx_params_t。如果开启了 --auto-fit，ModelRuntime 会探测当前设备的可用显存（在你的 Mac 上是统一内存，在 T4 上是 16GB VRAM）。FluxPipeline::prepare_memory_plan 会根据显存上限，决定哪些组件（T5, CLIP, VAE）常驻显存，哪些放在 CPU 内存，以及 DiT Transformer Block 是否需要开启分层卸载（Layered Offload）。 2. 权重加载与量化 (Weight Loading)： ModelLoader 读取 GGUF 或 Safetensors 文件。如果使用的是预量化的 GGUF（如 q8_0），权重直接 mmap 到内存。如果是 Safetensors 且需要动态量化，则在 CPU 上完成转换后推入目标设备。 3. 文本编码 (Text Conditioning)： Prompt 传入 Conditioner，分别经过 CLIP 和 T5 编码器。如果开启了 --text-encoder-offload，此时会将 T5 权重从 CPU 搬至 GPU（或 Metal 显存），计算出 Embeddings 后立即释放显存，为后续 DiT 腾出空间。 4. 扩散去噪循环 (Diffusion Loop)： 进入 Scheduler 控制的 timestep 循环。在每个 step 中，构建 ggml 计算图。如果显存不足以装下整个 DiT，ed_async_offload.cu（CUDA）或对应的 Metal 逻辑会介入：将 DiT Block 逐个从 CPU 内存流式传输到 GPU 执行。CUDA 后端利用 CUDA Stream 实现计算与传输的异步双缓冲（Double-buffering）。 在计算图执行期间（ggml_graph_compute），遇到 Attention 节点时，CUDA 后端会派发给 ed_cudnn_sdpa.cu 或 SageAttention，Metal 后端则调用 MPS 对应的 Flash Attention 实现。 5. VAE 解码 (VAE Decoding)： 去噪完成后，得到 Latent tensor。如果图像分辨率极高导致 VAE 显存超标，引擎会自动触发 VAE Tiling，将 Latent 切块解码为 Pixel 数据。 6. 输出 (Output)： Pixel 数据转为 RGB 格式，通过 stb_image_write.h 保存为图片，或通过 C API 返回给 Python 侧。

扩展点

  • 新模型 (New Model)：在 src/dit_models/pipelines/ 下继承 DiTPipeline 实现新流水线，并在 src/dit_models/pipelines/dit_pipeline.cpp 的 create_dit_pipeline 工厂函数中注册版本枚举。
  • 新后端 (New Backend)：在 CMakeLists.txt 中添加编译选项（如 ED_GGML_VULKAN），并在 src/core/runtime/model_runtime.cpp 的 init_explicit_backend 中添加设备匹配与初始化逻辑。
  • 新 Kernel (New Kernel, e.g., Metal 优化)：在 src/core/backend/ggml/ 下添加扩展头文件（如 ed_ggml_attention_ext.hpp），并在对应的后端实现中（如 Metal 的 custom op）拦截 ggml 计算图节点进行替换。
  • 新调度/缓存策略 (New Cache Policy)：在 src/core/optimization/cache/policy/policies/ 下实现新的 CachePolicy 子类，并在 policy_factory.cpp 中注册，即可通过参数启用。

三、本地跑起来（没有 GPU 的 Mac）

安装

  1. git clone --recursive https://github.com/THU-MIG/edge-dit.cpp
  2. cd edge-dit.cpp
  3. bash scripts/build_metal.sh
  4. cd bindings/python && python -m pip install -e '.[dev]'

哪些路径能真跑

在你的 16GB Mac 上，你可以完整编译并运行 CPU 和 Metal 后端。你可以深入调试 src/dit_models/pipelines/ 下的显存规划（Memory Plan）与调度逻辑，以及 src/core/optimization/cache/ 的缓存策略和 src/utils/model_io/ 的 GGUF/Safetensors 解析。Metal 后端算子位于 third_party/ggml/ 中。而 src/core/backend/ggml/cuda/（如 ed_cuda_sage_attn.cu, ed_async_offload.cu）、src/core/backend/cuDNN/（cuDNN SDPA）以及 src/core/parallel/（NCCL/MPI）只能阅读源码，或在 Colab T4 上通过 bash scripts/build_cuda.sh 编译验证。

最小可运行

  1. ./build-metal/bin/ed-cli --help
  2. cd bindings/python && pytest
  3. ED_BACKEND=metal ./build-metal/bin/ed-cli --model /path/to/small-model --prompt "test" --steps 4 --output test.png

测试

主要依赖 Python 层的 pytest。测试用例位于 bindings/python/tests/（如 test_engine_lifecycle.py, test_config_validation.py）。根据 CONTRIBUTING.md，真实的模型集成测试默认跳过（需设置 EDGE_DIT_RUN_INTEGRATION=1），因此默认的单元测试只验证 C API 布局、配置和生命周期，在 Mac CPU/Metal 上运行极快（几秒到十几秒）。

调试

  • 环境变量 ED_BACKEND=cpu 或 metal 可强制切换后端进行交叉验证。
  • 编译时在 CMake 中开启 -DED_BENCHMARK_MARKERS=ON，可输出 stdout 阶段耗时标记（Phase markers），用于 Profiling 归因。
  • 对齐调试：设置 ED_DEBUG_FLUX_KONTEXT_ALIGN=1 和 ED_FLUX_KONTEXT_ALIGN_DUMP_DIR=/tmp，可将中间 Tensor 导出为 .f32.bin 和 .shape 文件（见 flux_kontext_pipeline.cpp）。
  • 分布式调试：CMake 开启 ED_DEBUG_SP_COMM=ON 追踪序列并行通信。

CI

项目使用 GitHub Actions（.github/workflows/）。根据 CONTRIBUTING.md，PR 会被 Python 层的 pytest 失败卡住。此外，由于项目强调多后端，CI 极大概率会交叉编译 CPU 和 CUDA 目标。未拉取子模块或引入未隔离的特定硬件代码也会导致构建失败。

坑

  • 克隆时漏掉 --recursive：项目重度依赖 third_party/ggml 等子模块，漏掉会导致 CMake 报错，需执行 bash scripts/bootstrap.sh 补救。
  • Mac 统一内存 OOM：16GB Mac 跑 FLUX 等大模型时，如果不加 --auto-fit 或手动指定 --dit-offload，会直接 OOM。
  • Qwen-Image Lightning 模型陷阱：它以 LoRA 形式发布，不能直接加载，必须先用 scripts/merge_qwen_lora.py 合并到 Base 模型。
  • Metal 后端实验性：README 明确指出 Metal 是 Experimental，遇到算子不支持或 Core Dump 时，需用 ED_BACKEND=cpu 交叉验证。
