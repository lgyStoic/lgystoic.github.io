一、项目定位

TurboDiffusion 是由清华大学（thu-ml）开源的端到端视频扩散模型（Video Diffusion Models）推理加速框架。其核心价值在于通过算法与系统协同优化，将原本需要数千秒的视频生成过程（如 Wan2.2-I2V-A14B）压缩至几十秒内，在单张 RTX 5090 上实现 100-200 倍的加速，且几乎不损失视频质量。项目深度整合了算法层的步数蒸馏（rCM，将采样步数降至 1-4 步）和系统层的注意力机制优化（SageAttention、SLA 稀疏线性注意力），并针对底层算子进行了深度定制（基于 CUTLASS 的 GEMM、RMSNorm、量化算子）。 对于你（资深 GPU kernel/性能工程师）而言，这个项目非常契合你的技术栈（CUDA、Triton、CUTLASS、DiT 加速、量化）。但**必须注意你的硬件硬约束**：你目前只有 Apple Silicon Mac 和 Colab T4。该项目的核心价值全在 GPU 算子上，且 `setup.py` 中硬编码了编译目标为 `sm_80` 到 `sm_120a`（Ampere 到 Blackwell）。这意味着你**无法在本地 Mac 上编译或运行任何核心代码**。如果要在 Colab T4 上做最终验证，你必须首先修改 `setup.py`，强行加入 `sm_75` 的编译选项，且需验证 Flash-Attention 和部分 Triton 算子在 T4 上是否会 fallback 或报错。你的切入策略应该是：在 Mac 上纯静态阅读源码、推导 CUTLASS 模板和 Triton 逻辑，编写好极简的单测脚本，然后利用 Colab T4 的几十分钟进行精准的编译和 Kernel 级 Profiling。

解决什么问题、给谁用

解决 DiT（Diffusion Transformer）架构视频生成模型（如 Wan2.1/2.2，参数量高达 14B）在推理时面临的“双高”问题：极高的计算延迟（多步迭代+全局注意力）和极高的显存占用。目标用户是需要快速生成高质量视频的 AI 研究员、AIGC 应用开发者，以及受限于消费级显卡（如 24GB/32GB 显存的 RTX 4090/5090）但希望运行百亿参数视频模型的极客玩家。典型场景包括文本到视频（T2V）、图像到视频（I2V）的快速生成与终端交互式生成（TUI）。

AI 视频生成领域的研究人员、AIGC 应用开发者、以及拥有 RTX 3090/4090/5090 等消费级/准专业级显卡并希望本地部署百亿参数 DiT 模型的极客与创作者。

同类项目与差别

  • Hugging Face Diffusers：Diffusers 是通用扩散模型的高层 Pipeline 库，侧重广度与易用性；TurboDiffusion 则是针对特定模型（Wan 系列）的极致深度优化，包含 Diffusers 原生缺乏的定制化 CUTLASS 算子和 rCM 蒸馏算法。
  • TensorRT / TensorRT-LLM：TRT 是 NVIDIA 官方的通用推理图优化引擎。TurboDiffusion 的差异在于它是“算法+系统”的联合优化，不仅有底层的量化和 Kernel（类似 TRT），还直接修改了模型的前向逻辑（引入 SLA 稀疏注意力和 rCM 减少步数），这是纯计算图编译器做不到的。
  • vLLM：vLLM 专注于自回归文本生成（核心是 PagedAttention 和 KV Cache 管理）；TurboDiffusion 专注于全量空间-时间注意力（Spatial-Temporal Attention）的视频生成，核心技术栈是 SageAttention 和步数蒸馏。

二、架构与代码地图

TurboDiffusion 的架构设计呈现出典型的「算法-系统-底层算子」三层协同优化的特征，深度融合了模型蒸馏与系统级加速。针对你（资深 Kernel 工程师）的背景和**只有 Mac + Colab T4 的硬约束**，我将仓库分为以下几个逻辑层，并标明你的切入可行性： 1. **底层算子层 (Kernel Layer - 你的核心关注点)**：位于 `turbodiffusion/ops/` 和部分 `utils` 目录下。包含基于 CUTLASS 深度定制的 CUDA C++ 算子（GEMM、RMSNorm、LayerNorm、Quantization）以及基于 Triton 实现的 FlashAttention JVP 和 Fast Norm。**注意硬约束**：`setup.py` 中硬编码了 `sm_80` 到 `sm_120a`。在你的 Mac 上这层代码完全无法编译，只能做纯静态的 C++ 模板推导和 Triton 逻辑走读；在 Colab T4 上，你必须手动修改 `setup.py` 注入 `-gencode arch=compute_75,code=sm_75` 才能尝试编译，且需做好部分 CUTLASS 模板在 Turing 架构上 fallback 或编译失败的心理准备。 2. **注意力与调度层 (Attention & Dispatch Layer)**：位于 `turbodiffusion/SLA/` 和 `turbodiffusion/rcm/utils/attention.py`。这里实现了 Sparse-Linear Attention (SLA) 以及基于 GPU Compute Capability 的动态 Attention 路由（FlashAttn3 -> cuDNN SDPA -> FlashAttn2 -> xformers）。在 T4 上，代码会自动 fallback 到 xformers 或基础 SDPA。 3. **算法与模型层 (Algorithm Layer)**：位于 `turbodiffusion/rcm/`。这是项目的核心算法区（rCM 步数蒸馏），包含 Wan2.1/2.2 的 DiT 网络定义、JVP（雅可比向量乘积）辅助网络、以及极少步数（1-4步）的 Euler/UniPC 采样器。 4. **训练基建层 (Infra Layer)**：位于 `turbodiffusion/imaginaire/`。这是一个庞大的分布式训练脚手架，封装了 DDP/FSDP、Hydra 懒加载配置（Lazy Config）、WandB 日志和各类 Callback。代码风格偏向 NVIDIA 内部框架。 5. **多模态扩展子系统 (Vendored Subsystem)**：位于 `turbot2va/LTX-2/`。这是近期合入的 LTX-2 音视频联合生成模块，自带了一套独立的 Triton 算子（如 `fast_norm_kernels.py` 和 `kernels.py` 中的随机舍入量化），这部分 Triton 代码对硬件要求相对较低，是你可以在 T4 上快速跑通 Profiling 的好切入点。

一次调用怎么流过这些模块

以 `wan2.1_t2v_infer.py` 的一次文本到视频 (T2V) 推理请求为例，完整的数据流如下： 1. **初始化与配置加载**：脚本启动，解析命令行参数（分辨率、步数、Attention 类型等）。通过 `imaginaire` 的 Lazy Config 系统实例化 Wan2.1 DiT 模型、VAE 和 umT5 文本编码器。如果指定了 `--quant_linear`，模型权重将以量化格式加载。 2. **条件编码 (Conditioning)**：输入的 Prompt 文本经过 umT5 编码器，生成 Text Embeddings。 3. **初始噪声生成**：根据设定的分辨率（如 480p）和帧数（如 81 帧），在 GPU 上生成初始的随机高斯噪声 Latents。 4. **rCM 极速去噪循环 (Denoising Loop)**：进入核心的扩散模型采样阶段。由于采用了 rCM 蒸馏，原本需要数十步的循环被压缩至 1-4 步。每一步中，Latents 和 Text Embeddings 被送入 Wan2.1 DiT Block。 5. **注意力机制路由 (Attention Dispatch)**：在 DiT Block 内部，计算 Attention 时会调用 `turbodiffusion/rcm/utils/attention.py`。系统会通过 `get_device_cc()` 检查当前 GPU 架构。如果用户指定了 `sagesla`，请求会被路由到 `turbodiffusion/SLA/` 模块；否则，根据硬件能力分发给 FlashAttention 3/2 或 SDPA。 6. **底层算子执行 (Kernel Execution)**：在进行 Linear 投影或 Norm 操作时，数据流进入 `turbodiffusion/ops/`。如果是量化模型，会调用基于 CUTLASS 的 `quant.cu` 和 `gemm.cu` 进行 W8A8/W4A16 等混合精度矩阵乘法；Norm 操作则调用 `rmsnorm.cu` 或 Triton 实现的 `fast_norm_kernels.py`。**（注意：在你的 Mac 上这一步会直接报错或 fallback 到极慢的 CPU 实现；在 T4 上，如果未修改 setup.py，会报找不到符号的错误）**。 7. **VAE 解码**：经过 1-4 步去噪后，最终的 Latents 被送入 VAE Decoder，上采样还原为像素级的视频帧 (Pixel Space)。 8. **输出保存**：视频帧序列被编码为 MP4 或 GIF 格式，保存到本地磁盘。

扩展点

  • turbodiffusion/ops/bindings.cpp & setup.py：新增 CUDA/CUTLASS Kernel：在 `ops/` 下编写 `.cu` 文件，在 `bindings.cpp` 中使用 pybind11 注册，最后在 `setup.py` 的 `sources` 列表中添加该文件。对于你的 T4 验证，必须在 `setup.py` 的 `cc_flag` 中强行加入 `-gencode arch=compute_75,code=sm_75`。
  • turbodiffusion/rcm/utils/ (或 turbot2va/.../kernels.py)：新增 Triton Kernel：直接编写 `@triton.jit` 函数，并封装一个 Python wrapper 处理 Tensor 连续性、dtype 检查和 Grid 划分。如果需要反向传播，需继承 `torch.autograd.Function`。
  • turbodiffusion/rcm/utils/attention.py：新增 Attention 后端（如接入新的 FlashInfer）：修改 `_SDPA_CONFIG_CACHE` 逻辑，在 `_get_sdpa_config` 中根据 `get_device_cc()` 的返回值增加新的路由分支。
  • turbodiffusion/rcm/configs/defaults/model.py & turbodiffusion/rcm/networks/：接入新模型架构：在 `networks/` 下实现新的 DiT 类，然后在 Hydra 配置文件中注册该类的 Lazy Call (L(YourModel))。

哪些路径能真跑

在你的 Apple Silicon Mac 上，真正能执行的只有纯 PyTorch 编写的算法逻辑与脚手架代码，包括：`turbodiffusion/rcm/` 下的调度器（如 `samplers/euler.py`、`utils/lr_scheduler.py`）、模型定义（`networks/wan2pt1.py`），以及 `turbodiffusion/imaginaire/` 下的配置解析（Lazy Config）和数据流逻辑。而 `turbodiffusion/ops/`（基于 CUTLASS 的 GEMM/Norm）和 `turbodiffusion/SLA/`（依赖 FlashAttention/Triton）在 Mac 上完全无法运行，只能做纯静态的代码走读。如果要在 Colab T4 上验证，需注意 T4 是 sm_75，而代码硬编码了 sm_80 起步，必须修改 `setup.py` 才能尝试编译。

调试

  • 日志开关：项目依赖了 `loguru`，可以通过设置环境变量 `LOGURU_LEVEL=DEBUG` 来获取更详细的运行日志；训练过程深度集成了 `wandb`（见 `turbodiffusion/rcm/callbacks/wandb_log.py`）。
  • Profiling 入口：项目在 `turbodiffusion/imaginaire/utils/profiling.py` 中封装了 PyTorch Profiler，可以在你编写的单测脚本中手动调用，用于分析 CPU/MPS 上的算子耗时。

CI

仓库根目录下没有 `.github/workflows/` 目录，说明该项目目前没有配置任何自动化的 CI（持续集成）流水线。PR 的合并完全依赖维护者的本地测试与人工 Code Review。

坑

  • Mac 编译必挂：`setup.py` 强依赖 `CUDAExtension` 和 `nvcc`，在 Mac 上执行 `pip install -e .` 会直接报错。必须通过配置 `PYTHONPATH` 绕过安装，或者手动注释掉 `ext_modules`。
  • Mac 内存 OOM：14B 模型参数量巨大，16GB 统一内存的 Mac 绝对无法加载，强行运行会导致系统严重 Swap 甚至崩溃。在本地只能尝试加载 1.3B 模型进行逻辑验证。
  • Colab T4 架构不支持：`setup.py` 硬编码了 `sm_80` 到 `sm_120a`。T4 是 Turing 架构（`sm_75`），直接编译会报错。必须手动在 `setup.py` 的 `cc_flag` 中添加 `"-gencode", "arch=compute_75,code=sm_75"`。
  • 算子 Fallback 失败：在 Mac 上运行推理脚本时，必须显式传入 `--attention_type original` 和 `--default_norm`，否则代码会尝试调用缺失的 CUDA 算子（SLA / 自定义 RMSNorm）导致崩溃。
