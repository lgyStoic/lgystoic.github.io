修复 `--attention_type original` 时的权重加载失败问题

Issue #122 · net.load_state_dict(state_dict, assign=True) 失败 ↗

目标：确保在 `--attention_type original` 模式下，模型能够成功加载量化或非量化权重而不抛出 `Unexpected key(s)` 异常。

为什么值得长期做：权重加载是推理的入口。修复此问题能提升项目的开箱即用体验，帮助你熟悉项目的模型结构变体（Original vs SageSLA），是接手模型架构维护的绝佳起点。

第一步：在 `turbodiffusion/inference/wan2.2_i2v_infer.py` 中编写一个仅实例化模型并加载权重的极简测试脚本，复现报错。
大致实施方案
  • 定位 `turbodiffusion/rcm/networks/wan2pt1.py` 中的模型定义，对比 `original` 和 `sagesla` 模式下的 `state_dict` 键值差异。
  • 在加载权重前（如 `net.load_state_dict` 调用处），实现一个 `filter_state_dict` 函数，当检测到 `original` 模式时，自动剔除或映射 `proj_l` 等特定于 SLA 的权重键。
  • 确保修改兼容 `assign=True` 参数，避免破坏显存优化逻辑。
  • 在 Issue 中与维护者确认是否需要保留这些多余权重的警告信息，然后提交 PR。
可能涉及的目录或文件
  • turbodiffusion/inference/wan2.2_i2v_infer.py
  • turbodiffusion/rcm/networks/wan2pt1.py
验收方式
  • 在 CPU 环境下运行修改后的推理脚本，设置 `--attention_type original`，验证 `load_state_dict` 成功执行且无致命报错。
开工前问题与风险

向维护者确认

  • 对于 `original` 模式下不需要的权重（如 `proj_l`），是直接在加载时 `pop` 掉，还是建议提供一个专门的 clean checkpoint？

风险

  • 如果使用 `assign=True`，过滤后的 `state_dict` 必须与模型当前的参数结构完全一致，否则可能引发底层张量分配错误。

修复 CUDA 架构编译错误 `compute_120a`

Issue #80 · 报错 nvcc fatal : Unsupported gpu architecture 'compute_120a' ↗

目标：修改编译配置，使其能够根据当前环境的 CUDA 版本动态选择支持的架构，避免在旧版本 CUDA 上因 `compute_120a` 导致编译失败。

为什么值得长期做：编译构建系统是 AI Infra 的基石。解决硬件兼容性问题能让你熟悉项目的 C++/CUDA 扩展编译流程，为后续引入更多自定义算子打下基础。

第一步：全局搜索 `compute_120a` 或 `120a`，定位硬编码的 CMake 或 setup.py 文件。
大致实施方案
  • 需先定位包含 `CUTLASS_NVCC_ARCHS_SUPPORTED` 或 `gencode` 的配置文件（可能是 `setup.py` 或 `ops/cutlass/CMakeLists.txt`）。
  • 引入逻辑检查当前 `nvcc --version`，如果 CUDA 版本低于 12.8，则自动从编译列表中移除 `120a` 等超前架构。
  • 或者，遵循 PyTorch 惯例，优先读取 `TORCH_CUDA_ARCH_LIST` 环境变量，赋予用户覆盖默认架构列表的能力。
  • 清理构建缓存并重新运行 `pip install -e .` 测试编译流程。
可能涉及的目录或文件
  • setup.py
  • CMakeLists.txt (需先定位)
验收方式
  • 在 CUDA 12.1 或 11.8 环境下运行 `python setup.py egg_info` 或实际编译，验证不再出现 `Unsupported gpu architecture` 错误。
开工前问题与风险

向维护者确认

  • 是否同意优先使用 `TORCH_CUDA_ARCH_LIST` 环境变量来控制编译架构？对于未设置该变量的用户，默认回退到哪些架构最合适？

风险

  • 修改 CMake 配置可能影响其他依赖项（如 Cutlass）的编译，需确保传递给子模块的架构参数格式正确。

对齐官方 Wan-Video 的 Patch Embedding 实现

Issue #114 · Question about different patch embedding implementation compared to official Wan-Video ↗

目标：解答 Issue 疑问，并提供代码层面的兼容方案，使得项目能够无缝加载官方使用 `nn.Conv3d` 的权重。

为什么值得长期做：模型结构的对齐直接关系到预训练权重的兼容性。处理此类问题能让你深入理解 DiT 的输入处理机制，建立对上游模型生态的敏锐度。

第一步：在 `turbodiffusion/rcm/networks/wan2pt1.py` 中对比 `nn.Linear` 的输入输出 shape 与官方 `nn.Conv3d` 的差异。
大致实施方案
  • 分析数学等价性：`nn.Conv3d(stride=patch_size)` 在展平后等价于 `nn.Linear`，但权重的 shape 和内存排布不同。
  • 编写一个轻量级的权重转换函数 `convert_patch_embed_weight`，将官方 `[out_dim, in_dim, k_t, k_h, k_w]` 的卷积核 reshape 为 `[out_dim, in_dim * k_t * k_h * k_w]`。
  • 在 `load_state_dict` 逻辑中集成该转换函数，或者在 `scripts/` 下新增一个独立的权重转换脚本。
  • 在 Issue 中回复作者，解释 `nn.Linear` 可能是为了适配某些算子或加速库，并提交包含转换逻辑的 PR。
可能涉及的目录或文件
  • turbodiffusion/rcm/networks/wan2pt1.py
  • turbodiffusion/scripts/convert_weights.py (需新建)
验收方式
  • 构造一个随机的官方格式 `Conv3d` 权重字典，通过你的转换逻辑加载到 `nn.Linear` 中，输入相同的 dummy tensor，验证输出数值的绝对误差在 `1e-5` 以内。
开工前问题与风险

向维护者确认

  • 当初选择 `nn.Linear` 替代 `nn.Conv3d` 是出于特定的性能优化考虑（如融合算子）吗？是否接受在加载权重时自动进行 reshape 转换？

风险

  • Reshape 时的维度顺序（如 C, T, H, W 的展平顺序）极易出错，必须严格对照 PyTorch 的内存排布进行单元测试。

修复分布式训练时的 `NotImplementedError` (Checkpoint Wrapper)

Issue #97 · NotImplementedError ↗

目标：修复 `trainer_distillation.py` 中因模型 forward 签名或 kwargs 传递不当，导致 `checkpoint_wrapper` 抛出 `NotImplementedError` 的问题。

为什么值得长期做：分布式训练的稳定性是 AI Infra 的核心。解决 Activation Checkpointing 的兼容性问题能证明你对 PyTorch 底层机制的深刻理解，是成为训练框架维护者的关键一步。

第一步：查阅 PyTorch `checkpoint_wrapper` 的源码，确认触发 `NotImplementedError` 的具体条件（通常是不支持 kwargs 或特定的输入类型）。
大致实施方案
  • 定位 `turbodiffusion/rcm/networks/wan2pt1.py` 中的 `forward` 方法，检查传递给 `checkpoint_wrapper` 包装的 `block` 的参数。
  • 如果 `checkpoint_wrapper` 不支持 kwargs，重构 `block` 的调用方式，将 kwargs 转换为位置参数（args），或者使用 `functools.partial` 包装。
  • 检查 `t2v_model_distill_rcm.py` 中的 `denoise` 调用，确保传递给网络的所有张量都设置了正确的 `requires_grad` 属性（Checkpointing 需要至少一个输入需要梯度）。
  • 编写一个极简的 mock 脚本，仅包含一个被 checkpoint 包装的 block，模拟训练时的前向和反向传播，验证修复方案。
可能涉及的目录或文件
  • turbodiffusion/rcm/networks/wan2pt1.py
  • turbodiffusion/rcm/models/t2v_model_distill_rcm.py
验收方式
  • 在 CPU 上运行修改后的 mock 脚本，成功执行 `loss.backward()` 而不抛出 `NotImplementedError`。
开工前问题与风险

向维护者确认

  • 目前使用的 PyTorch 版本是多少？是否考虑使用较新的 `torch.utils.checkpoint.checkpoint` API 并开启 `use_reentrant=False` 来替代旧的 `checkpoint_wrapper`？

风险

  • 修改 forward 签名可能引发连锁反应，影响推理脚本或其他未开启 checkpoint 的训练逻辑，需确保修改向后兼容。

支持多 GPU 并行推理脚本

Issue #5 · 有多GPU推理脚本吗？ ↗

目标：提供一个官方支持的多卡推理脚本，允许用户利用多张 GPU 加速单个视频的生成（如通过模型并行）或并行生成多个视频（数据并行）。

为什么值得长期做：多卡推理是端侧/服务器部署的高阶需求。主导此功能的开发能让你全面接管项目的部署架构，展现你在 AI Infra 领域的系统级设计能力。

第一步：分析 `turbodiffusion/inference/wan2.1_t2v_infer.py`，评估当前模型是否容易被 `accelerate` 的 `device_map="auto"` 切分。
大致实施方案
  • 方案 A（简单）：编写 `multi_gpu_batch_infer.py`，使用 `torch.distributed` 启动多个进程，将不同的 `num_samples` 分配到不同 GPU 上并行生成，最后合并结果。
  • 方案 B（进阶，针对单视频加速）：引入 `accelerate`，在加载模型时配置 `device_map="auto"`，让模型的不同 Transformer Block 分布在不同 GPU 上（Pipeline Parallelism 的雏形）。
  • 处理 VAE 和 Text Encoder 的设备分配，确保它们与 DiT 模型的输入输出设备匹配，避免跨设备张量操作报错。
  • 在脚本中添加详细的注释和启动命令示例（如 `accelerate launch ...`）。
可能涉及的目录或文件
  • turbodiffusion/inference/wan2.1_t2v_infer.py
  • turbodiffusion/inference/multi_gpu_infer.py (需新建)
验收方式
  • 在无 GPU 环境下，设置 `CUDA_VISIBLE_DEVICES=` 并使用 CPU 模拟多进程启动，验证数据分发和收集逻辑正确；或在低端双卡机器上验证显存占用被成功分摊。
开工前问题与风险

向维护者确认

  • 对于多卡推理，社区更迫切的需求是『加速单个高分辨率视频的生成』（需要模型切分/序列并行），还是『同时生成多个视频以提高吞吐量』（数据并行）？我计划先实现后者，是否合适？

风险

  • 如果采用模型切分，跨卡通信开销可能抵消计算加速，导致实际耗时反而增加，需在文档中明确说明适用场景。
