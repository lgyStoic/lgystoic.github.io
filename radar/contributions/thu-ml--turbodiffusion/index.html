Issue #102 · [Benchmark] Inference Performance on RTX 5090 with Wan2.1-1.3B (PyTorch 2.8.0) ↗

无人认领1 条评论更新 2026-02-05

用到的专长：PyTorch 性能分析与 Benchmark 规范

目标：修复用户测速脚本中缺少 warmup 和 CUDA 同步的问题，提供官方标准 benchmark 脚本。

为什么值得长期做：性能工程师对 Benchmark 的严谨性至关重要，提供标准的测速脚本能帮助项目建立可靠的性能基线，减少无效的性能质疑 Issue。

怎么介入：Issue 开放，无 assignee，无 linked PR，适合直接认领并解答用户的性能疑问。
第一个 PR 的边界：仅新增一个专门用于测速的独立脚本，不修改核心推理逻辑。
第一步：在 Issue 中指出用户测速代码的缺陷，并提议新增标准测速脚本。
认领留言（英文，可直接贴到 Issue）
Hi, the discrepancy is likely due to missing warmup iterations and `torch.cuda.synchronize()` in the timing script. I can add a standardized `benchmark_inference.py` script to the repository to help users reproduce the official performance metrics accurately. I'll submit a PR shortly.
大致实施方案
  • 在 Issue 中回复指出用户代码缺少 `torch.cuda.synchronize()` 和 warmup 迭代，导致测速不准。
  • 在 `scripts/` 目录下新增 `benchmark_inference.py`，引入标准的 PyTorch 同步计时逻辑。
  • 在脚本中加入 2-3 次 warmup 运行，随后进行 10 次迭代取平均耗时。
  • 在本地 4090 运行测试，确保输出格式清晰，并提交 PR。
可能涉及的目录或文件
  • turbodiffusion/inference/wan2.1_t2v_infer.py
  • scripts/benchmark_inference.py
验收方式
  • 运行新增的 benchmark 脚本，输出的耗时数据稳定，且能准确反映纯 DiT 采样阶段的真实耗时。
开工前问题与风险

向维护者确认

  • 官方 README 中宣称的 1.9s 是端到端时间（包含 VAE 编码/解码）还是纯 DiT 采样时间？

风险

  • 如果加入同步后测出的时间仍达不到官方宣称的性能，可能需要进一步 profile 寻找 CPU overhead。

Issue #80 · 报错 nvcc fatal : Unsupported gpu architecture 'compute_120a' ↗

无人认领1 条评论更新 2026-01-22

用到的专长：CUDA C++ / CMake 构建系统

目标：使 CMake 能够根据当前环境动态选择 CUDA 架构，避免在非 Blackwell 架构（如 A10/4090）上编译失败。

为什么值得长期做：解决底层算子库的编译构建问题能极大提升开源项目的易用性，是底层维护者掌控构建系统的第一步。

怎么介入：Issue 开放，无 assignee，无 linked PR，用户明确给出了报错日志，适合直接修复。
第一个 PR 的边界：仅修改 CMakeLists 和 setup.py 中的架构检测逻辑，不改动 C++ 源码。
第一步：检查 `ops/cutlass/CMakeLists.txt` 中的架构配置逻辑。
认领留言（英文，可直接贴到 Issue）
Hi, hardcoding `compute_120a` causes build failures on older GPUs like A10. I can update the CMake configuration to dynamically detect the target GPU architecture or respect the `TORCH_CUDA_ARCH_LIST` environment variable. I'll open a PR to fix this build issue.
大致实施方案
  • 修改 `ops/cutlass/CMakeLists.txt`，移除硬编码的 `120a` 等架构列表。
  • 引入 CMake 逻辑：优先读取 `TORCH_CUDA_ARCH_LIST` 环境变量。
  • 如果环境变量未设置，则通过 PyTorch 的 C++ 扩展工具或 `nvcc` 动态探测当前 GPU 架构。
  • 更新 `setup.py`，确保在执行 `pip install` 时正确传递架构参数给 CMake。
可能涉及的目录或文件
  • ops/cutlass/CMakeLists.txt
  • ops/cutlass/customConfigs.cmake
  • setup.py
验收方式
  • 在非 5090 的 GPU（如 T4 或 4090）上运行 `pip install -e .`，能够成功编译，不再报 `compute_120a` 错误。
开工前问题与风险

向维护者确认

  • 项目中的 CUTLASS kernel 是否强依赖 compute_90 以上的硬件特性（如 TMA/WGMMA）？如果是，需在 README 中明确说明最低硬件要求。

风险

  • 动态探测可能在某些无 GPU 的 Docker 构建环境下失效，需提供合理的 fallback 机制（如默认编译 80;89;90）。

目标：修复当 `--attention_type original` 时，模型加载包含 SLA 权重的 checkpoint 导致的 key 不匹配问题。

为什么值得长期做：保证向后兼容性和不同配置的可用性是框架成熟的标志，有助于深入理解模型在不同 Attention 模式下的结构差异。

怎么介入：Issue 开放，无 assignee，无 linked PR，适合快速修复。
第一个 PR 的边界：修改推理脚本中的 `load_state_dict` 逻辑，添加键过滤和警告信息。

认领留言（英文，可直接贴到 Issue）

大致实施方案
  • 运行 Issue 中的复现命令，捕获 `Unexpected key(s)` 错误（主要集中在 `proj_l`）。

验收方式

目标：提供一个支持多卡并行的推理脚本，降低 14B 模型的单卡显存压力，提升大分辨率视频的生成可行性。

为什么值得长期做：分布式推理是 14B 大模型落地的关键，主导此功能可确立在项目架构设计中的核心地位。

怎么介入：Issue 开放，无 assignee，多个用户（如 Issue 5）提出了类似需求，价值极高。
第一个 PR 的边界：新增一个基于 `accelerate` 的多卡推理脚本及相关 README 文档说明。
第一步：评估模型结构，决定使用 Pipeline Parallelism 还是基于 Accelerate 的层级切分。
认领留言（英文，可直接贴到 Issue）
Hi, I have extensive experience in distributed inference. I can help implement a multi-GPU inference script using `accelerate` for layer-wise partitioning, which will help users run the 14B model on multiple smaller GPUs. Would you prefer this approach or something more complex like Sequence Parallelism?
大致实施方案
  • 分析 `wan2.1_t2v_infer.py`，评估引入 HuggingFace `accelerate` 库的可行性。
  • 编写 `wan2.1_t2v_infer_multi_gpu.py`，使用 `accelerate` 的 `device_map="auto"` 对 DiT 模型进行层级切分（Pipeline Parallelism）。

开工前问题与风险

向维护者确认

  • 团队更倾向于使用 `accelerate` 进行简单的层切分，还是希望实现更细粒度的 Sequence Parallelism 以追求极致速度？

风险
